## 3. Getroffene Entscheidungen

1. Spool im Format `SIV_GCM`, jeder Schreibzugriff verschlüsselt jeden geänderten Block mit neuer Nonce; Blockvertauschung scheitert am AAD; Kürzen an Blockgrenzen ist im Format nicht erkennbar (Grenze).
2. Schlüssel: 32 Byte zufällig je Laufwerk, AES-KW mit `spool-wrap`, Datei `<spool-root>/<mount-id>/spool-key.wrapped`; Inhalts- und Textschlüssel per HKDF-SHA256 mit 64 Byte Ausgabe (`se-mount-spool-content-v1`, `se-mount-journal-v1`). Eine Schlüsseldatei, die nicht entwickelt, bleibt liegen (Fehler statt Überschreiben).
3. Tresorerkennung im Host: Backend-Schema `Vault` aus `MountHostReady`; kein neues Feld in `MountHostConfig`.
4. U02 offener Punkt 5: `detail`-Texte werden für Tresor-Laufwerke versiegelt (Trait-Methoden mit Identitäts-Standard; das U02-Signal bleibt unverändert). Commit: VLT-M12, weil `JournalPathSealer` sie umsetzt.
5. `PrepareLock`: lange Abfrage des Hosts über `MountHostExt` (höchstens 30 s, Host fragt mit 25 s); Antwort `PrepareLock { deadline_ms, keep_unsaved }` oder `Idle`; der Host antwortet auf derselben Verbindung mit `LockPrepared`. Ein Teilnehmer für alle Tresor-Laufwerke, Aufträge zugleich, gemeinsame Frist. Ohne Antwort bis zur Frist: Linux faules Aushängen und `fusectl`-Abbruch, danach Host beenden; Windows Host im Job-Objekt beenden. Bestätigung erst danach.
6. U06 Frage 1: Ein beim Anmelden gesperrter Tresor wird zurückgestellt (Status `Failed` mit Code `vault_locked`, mit Änderungen `RequiresUnlock { pending }`) und nach dem Entsperren eingebunden.
7. U06 Frage 2: Sperren behält den Registry-Eintrag; jedes Entsperren bindet das Laufwerk wieder ein und veröffentlicht die versiegelten Änderungen. Ausdrückliches Aushängen vergisst das Laufwerk wie bisher; beim Worker-Ende bleiben nur Laufwerke mit „Beim Anmelden automatisch einbinden“.
8. `MountRecovery::RequiresUnlock { pending: u32 }`, JSON `{"requires_unlock":{"pending":<n>}}` (Abweichung vom Plantext `recovery: "requires_unlock"`, weil die CLI die Zahl braucht).
9. Linux: Tresor-Laufwerk nur unterhalb des Tresor-Orts (`vault_place_refusal` beim Start; tmpfs-Prüfung im Host über `place_kind`).
10. Ablehnungstext einer Sperre nennt Laufwerksbezeichnung und Zahl, nie den Fehlertext des Veröffentlichens.
11. `MountPathFor` antwortet mit `IpcResponse::Mounts` (0 oder 1 Laufwerk), keine neue Antwortvariante; abgebildet werden `vault://` und `gdrive:///`; nur `vault://` wird bei `ensure_mounted_for` eingebunden (vorhandenes Laufwerk per Retry, sonst neu, lesend und schreibend, Tresor-Label).
12. Neue Daemon-Dateien als Kindmodule eigener Dateien (`mount_manager.rs`, `mount_client.rs`); `ipc_protocol_mount_host.rs` über Registrierungsbedarf in `daemon/drive_modules.rs`.
13. `se drive mount vault://<SITE>`: Ziel ohne Unterpfad, Label = Tresor-Bezeichnung, wenn `--label` fehlt; `vault-store://` wird abgelehnt.
