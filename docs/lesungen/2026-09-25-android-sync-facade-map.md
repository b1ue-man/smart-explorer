## 1. `SyncJob` — every field, type, meaning, default

`struct SyncJob` (`native/src/syncjobs/core/types.rs:62-135`). Defaults are from `SyncJob::new`
(`types.rs:148-193`, called with `direction=Both, conflict=FileLevel` etc.); `id` is generated by
`gen_id()` (`types.rs:137-143`) = lowercase-hex of nanoseconds-since-epoch — **no collision check
anywhere**; two jobs created in the same clock tick on a coarse timer would silently share an id
and one would overwrite the other's `<id>.conf` on the next `upsert`.

### 1.1 `Trigger` (`syncjobs/core/types.rs:7-58`)
`Manual | Interval | Calendar | RealTime | OnStartup | OnConnect`. `as_str()`/`parse()` give the
persistence codec's string form; `label()` gives the German UI label; `Trigger::ALL` (6 entries) is
what the editor's combo box iterates. `SyncJob::due(now)` (`syncjobs/core/schedule.rs:36-63`)
returns `true` **only** for `Interval`/`Calendar` (the `_ => false` arm, line 61) — the other three
are event-driven and evaluated only inside the daemon's own tick loop (§8).

### 1.2 `SyncJob` methods a facade will call

| Method | Signature | file:line |
|---|---|---|
| `new` | `fn new(name: String, source: String, target: String) -> Self` | types.rs:148 |
| `validate` | `fn validate(&self) -> Result<(), String>` | validation.rs:18 |
| `due` | `fn due(&self, now: i64) -> bool` | syncjobs/core/schedule.rs:36 |
| `active_now` | `fn active_now(&self, now: i64) -> bool` | schedule.rs:66 |
| `checked_opts` | `fn checked_opts(&self, dry_run: bool) -> Result<bisync::BisyncOptions, String>` | types.rs:237 |
| `checked_filter_bounds` | `fn checked_filter_bounds(&self, now_secs: i64) -> Result<(u64,u64,i64,i64), String>` | types.rs:204 |
| `checked_glob_set` | `fn checked_glob_set(&self) -> Result<globset::GlobSet, String>` | validation.rs:29 |

`opts()`/`filter_bounds()`/`glob_set()` are infallible wrappers that fail closed (dry-run + no
delete, or a match-everything reject-glob) rather than panic — a facade should prefer the
`checked_*` forms and surface the `Err(String)` to the caller instead of silently falling back.

**"Next due time":** there is no ready-made function for it. `SyncJob::due(now)` only answers
"due right now"; the daemon calendar helper `last_occurrence` (`syncjobs/core/schedule.rs:87-109`,
`pub(super)`/private) only searches **backward** from `now` for the most recent past occurrence —
there is no forward "next occurrence" search anywhere in the read surface. A facade's "next run"
column must either reproduce the schedule **description** the desktop UI shows (trigger kind +
params, `menus_sync_jobs.rs:124-156`) or implement a new forward search itself.

## 4. `bisync` options and outcome

`BisyncOptions` (`bisync/core/types.rs:258-293`, `Default` at 295-320 = "the safe default"):
`direction, conflict, reversible: bool, dry_run: bool, delete: DeletePolicy, move_files: bool,
compare: CompareMode, modify_window_ms: i64, versioning: Versioning{scheme,days,count},
use_recycle: bool, max_delete: u64, max_delete_pct: u8, bwlimit_bps: u64, max_transfers: usize,
atomic: bool, verify: bool, retries: u32, retry_delay_secs: u64`.
`SyncJob::checked_opts` (types.rs:237-271) is the sole place that derives this from a `SyncJob`
(unit conversions: KB→bytes, seconds→ms, with `checked_mul`/`try_from` overflow guards).

`ConflictMode::ALL` (8, `bisync/core/types.rs:108-117`): `FileLevel` (strict, default),
`NewerWins, OlderWins, LargerWins, SmallerWins, SourceWins, DestWins, KeepBoth`. Only `FileLevel`
surfaces a manual conflicts dialog; the other 7 resolve automatically inside `plan()` (not in my
read surface) — a facade offering "conflict mode" must reproduce all 8, not just strict.

`bisync::run` (`bisync/os/shared/orchestration.rs:35-49`, re-exported `bisync::mod.rs:70`):
```
pub fn run(
    a: &dyn Backend, root_a: &str, b: &dyn Backend, root_b: &str,
    opts: BisyncOptions, cancel: &AtomicBool, filter: &WalkFilter,
) -> Outcome
```
Runs **synchronously to completion on the calling thread**; the app always calls it from a spawned
`std::thread` (`app/core/sync_core.rs:181-195`) and receives exactly **one** message — the final
`Outcome` — over an `unbounded()` channel. **There is no progress callback/streaming for `bisync::run`
itself** (contrast §6: the one-way `crate::sync` engine below does stream progress).

`Outcome` (`orchestration.rs:23-30`): `{ stats: BisyncStats, conflicts: Vec<Conflict>, errors: Vec<(String,String)>, baseline: Baseline, omissions: SyncOmissions }`.
`BisyncStats` (`types.rs:387-395`): `{ a_to_b, b_to_a, deleted, conflicts, bytes, errors: u64 }`.
`Conflict` (`types.rs:380-385`): `{ rel: String, a: Option<Sig>, b: Option<Sig> }`.
`Sig` (`types.rs:4-12`): `{ size: u64, mtime_ms: i64, hash: u64 }`.
`WalkFilter<'a>` (`bisync/os/shared/snapshot.rs:18-28`): `{ include_hidden: bool, ignore: &'a globset::GlobSet, min_size: u64, max_size: u64, after_mtime_ms: i64, before_mtime_ms: i64 }`; `WalkFilter::basic(include_hidden, ignore)` (snapshot.rs:37) is the no-bounds convenience constructor.

## 5. Baseline / conflicts / omissions persistence

- `pair_id_for(a,root_a,b,root_b) -> String` (`bisync/os/shared/persistence.rs:25-34`): a stable,
  order-sensitive (A vs B matters), backend-identity-sensitive (`Backend::state_identity()`) hash
  — same-looking paths on **different** backends/remotes get different pair ids, matching
  AGENTS.md's "equal backend-relative paths on different remotes are different locations" rule.
- `baseline_path(pair) -> PathBuf` / `versions_dir(pair) -> PathBuf` (persistence.rs:55-61):
  `<sync_data_dir>/baseline_<pair>.sebl` and `<sync_data_dir>/versions_<pair>/`.
- `load_baseline(path) -> io::Result<Baseline>` / `save_baseline(path,&Baseline) -> io::Result<()>`
  (persistence.rs:63-82, 171-219): custom binary format (`SEBL\x02` magic), 128 MiB / 1,000,000-entry
  budget, atomic staged-write-then-`promote_staged_replace`. **`bisync::run` loads and saves the
  baseline itself** (`orchestration.rs run_full` at lines 109-122, 362-374) — the caller never
  passes a baseline in.
- `Baseline = BTreeMap<String, (Option<Sig>, Option<Sig>)>` (`types.rs:18`) — last-known signature
  per relative path per side; absence on one side = "didn't exist at last sync".
- **Conflicts are not separately persisted.** There is no on-disk "conflict list" file — a
  `Conflict` only exists as a member of the `Outcome.conflicts` returned by the run that just
  finished, held in `App.bisync_conflicts` (`app/core/state.rs:359`) for the session. To "list
  conflicts of a pair" without having just synced, a facade must itself invoke `bisync::run(...)`
  (optionally `dry_run: true`) and read `.conflicts` from the result — there is no separate query.
- `prune_versions(versions_dir, &Versioning) -> io::Result<()>` (persistence.rs:302-356): applies
  the job's `versioning_scheme` (Days/Count/Staggered/Gfs) after a successful non-dry-run.

### 5.1 `resolve_checked` — signature and semantics

```rust
// bisync/os/shared/resolve.rs:74-84
pub fn resolve_checked(
    a: &dyn Backend, root_a: &str, b: &dyn Backend, root_b: &str,
    conflict: &Conflict, keep_a: bool, pair: &str, cancel: &AtomicBool,
    mut progress: impl FnMut(ResolvePhase),
) -> io::Result<(Option<Sig>, Option<Sig>)>
```
- Revalidates the **exact displayed signatures** at commit time (`conflict.a`/`conflict.b` become
  `ExpectedFile::Present(sig)`/`Missing`) — rejects if either side drifted since the conflict was
  shown to the user (drift/type errors never silently proceed).
- `keep_a=true`: copies A over B, backing up B's current bytes into `versions_dir(pair)` first
  (reversible); `keep_a=false`: the mirror image. If the **winning** side is absent, the losing
  side is deleted (guarded, reversible) instead of copied.
- `ResolvePhase` (`resolve.rs:13-19`): `Preparing, BackingUp, Copying, Deleting, ReadingSignatures`
  — the only progress granularity; no byte/percentage progress inside a phase.
- Returns the **new** post-resolution `(Option<Sig>, Option<Sig>)` for (A,B); the caller must
  `baseline.insert(rel, signatures)` and persist via `save_baseline`. That merge-and-persist step
  is **not** inside `resolve_checked` — it is app logic (`bisync_conflicts.rs:262-318,322-351`).
- `resolve(...)` (resolve.rs:25-66) is a simpler, non-progress compatibility entry point that
  captures state at call time instead of against a caller-supplied `Conflict` snapshot; the
  interactive path should use `resolve_checked`.

There is **no manual "keep both" mode in `resolve_checked`** — `ConflictMode::KeepBoth` is only an
automatic `plan()`-time policy. The desktop conflicts dialog (`bisync_conflict_ui.rs`) offers only
four manual actions per row: keep A, keep B, line-merge, or skip (§6). "Keep both" as a *manual*
per-conflict action exists only inside the line-merge dialog for text files (§7).

### 5.2 `SyncOmissions` (`bisync/core/omissions.rs`)

Tracks protected symlink/junction subtrees skipped during a walk. Key methods: `protects(rel)`,
`contains(rel)`, `exclude_tree(&mut Tree)`, `planning_baseline`/`preserve_baseline` (keep the
baseline entries for omitted paths untouched across runs — "never let a partial scan seed a
complete incremental index"), `summary() -> Option<String>` (German, up to 3 sample paths),
`result_note(status) -> String` (folds the omissions summary into a `JobResult.note`).

## 6. Conflicts dialog flow (`app/core/bisync_conflicts.rs`, `bisync_conflict_ui.rs`)

`bisync_conflicts.rs` has **zero egui imports** — it is a self-contained worker-thread
lifecycle (spawn → phase updates → terminal result) wrapping `resolve_checked`, and is a strong
"extractable near-verbatim" candidate: its only App-coupling is (a) reading/writing a handful of
`App` fields as a task table instead of local struct fields, and (b) calling `self.rescan()`
(out of my surface) which a facade would replace with "tell the caller the view is stale".

- `start_conflict_resolution(index, side, from_bulk) -> bool` (bisync_conflicts.rs:92-179):
  rejects if a resolution or merge is already active; clones the `Conflict` and the `BisyncCtx`
  (`a,b: BackendHandle, root_a,root_b,pair: String`, `support_paths.rs:31-38`); spawns a
  `"bisync-conflict"` thread calling `resolve_checked`; phase updates and the terminal
  `Ok/Err` go over a **bounded(8)** channel (at most 5 messages per resolution: up to 5
  `ResolvePhase`s + 1 terminal).
- `drain_conflict_resolution()` (192-260): drains up to 8 messages/frame; on success calls
  `apply_conflict_resolution_result` (262-318): merges the new sigs into `bisync_ctx.baseline`,
  sets `conflict_baseline_dirty=true`, removes the conflict from `App.bisync_conflicts`
  (`swap_remove`), and — if that was the last conflict — calls `finish_bisync_conflicts()`.
- `finish_bisync_conflicts() -> bool` (322-351): if the baseline is dirty, `save_baseline(...)`;
  on failure, the dialog **stays open** (returns `false`) with an explicit "Speichern erneut
  versuchen" retry (`bisync_conflict_ui.rs:240-254`) — a resolved-but-unsaved conflict is never
  silently dropped. On success: closes the dialog, clears bulk state, rescans if a folder is open.

## 9. Endpoint resolution (`connect`)

- `resolve_endpoint(endpoint: &str) -> Result<(BackendHandle, String), String>`
  (`connect/os/shared/resolution.rs:7-35`): parses via `EndpointSpec::parse` (`connect/core/location.rs:15-51`)
  into `Local(path) | Saved(url) | Drive(path) | Peer(target,path)`; a **local** path that is
  itself a UNC path is checked against saved connections first (`unc_is_same_or_below`, longest
  matching root wins) so a UNC endpoint stored under a saved connection reconnects with its
  credentials instead of falling back to a raw, unauthenticated UNC open. `Saved`/`Peer`/`Drive`
  route through `creds::load_connections_checked`/`daemon::open_share_backend`/`connector::open_gdrive`
  (out of my surface, signature-only).
- `validate_sync_endpoints(source, target) -> Result<(), String>` (`connect/core/location.rs:105-114`):
  parses both, then rejects only when they resolve to the **same backend identity** AND
  overlapping (equal or one-nested-in-the-other) paths — `"Quelle und Ziel müssen verschieden und
  dürfen nicht ineinander verschachtelt sein (distinct, non-nested endpoints)."`. Backend identity
  keys differ by scheme+host+user+port for saved connections, so the same-looking local path under
  two **different** SFTP hosts is correctly treated as non-overlapping (matches AGENTS.md's
  cross-remote-pair compatibility rule).
- `run_job`'s connect step (`app/os/shared/sync_jobs.rs:6-52`) resolves **both** endpoints
  off-thread with a single `("job-connect")` worker before ever touching `bisync::run`; on error,
  the job never launches and no state is left running.

### 11.1 `run_daemon()` and a hypothetical "run all due jobs once, then return"

`run_daemon()` (`daemon/os/shared/schedule.rs:134`, re-exported `daemon/mod.rs:155`) takes no
parameters, reads `SMART_EXPLORER_DAEMON_HANDOFF`/`..._RETIRING_GENERATION` env vars
(`autostart::DAEMON_HANDOFF_ENV`/`DAEMON_RETIRING_GENERATION_ENV`, `autostart/mod.rs:8-9`), takes
an OS-level `flock` single-instance guard (`acquire_instance_guard`, out of my surface,
schedule.rs:168-175), and then **never returns** (`loop { … }`, lines 229-374).

A one-shot "run all due jobs once" facade function is not exposed today and would have to be
assembled from these pieces:

| Piece | Visibility | Usable directly from outside `daemon`? |
|---|---|---|
| `syncjobs::load()` + `SyncJob::due(now)` | fully `pub` | **Yes** — filter the loaded list by `due(now_secs)` |
| `job::run_one(job: &SyncJob, cancel: &AtomicBool)` | `pub(crate)` inside `daemon` (job.rs:10) | **No** — not re-exported from `daemon::` (mod.rs's `pub use` list omits it); needs either a new `pub fn` wrapper in `daemon`, or the facade reimplements its body from already-public pieces (`connect::resolve_endpoint`, `bisync::run`, `syncjobs::mark_run`/`record_result`) |
| `JobSupervisor` | `pub(super)` (job_supervisor.rs:33) | **No**, and not needed — it exists to serialize+dedupe **concurrent** enqueue attempts across daemon ticks; a simple sequential loop over due jobs doesn't need its queue/cooldown machinery |
| `platform::run_shell_command` (for `run_before`/`run_after`) | daemon `os`-adapter-only | **No** — Linux-only shared adapter, unread in this surface |

**Behavior gap worth flagging explicitly**: `run_before`/`run_after` shell hooks (`job.rs:46-64,
117-127`) fire **only** from the daemon's `job::run_one` — the GUI's own "▶ Jetzt" path
(`app/os/shared/sync_jobs.rs` → `sync_core.rs::launch_bisync`) calls `bisync::run` **directly**,
never touching `run_before`/`run_after`. A facade author must decide explicitly whether an
interactive "run now" should also run these hooks (matching the daemon) or not (matching today's

**RealTime/OnStartup/OnConnect jobs are entirely invisible to `due()`** (`syncjobs/core/schedule.rs:61`,

helper built from `due()` alone will **silently skip** all three trigger kinds; treating every
enabled `OnStartup` job as "due" on an explicit app-launch call is a plausible facade-side
special-case, but nothing in this read surface already does it outside the full tick loop.

## Facade call recipes

Every recipe below is written against the crate's **public** API where one exists, and flags the
exact gap when it does not (daemon job-run and next-due-time, §1/§11.1).

### (1) List jobs + last result

1. `jobs = crate::syncjobs::load()` → `Vec<SyncJob>` (`syncjobs/os/shared/persistence.rs:140`).
2. `results = crate::syncjobs::load_results()` → `BTreeMap<String, JobResult>` (`results.rs:27`).
3. For each job, join by `job.id` → `results.get(&job.id)` for last-run stats (a_to_b/b_to_a/deleted/conflicts/errors/note), same as `menus_sync_jobs.rs:56,174-188`.
4. Optional "due now" flag: `job.due(now_secs)` per job (`syncjobs/core/schedule.rs:36`) — **not** a next-run timestamp (see §1 gap); render the trigger/schedule fields as a description instead, as `menus_sync_jobs.rs:124-156` does.
5. Persist: nothing (pure read). Await: nothing — synchronous filesystem calls, safe off the UI/main thread.

### (2) Create / edit a job

1. Collect the draft as a String-typed object mirroring `JobEditor` (`app/core/job_editor.rs:3-52`) — every `SyncJob` field, numbers as strings.
2. `job = JobEditor::build_sync_job(&draft, existing.as_ref())` (`app/core/job_editor_validation.rs:5`) — reuse this function verbatim (it is already egui-free); on `Err(String)` surface the German text to the user (§2.1 table).
   - If reimplementing outside `app/` instead of calling into it: replicate the same order — `validate_endpoints` → `validate_ignore_patterns` → the two direction/delete_policy/move_files cross-checks → parse every numeric field via `parse_number` → build/patch the `SyncJob` → final `job.validate()`.
3. Persist: `crate::syncjobs::upsert(&job)` (`persistence.rs:146`) — this itself re-validates (`write_job` → `job.validate()`) and atomically writes `jobs/<id>.conf`.
4. Reload the cached list: `crate::syncjobs::load()` (as in `job_editor_ui.rs:343-357`).
5. Await: nothing async — both calls are synchronous filesystem I/O; no channel/event involved unless the facade itself makes them async.

### (3) Enable / disable, delete a job

1. **Enable/disable**: load the job (from the cached list or `syncjobs::load()`), flip `enabled`, `crate::syncjobs::upsert(&job)` (`menus_sync_jobs.rs:202-212`), reload the list.
2. **Delete**: `crate::syncjobs::remove(&id)` (`persistence.rs:151`), reload the list (`menus_sync_jobs.rs:214-221`).
3. Persist: the `upsert`/`remove` call itself. Await: nothing.

### (4) Run a job now, with progress and cancel

1. Guard against a concurrent run (facade-side equivalent of `bisync_running || sync_running || job_connect_rx.is_some()`, `app/os/shared/sync_jobs.rs:7`).
2. `job.validate()` then `job.checked_opts(false)` and `job.checked_filter_bounds(now_secs())` (`app/os/shared/sync_jobs.rs:107-113`, `checked_job_settings`) — reject before touching the network.
3. Resolve both endpoints, ideally off the calling thread: `crate::connect::resolve_endpoint(&job.source)` and `(&job.target)` → each gives `(BackendHandle, String)` (`connect/os/shared/resolution.rs:7`). Await: the resolve step (network/credential I/O) — this is exactly the `"job-connect"` thread + channel in `sync_jobs.rs:24-34`.
4. Build the filter: `WalkFilter { include_hidden: job.include_hidden, ignore: &job.checked_glob_set()?, min_size, max_size, after_mtime_ms, before_mtime_ms }` from step 2's bounds (`sync_core.rs:184-191`).
5. Run (on a worker thread — this call blocks until the whole sync finishes; **no progress messages, only one final result**): `out = crate::bisync::run(&*a, &root_a, &*b, &root_b, opts, &cancel, &filter)` (`bisync/os/shared/orchestration.rs:35`). Await: the single terminal message on whatever channel/future the facade uses to bridge the thread.
6. Cancel: set the `AtomicBool` passed as `cancel` to `true` from another thread at any time; `bisync::run` checks it between phases/directory levels, never mid-file-write (reversibility preserved).
7. Persist the result — **all three steps are required together** (`bisync_ui.rs:201-234`, out of my assigned surface but load-bearing, confirmed by signature read):
   - `crate::syncjobs::mark_run(&job.id)` (`results.rs:115`) — updates `last_run`.
   - `crate::syncjobs::record_result(&job.id, &JobResult{ when: now_secs(), a_to_b: out.stats.a_to_b, b_to_a: out.stats.b_to_a, deleted: out.stats.deleted, conflicts: out.conflicts.len() as u64, errors: out.errors.len() as u64, note: out.omissions.result_note(note) })` where `note` = `"abgebrochen"` if canceled, else `"Fehler"` if `!out.errors.is_empty()`, else `"Konflikte"` if `!out.conflicts.is_empty()`, else `"ok"` (`results.rs:12-21`).
   - Reload the job list: `crate::syncjobs::load()`.
8. Hold `out.baseline` and `out.conflicts` in the facade's session/task state (NOT re-persisted separately — `out.baseline` was already saved to disk *inside* `bisync::run` when it succeeded without errors/conflicts; the caller's copy is only needed to feed conflict-resolution/merge, §5/§6/§7) — mirrors `ctx.baseline = out.baseline; self.bisync_conflicts = out.conflicts;` (`bisync_ui.rs:236,240`).
9. If `out.conflicts` is non-empty, surface the conflicts flow (recipe 6) as the natural next step (`bisync_ui.rs:278-280`).

### (5) Quick mirror of the current folder to a target

1. Resolve the **source**: whatever backend+root the facade's "current folder" concept already tracks (Android has no split-view/tab pane lookup to reproduce — `pane_backend`, §10, is GUI-shape-specific and should not be ported as-is).
2. Resolve the **destination**: same `connect::resolve_endpoint`-style resolution as recipe 4, or a locally-picked target path/backend.
3. `handle = crate::sync::start_sync(src, src_root, dst, dst_root, crate::sync::SyncOptions { delete_extra: false, dry_run: false }, tx)` (`sync/os/shared/sync.rs:146`) — **exact options the desktop menu uses**; expose `delete_extra` as a facade-level choice only if the product wants a configurable mirror (the desktop menu itself hardcodes it off).
4. Await: `SyncMsg::Progress(SyncProgress{current, stats, elapsed_ms})` messages repeatedly (live progress, unlike bisync), then one `SyncMsg::Done(SyncResult{stats, errors, omissions, elapsed_ms})`.
5. Cancel: `handle.cancel.store(true, Ordering::Relaxed)`.
6. Persist: **nothing** — a quick mirror has no job id, is never saved, and updates no baseline/results store. If the facade wants "save this as a job," that is a **separate** action — pre-fill a `JobEditor`-shaped draft with `source`/`target` and route through recipe 2 (`menus_sync.rs:147-154`, `begin_pane_sync_setup`, out of my assigned surface).

### (6) List conflicts of a pair, resolve each (keep A / keep B / keep both)

1. There is no persisted conflict list — conflicts only exist as the `conflicts: Vec<Conflict>` field of the `Outcome` from the **most recent** `bisync::run` for that pair (recipe 4, or a fresh `dry_run: true` run purely to enumerate them). Keep the resulting `BisyncCtx`-equivalent (`a,b: BackendHandle`, `root_a,root_b: String`, `pair: String`, `baseline: Baseline`) alive in session state — every resolution below needs it.
2. **Keep A** or **Keep B** for one conflict:
   ```
   let (sig_a, sig_b) = crate::bisync::resolve_checked(
       &*a, &root_a, &*b, &root_b, &conflict, keep_a /* true=A wins */, &pair,
       &cancel, |phase| /* ResolvePhase: Preparing→BackingUp→Copying/Deleting→ReadingSignatures */,
   )?;
   ```
   (`bisync/os/shared/resolve.rs:74`). Await: the `ResolvePhase` stream (facade progress UI) then the terminal `Result`.
3. On success: `baseline.insert(conflict.rel.clone(), (sig_a, sig_b))`; `conflict_baseline_dirty = true`; remove the conflict from the session list.
4. **Keep both** for a *binary* conflict: not offered by `resolve_checked` — the desktop UI only exposes "keep both" for text files via the line-merge dialog (recipe 7's "keep both" step). A facade wanting a binary "keep both" would need new logic (write the loser under a `conflict_rel_name`-style copy, then call `resolve_checked` with the winner) — **not an existing call**, flag as a gap if required.
5. **Bulk "resolve all with side X"**: loop step 2 against index 0 of the remaining conflict list with the same `keep_a`, once per completed resolution (`bisync_conflict_ui.rs:184-189`) — purely a client-side loop, no bulk API in `bisync`.
6. **Skip** one conflict: drop it from the session list only; nothing persisted, it will reappear on the next `bisync::run` for the same pair.
7. When the session list becomes empty (or when the dialog is closed early): if `conflict_baseline_dirty`, `crate::bisync::save_baseline(&crate::bisync::baseline_path(&pair), &baseline)` (`persistence.rs:171`) — **must succeed before considering the pair "settled"**; on failure, keep offering retry, never discard the dirty baseline (`bisync_conflicts.rs:322-351`).

### (7) Line merge of a text conflict

1. Load both versions off-thread: `read_text(&*a, ep_join(&root_a,&rel))` / `read_text(&*b, ep_join(&root_b,&rel))` (`app/os/shared/remote_helpers.rs:73-74,101`) — enforce the same 16 MiB/side, UTF-8-only, no-binary rules if reimplementing outside `app/`.
2. `rows = crate::linemerge::rows(&text_a, &text_b)?` → `Result<Vec<Row>, LineMergeError>` (`linemerge/core/linemerge.rs:230`). Surface `LineMergeError` messages directly (already German, `linemerge.rs:33-56`) on `InputTooLarge`/`TooManyLines`/`TimedOut`/`InvalidTimeout`.
3. Let the user toggle `take_left`/`take_right` per non-equal `Row` (equal rows are fixed).
4. **Apply/merge**: `merged = crate::linemerge::assemble_rows(&rows)` (`linemerge.rs:300`) → write `merged` bytes to **both** `ep_join(root_a,rel)` and `ep_join(root_b,rel)` via `write_bytes` (`remote_helpers.rs:129`) → `sig_from` both sides (`remote_helpers.rs:153`) → `(rel, Sig, Sig)`.
5. **Keep both** instead: `a_full = crate::linemerge::side_a(&rows)`, `b_full = crate::linemerge::side_b(&rows)` (`linemerge.rs:284,292`) → write `a_full` under `rel` on **both** sides, write `b_full` under `crel = conflict_rel_name(rel)` (`remote_helpers.rs:78`) on **both** sides → `sig_from` both original-name paths.
6. Persist exactly as recipe 6 step 3/7: `baseline.insert(rel, (sig_a, sig_b))`, mark dirty, remove from the session conflict list, save the baseline once no conflicts remain (or on explicit close).
7. Await: the merge-load thread's result, then (on apply/keep-both) the write-thread's result — two sequential async steps, matching `merge_load_rx`/`merge_apply_rx` (`app/core/state.rs:366-367`).

### (8) Background daemon control

1. **Read "background sync enabled"**: `crate::autostart::is_enabled() -> bool`.
2. **Turn on**: `crate::autostart::enable()?` → on success `crate::daemon::request_daemon_replacement()`; on that failure, roll back with `crate::autostart::disable()` and report both errors (`settings_background.rs:23-43`).
3. **Turn off**: `crate::autostart::disable()?` only — **do not** call `request_stop()` here; the running daemon (if any) keeps Share/LAN/mount alive and stops scheduling on its own next tick.
4. **Pause**: `crate::daemon::pause_for_secs(2*3600 | 8*3600 | 24*3600)` or `pause_indefinite()`; **resume**: `crate::daemon::resume()`; **status**: `crate::daemon::pause_remaining() -> Option<i64>`.
5. **Autopause**: `crate::daemon::autopause_flags() -> (battery, metered)`; `set_autopause_flags(battery, metered)` — remember these are currently no-ops on Linux (§11 stubs); Android-inherited-as-is would need real `BatteryManager`/`ConnectivityManager` checks to matter.
6. **Cadence**: `crate::daemon::cadence_secs() -> u64` (2..=3600) / `set_cadence_secs(u64)`.
7. **Liveness**: `crate::daemon::is_running() -> bool`, `crate::daemon::last_heartbeat_age() -> Option<i64>`.
8. **Log**: `crate::daemon::read_log_tail(lines: usize) -> String`.
9. **Stop**: `crate::daemon::request_stop()` — file-based, transport-agnostic; safe to call regardless of whether the daemon is a separate process or an in-process loop.
10. **"Run all due jobs once, then return"** — no ready-made call; assemble from public pieces (§11.1 table): `due = syncjobs::load()?.into_iter().filter(|j| j.due(now_secs))`; for each due job, either (a) add a new `pub fn` to `daemon` that wraps the private `job::run_one`, or (b) reimplement its body directly using `connect::resolve_endpoint` + `bisync::run` + `syncjobs::mark_run`/`record_result` (all public) — deciding first whether `run_before`/`run_after` hooks should fire from this path (daemon does; the GUI's "Jetzt" does not — §11.1 gap). **RealTime/OnStartup/OnConnect jobs will not appear in `due` and need separate, explicit handling** if the facade wants to honor them at all (§11.1).
