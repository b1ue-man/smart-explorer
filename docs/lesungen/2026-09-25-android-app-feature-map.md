# Android feature map: desktop GUI features → non-GUI APIs, and logic trapped in `app/`

**Purpose.** For each desktop user feature, map the eframe/egui GUI module (`native/src/app/**`, excluded
from an Android build) to the non-GUI (`crate::*`, non-`app`) API it calls, and flag business logic that
currently lives *inside* `app/` and therefore has no home in an Android build unless it is extracted or
re-implemented. Also documents GUI-state persistence (files/formats) and the GUI↔daemon IPC path.

## 0. Architecture fact-check (governs every row below)

- `native/Cargo.toml:9-10` — `eframe`/`egui_extras` are **unconditional** dependencies (no `target_os` gate). `native/src/lib.rs:4` — `pub mod app;` is likewise unconditional. Nothing in the tree today excludes `app/` for any target; an Android build must add that gate itself.
- `App` (`native/src/app/core/state.rs:35`) is a single struct with **263** `pub(in crate::app)` fields — the classic egui immediate-mode "one big struct polled every frame" shape, driven by dozens of `drain_*`/`poll_*` methods called from the frame loop (`frame_update.rs`). This is not just a UI-framework dependency: the *state-machine shape itself* (thread spawn → `crossbeam_channel` → drain-on-next-frame) is repeated for essentially every async operation (scan, copy, delete, analytics, reclaim, merge, share, updates…). Porting to Android/Compose means re-hosting each of these state machines under a different scheduler (coroutines/WorkManager/ViewModel `Flow`), not just swapping the paint calls.
- **Naming is not a reliable signal.** Several `*_ui.rs`/`*_view.rs` files contain zero `egui`/`eframe` references and are pure logic (e.g. `share_lifecycle_view.rs`, `share_removal_ui.rs`, `share_discovery_state.rs`); conversely some non-`_ui` files (`omni_accel.rs`, `remote_context_menu.rs`, `treemap.rs`, `support_paths.rs`) interleave real business logic with egui painting/geometry in the same function. The egui-import column below is per-file, from `rg -l 'egui|eframe'`; it is necessary but not sufficient — see the "logic to reuse" column for what to actually extract.
- The `vfs::Backend`/`BackendHandle` trait (`crate::vfs`, 174 references from `app/`) is the one polymorphic abstraction already shared by local/SFTP/FTP/WebDAV/Google-Drive/Direct-Share backends; almost every feature below reaches storage through it, not through per-protocol app code. That part is Android-portable as-is via JNI.

## 2. Platform-adapter functions an Android `os/android.rs` would need to supply

These are called from `app/` through `os::platform_helpers` (selected in `mod.rs` via `#[cfg(windows)]`/`#[cfg(not(windows))]`, currently only Windows vs. "everything else = Linux"); an Android target would need a third arm or its own module, and would inherit the Linux stub behavior only if literally compiled with `#[cfg(not(windows))]` today (it is not — Android is a separate `target_os`, so this must be added explicitly, matching the task's architecture note that `#[cfg(target_os = "linux")]` does **not** cover Android):

| Function | Windows (`os/windows/platform.rs`) | Linux (`os/linux_os.rs`) | Android reality |
|---|---|---|---|
| `confirm_yes_no(title, msg) -> bool` | native blocking message box — `:6` | native blocking dialog — `:11` | No blocking-modal primitive in Compose; needs an async confirm (suspend fn / callback), not a straight port |
| `local_names_follow_win32_rules() -> bool` | `true` — `:278` | `false` — `:126` | `false` is already correct for Android's Linux-kernel FS (matches Linux behavior, reuse as-is) |
| `start_watcher`/`drain_watcher` (live folder-index update on FS change) | real `ReadDirectoryChangesW`-based watcher + `apply_batched_changes` — `os/windows/watchers.rs:58-222`, `os/shared/watchers.rs:7-81` (`#[cfg(windows)]`-gated batching logic) | **no-op stubs** — `os/linux_os.rs:166-168`, `should_start_watcher() -> false` — `:174` | **The Linux desktop build already has no live index watcher** — the folder index only updates via full scans today on non-Windows. Android inherits this gap unless a new `inotify`/`FileObserver`-based watcher is built; this is a pre-existing limitation, not something introduced by the port |

## 3. GUI-state persistence

All files below live under `crate::support_dirs::app_data_dir()` (`native/src/support_dirs.rs:28`, OS-specific app-data path) and are plain text, **not** `serde`/JSON, defined in `native/src/app/os/shared/platform_helpers.rs`:

| File | Format | Defined | Read by daemon/CLI too? |
|---|---|---|---|
| `recent.txt` | newline-separated path list, max 10 | `settings_path()` :121, written by `core/prefs_tabs.rs:9-24` | No — app-only |
| `favorites.txt` | newline-separated path/URL list | `favorites_path()` :137-139, r/w `core/prefs_tabs.rs:27-55`, also read+rewritten on endpoint removal by `connection_cleanup.rs:230-245` | No — app-only |
| `folder_index.txt` | `folder_index::FolderIndex` custom on-disk format (own load/save, not touched here) | `folder_index_path()` :125 | No — app-only (index is a GUI convenience) |
| `dir_sort.tsv` | `path\t0|1` per line (per-location "directories first" override) | `load_dir_sort`/`save_dir_sort` — `platform_helpers.rs:159-179` | No — app-only |
| `ui_state.txt` | custom `key=value\n` lines (`show_filters`, `show_summary`, `color_mode`, `compact`, `detailed_columns`) | `UiState::{load,save,parse,encode}` — `platform_helpers.rs:139-152`, format in `core/ui_preferences.rs:44-83` | No — app-only. Note: `ui_preferences.rs` self-describes as "Storage belongs to the OS adapter" / "Portable presentation preferences" but its `ColorMode::preference()` still returns `egui::ThemePreference` (`:2,13-19`) — strip that one method for a portable copy |
| `share_server.txt` | single trimmed line | `share_server_path()`/`load_share_server` — `support_paths.rs:48-56` | No — app-only |
| `connections.txt` | custom TSV-like (`creds::core::{parse,serialize}`), secrets **excluded** and stored via platform credential backend (Windows Credential Manager / Linux protected file) | `native/src/creds/os/shared.rs:33-160` (non-app) | **Yes** — `crate::creds` is shared; `native/src/cli/connections.rs`, `native/src/cli/doctor.rs`, `native/src/daemon/os/shared/{job.rs,job_supervisor.rs,mount_source.rs}` all reference it directly |
| Sync jobs: `jobs/<id>.conf` (+ legacy `jobs.tsv`) | key-value (`syncjobs::persistence_codec::{serialize_kv,parse_kv}`) under `support_dirs::sync_data_dir()` | `native/src/syncjobs/os/shared/persistence.rs:12-151` (non-app) | **Yes** — daemon (`job.rs`, `job_supervisor.rs`, `schedule.rs`) and `cli` both read/write it; this is the one persistence store genuinely shared between GUI, daemon and CLI |

**Implication for Android:** favourites/recents/dir-sort/ui-state/folder-index are GUI-private convenience state with a trivial custom text format — reimplementing them (as `SharedPreferences`/Room, whatever fits Compose) is low-risk and requires no protocol compatibility with the desktop files, since nothing else reads them. Saved connections and sync jobs, by contrast, are genuinely shared formats — if the Android app is meant to interoperate with a desktop daemon reading the same files (e.g. on a shared profile/sync location), those formats must be read/written exactly as `crate::creds`/`crate::syncjobs` already do (which is why those two crates should be linked in via JNI rather than reimplemented).

## 4. GUI ↔ background-daemon IPC

- Transport: **TCP loopback socket**, address + a random per-boot token discovered from files under app-data (`native/src/daemon/os/{windows,linux_os}/ipc_storage.rs`, outside the assigned read surface — confirmed only by signature/import from `native/src/daemon/os/shared/ipc_client.rs:1-10`: `TcpStream`, `read_ipc_addr`, `read_token`, `read_ipc_generation`).
- Every client call in `app/` funnels through `crate::daemon::*` (never a raw socket in `app/` itself): `is_running()` — `native/src/daemon/os/shared/state.rs:129`; `list_mounts()` — `native/src/daemon/os/shared/mount_client.rs:36`; `send_share_command(cmd)` — `native/src/daemon/os/shared/ipc_client.rs:129`; `request_daemon_replacement()` — `:201`; plus `open_share_backend`, `stop_mount`/`start_mount`/`retry_mount`, `exec_jobs`/`cancel_exec`/`mutate_exec_grant`, `pause_for_secs`/`resume`/`pause_indefinite`/`autopause_flags`/`set_cadence_secs`, `read_log_tail`, `refresh_share_worker_checked`, `drain_share_worker_events`, `probe_share_mount_capabilities` (28 distinct daemon-API symbols referenced from `app/`, none of them egui-coupled).
- **Autostart of the daemon is a separate OS process spawn**: `ensure_worker_ready()` (`ipc_client.rs:178`) calls `crate::autostart::spawn_daemon_handoff_checked(...)` (`:269`) — i.e. the GUI process launches a *second, independent* daemon executable and hands off generations to it. This has no direct Android equivalent (no arbitrary child-process spawn of a second APK's binary in the normal app sandbox); the task's suggested foreground-service/WorkManager model would need the daemon logic linked **in-process** with the GUI (same JNI library, different entry point/coroutine scope) rather than spawned as today, which changes the daemon's lifecycle/IPC story rather than porting it unchanged.

## 5. What's directly reusable vs. what needs a redesign (summary, not a verdict on the whole architecture)

- **Reusable via JNI mostly as-is** (non-`app` crates already called polymorphically): `vfs` (all backends), `scanner`/`rscan`, `copy`, `filter`, `folder_index`, `bisync`, `linemerge`, `syncjobs`, `creds`, `connect`, `zipfs`, `analytics`, `share`, `daemon` client API, `types`.
- **App-local logic with no egui coupling — extractable close to verbatim** (candidates for a new shared `core`-adjacent module, not `app`): `core/transfer_jobs.rs` (worker-pool lane), `core/job_editor_validation.rs` (job-draft validation), `core/delete_hostile_names.rs`, `core/filter_scope.rs`, `core/connection_cleanup.rs`, `core/share_discovery_state.rs`, `core/share_lifecycle_view.rs`, `core/share_profile_edits.rs`, `core/share_poll_status.rs`, `core/navigation_path.rs`.
- **App-local logic with light egui coupling — needs the type swapped but the algorithm is fine**: treemap squarify layout (`egui::Rect` → plain struct), `ui_preferences::ColorMode` (drop the `egui::ThemePreference` mapping), `omni_accel::build_omni_items` (drop `egui::Rect`/`Id` bits, keep the ranking).
- **No Android equivalent / needs a genuine redesign, not a port**: the self-replacing updater (`agent_update_remote.rs`/`crate::updater`), the watched-temp-file "open externally, save back" flow (`remote_open.rs`), blocking native confirm dialogs, mouse rubber-band selection, Dokany drive-letter mounting (`mount_ui*.rs`, `crate::mount` — already out of scope per the task brief), and the daemon's separate-process autostart model.

## Decisions made (safe, local, do not affect scope)

- Classified "does this file import egui" strictly by literal `egui`/`eframe` token presence (`rg -l`), not by transitive exposure through `use super::prelude::*` (which re-exports `eframe::egui` in every file). This matches what the task's "skip pure painting code" instruction actually needs: whether the *file's own code* touches egui types, not whether the module happens to compile against the egui crate.
- Where a feature's files number more than ~4, listed representative/most-logic-dense `file:line` citations rather than every function in every file, to keep the table readable; the "Files read" glob list above is complete for anyone who needs the rest.
- Treated `native/src/app/os/shared/*` (files selected by `#[cfg(windows)]`/`#[cfg(not(windows))]` from `mod.rs`, but themselves free of `#[cfg]`) as in-scope "app files" since they are compiled into and only used by the `app` module.

## Unresolved / out of scope for this pass

- Exact contents of `native/src/daemon/os/{windows,linux_os}/ipc_storage.rs` (token/address file format and location) were not read — outside the assigned `app/` read surface; only their signatures were inferred from the `ipc_client.rs` imports. Needed before designing the Android-side IPC or in-process daemon linkage.
- `native/src/updater/**` internals (staged-update layout, signature/hash verification) were not read, only its public symbol list as called from `app/agent_update_remote.rs`. Relevant only if any self-update concept is kept for Android; the main agent's brief suggests Play Store/APK sideload instead, which would make this moot.
- `native/src/autostart::spawn_daemon_handoff_checked` (process-spawn/generation-handoff mechanics) not read — flagged in §4 as needing a different (in-process) design for Android, but the exact handoff protocol it replaces was not inspected.
- `core/sidebar.rs`, `core/sidebar_locations.rs`, `core/landing.rs`, `core/landing_tiles.rs` (favourites-tile home screen) were confirmed egui-importing (rendering only); `core/prefs_tabs.rs` already carries the actual favourites logic these files render, so no separate logic-extraction citation was needed for them.
- Whether the daemon/CLI-shared `creds`/`syncjobs` stores are meant to be **the same files** on an Android device (e.g. via app-shared storage) or merely the same *format* for a possible future desktop↔phone profile sync was not specified in the brief and is a product decision, not a code fact.
