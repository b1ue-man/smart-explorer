### Abweichungen
- WebDAV nur über HTTPS: der Desktop verbindet WebDAV immer mit https (connect_webdav, SavedConnection hat kein http-Feld; creds liegt außerhalb meines Scopes). conn.* liefert https=true für WebDAV, ConnectionInput mit https=false wird mit kind unsupported abgelehnt. spec F12 nennt http/https – für http bräuchte es eine Formaterweiterung in creds/connect.
- Baseline-Speicherung nach Konfliktlösungen: statt die In-Memory-Baseline ganz zu überschreiben (Desktop finish_bisync_conflicts) werden nur die gelösten Einträge in die gespeicherte Baseline gemischt (load_baseline + insert + save_baseline, serialisiert). Ergebnis im Normalfall identisch, verhindert aber das Überschreiben einer neueren Baseline des eingebetteten Daemons. Für den Probelauf (dry_run liefert eine hypothetische Baseline) ist das zwingend.
- sync.run speichert offene, noch nicht gesicherte Konfliktlösungen vor dem Start automatisch (Desktop verweigert den Lauf dann nur); scheitert das, Fehler kind conflict.
- mergeApply/mergeKeepBoth prüfen vor dem Schreiben, ob sich eine Seite seit mergeRows geändert hat (Größe+mtime per stat) → kind conflict; der Desktop schreibt ohne diese Prüfung.
- Alle job-gebundenen Tasks (run, checkConflicts, resolve, mergeApply, mergeKeepBoth) laufen je Job exklusiv (zweiter Aufruf → busy); sync.delete wird während eines solchen Tasks mit busy abgelehnt.
- Share-Poller pollt zusätzlich mit 300 ms, solange ein Pairing-Befehl oder Schlüsselaustausch läuft (nicht nur bei share.watch).
- Fehler-Ereignisse des Share-Workers werden mit Runtime::record_error ins Fehlerprotokoll geschrieben (ohne error-Event), damit ein Offline-Worker keine Snackbar-Flut erzeugt; alle anderen Fehler über log_error bzw. B2s Task-Abschluss.
- Share-Server-Validierung aus cli/share.rs::validate_server nachgebaut (deutsche Texte), weil cli auf Android nicht kompiliert wird und cli/** nicht in meinem Scope liegt (Duplikat, siehe offene Punkte).
- share.setOnline(true) verlangt keinen Share-Server (api.md: leer = nur LAN); wird der Worker nicht aktiv, entsteht ein Hinweis in notices statt eines Fehlers.
- share.exec: Abbruch beendet den Task sofort, der Befehl läuft auf dem Gerät bis zu seiner Zeitgrenze weiter (exec_share ist ein blockierender At-most-once-Aufruf); die Erkennung „Gerät erlaubt keine Befehle“ ist eine Textheuristik, weil der Fehlertext des Peers nicht festgelegt ist.
- gdrive.signIn: Abbruch/180-s-Grenze beenden den Task; der Desktop-Ablauf cloud::authorize wartet auf seinem Hilfsthread bis zu seiner eigenen 300-s-Grenze weiter (cloud liegt außerhalb meines Scopes).
- Analyse schließt den App-Papierkorb laut Plan aus (sein Platz erscheint nicht in der Treemap); Reclaim zählt ihn als Kind (Elternordner nicht „leer“), bietet ihn aber nie an.
- Bei Speicheranalyse/Duplikaten remote wird das ungecachte Backend (vfs::sync_backend) gescannt, damit ein Vollscan nicht den Browse-Cache füllt; sync.mirror nutzt Runtime::resolve + sync_backend, sync.run wie am Desktop connect::resolve_endpoint.
- Ergänzende Ergebnisfelder: sync.mirror.result.summary, sync.checkConflicts.result {conflicts, errors}, resolve/merge*.result {remaining}, bg.catchUp.result {admitted, skipped, message}, analyze.start.result {files, dirs, bytes, issues}, reclaim.start.result {groups, reclaimable, errors}, gdrive.signIn.result {signedIn}; ShareStatus.rooms[].roomId (Wire-ID) zusätzlich.

### Abweichungen
- HostMonitor is a Kotlin `object` (process-wide receivers and callbacks registered once), not an instantiable class. The contract lists it among the 'Klassen'. Only K2 code uses it (start, setForeground, pushNow, measure, shareOnline).
- BackgroundSettingsSection has an optional parameter: `fun BackgroundSettingsSection(modifier: Modifier = Modifier)`. Calling `BackgroundSettingsSection()` as in the contract still works.
- Persistent mode also schedules the periodic work, as a fallback in case the system ends the service. SyncWorker returns at once while BackgroundService runs in the process, so real-time jobs do not run an extra time each period. Mode 'off' cancels the work.
- Mode 'Aus' only sets the sync flag (bg.setSyncEnabled false), cancels the work and stops the service. It does not call share.setOnline. Reason: spec F17 defines 'Aus' as 'keine geplanten Jobs', and share online is the user's own toggle on the Share page. Calling it from apply() at every app start would override that toggle.
- Helpers `TaskInfo.resultAs<T>()`, `TaskInfo.failureText()`, `Throwable.displayText()` and the private response DTOs sit inside `object SyncApi`. Reason: K1 and K3 write files in the same package `api` in parallel, and equally named top-level functions or private top-level classes (e.g. TaskRef) would fail with redeclaration or duplicate-class errors.

- SyncWorker asks for the foreground (setForeground, dataSync, try/catch) only when the catch-up run is still going after 3 s. Quick 'Keine fälligen Jobs' runs therefore post no notification. While promoted, the notification shows the task message.
- [Pausieren] in the persistent-mode notification pauses for 1 h. 'Bis morgen' in the settings pauses until the start of the next local day.
- Extra elements not named in the spec: [Jetzt nachholen] (manual bg.catchUp, which also shows the B1b skipped list), a Sync-page ⋮ with 'Ordner spiegeln' and 'Hintergrund', and 'Dateien verschieben' (Job.moveFiles, one-way jobs only) in 'Erweitert'.

### Abweichungen
- LocalFileProvider.openFile uses parseMode(if (mode == "w") "wt" else mode) instead of plain parseMode(mode). AOSP FileUtils maps "w" to O_WRONLY|O_CREAT without truncation. An editor that saves a shorter version would otherwise leave the tail of the old content in the original. androidx FileProvider also treats "w" as "wt". Documented in android-apis.md §12.2.
- Besides §4.2–§4.5, K1 also calls task.get, task.cancel and task.clear (api.md §3). They are needed to await results (awaitTask), for [Stopp], [✕], cancel on "Wird geladen…" and [Leeren]. task.cancelAll is not used: [Alle abbrechen] cancels each visible transfer individually, so scans and the catch-up run are not stopped too.
- fs.uploadEdit sends an extra `force: true` only for "Remote überschreiben" after a reported conflict (result.conflict). The contract has no way to overwrite after a conflict. Proposal: add `force:Boolean` to api.md §4.3, or a mode `overwriteForce`. Until B2 supports it, the upload ends in a conflict again (or `invalid` if unknown fields are rejected).
- The Files ⋮ menu lacks "Spiegeln nach…" (F14) and "Analysieren" (F19). sync.mirror and analyze.* are outside K1's methods, and no NavRequest can hand a place to K2 or K3. Proposal: NavRequest.MirrorFrom(location) → Sync tab (K2) and NavRequest.Analyze(location) → More (K3), added to AppNav and wired into FolderAction. As a stopgap, FilesLocation.current exposes the current place.
- "Verbindung hinzufügen", the Google Drive entry when not set up, and "Verbindungen bearbeiten" (instead of [Bearbeiten] on the error card for auth/network errors) only switch to the More tab via AppNav.send(SelectTab(More)). The contract has no request to open the connection form or the Drive setup. Proposal: NavRequest.ShowConnections(editId: String?) and ShowDriveSetup (K3).
- The all-files-access banner sits at the top of the bottom bar area, not under the title bar, so it fits both panes without clashing with the status-bar insets of the title bars.
- Rename/new name: K1 itself blocks only names the file systems never accept (empty, '/', NUL, '.', '..'). The `problem` from fs.checkName is shown as a warning and does not block; `exists` blocks ("Existiert bereits"; a case-only rename is allowed). For entries deeper in the recursive view (depth > 0) there is no live check, because the parent location is unknown and Kotlin does not build locations; fs.rename reports errors.
- Trash: entries older than 30 days are purged at Files start (the UI start) and again when the trash page opens. The worker (K2) covers the background.
- Received shares: descriptors are opened right on SEND (grant lifetime), not only after the target is chosen. Cancel or a newer share closes them.
