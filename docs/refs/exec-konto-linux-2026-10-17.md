## 1 Ziel und Fragen

Ziel (Plan A, Tabelle „Beauftragte Ergebnisse“, Zeile E2, Nutzerzitat): „i would prefer support of setting a user, a different user then se is running as when wished, for the incoming terminal connections so permissions can be handled on the actual operating system“. Betrachtet wird nur Linux. Android (E3) und Windows sind nicht Gegenstand dieser Datei.

Arbeitsdefinitionen
- **Root-Worker**: Worker-Prozess mit effektiver UID 0. **Nicht-root-Worker**: Worker-Prozess mit effektiver UID ungleich 0. Grundlage im gelesenen Code: `ESY:85-95` wählt bei euid 0 den System-Bus (`Connection::system()`), sonst den Benutzer-Bus `unix:path=/run/user/<euid>/bus`.
- **Zielkonto**: das lokale Konto, als das die Terminalverbindung laufen soll. Der se-Code löst es per `getpwnam_r` auf (`EA:28`).
- **PAM-Sitzung „ja“**: der Weg ruft mindestens `pam_open_session` auf. Die einzelnen PAM-Aufrufe (`pam_start`, `pam_authenticate`, `pam_acct_mgmt`, `pam_setcred`, `pam_close_session`) nennen die Befunde je Weg.

Fragen des Auftraggebers
1. Root-Worker: korrekte Reihenfolge `initgroups`/`setgroups`, `setgid`, `setuid`; PAM-Sitzung (`pam_start`, `pam_acct_mgmt`, `pam_open_session`, `pam_setcred`) und der Beitrag von `pam_limits`, `pam_loginuid`, `pam_systemd`, `pam_env`, `pam_keyinit`; Umgebung, Heimatverzeichnis, Kontrollterminal (`setsid`, `TIOCSCTTY`); Vorgehen von sshd (`session.c`), `su -`, `runuser`, `machinectl shell` und `systemd-run --uid --pty`; welche dieser Schritte der gelesene se-Code bereits ausführt (Beleg `Pfad:Zeile`).
2. Nicht-root-Worker: belegte Wege zu einem Zielkonto mit Einrichtungsschritten und Sicherheitsfolgen: sudo mit Drop-in-Regel (`/etc/sudoers.d`, `NOPASSWD`, Befehlsbeschränkung); polkit/`pkexec` (Regeldatei, `auth_admin_keep`); `su` mit Passwort über PTY; setuid-Hilfsprogramm; `systemd-run --uid` mit polkit-Regel (`org.freedesktop.systemd1.manage-units`); privilegierter systemd-Systemdienst als Hilfsdienst (Socket-Aktivierung, Aufruferprüfung über `SO_PEERCRED`); SSH auf localhost über sshd.
3. Einschränkung ohne zweites Konto: bubblewrap, firejail, Landlock (Kernel ab 5.13, ABI-Versionen), seccomp, unprivilegierte User-Namespaces: Was erzwingen sie (Dateisystem nur lesbar, Netzwerk) und welche Kernel- und Distributionsvoraussetzungen gelten (Ubuntu-24.04-AppArmor-Einschränkung, Debian, Fedora)?
4. Konto für Fernzugriff anlegen und entfernen: `useradd`/`userdel` (ohne Login-Passwort, Shell, Gruppen), benötigte Rechte, `systemd-homed` als Sonderfall.

## 2 Befunde je Frage

### 2.1 Frage 1: Root-Worker

#### 2.1.1 Reihenfolge der Kennungswechsel und nötige Rechte

Tatsachen aus Kernel- und libc-Dokumentation [S01]:
- `setgroups(2)`, Fehler `EPERM`: „The calling process has insufficient privilege (the caller does not have the CAP_SETGID capability in the user namespace in which it resides).“
- `setuid(2)`: „setuid() sets the effective user ID of the calling process. If the calling process is privileged (more precisely: if the process has the CAP_SETUID capability in its user namespace), the real UID and saved set-user-ID are also set.“ Weiter: „If the user is root or the program is set-user-ID-root, special care must be taken: setuid() checks the effective user ID of the caller and if it is the superuser, all process-related user ID's are set to uid. After this has occurred, it is impossible for the program to regain root privileges.“ Rückgabewert: „Note: there are cases where setuid() can fail even when the caller is UID 0; it is a grave security error to omit checking for a failure return from setuid().“
- `setresuid(2)` (und `setresgid`): ein privilegierter Prozess (CAP_SETUID bzw. CAP_SETGID) darf reale, effektive und gespeicherte Kennung auf beliebige Werte setzen; ein unprivilegierter Prozess nur auf einen der drei bisherigen Werte. Der Hinweis auf mögliche Fehlschläge auch für UID 0 steht ebenfalls dort.
- `capabilities(7)`, Abschnitt „Effect of user ID changes on capabilities“: „If one or more of the real, effective, or saved set user IDs was previously 0, and as a result of the UID changes all of these IDs have a nonzero value, then all capabilities are cleared from the permitted, effective, and ambient capability sets.“ Die Bounding-Menge nennt diese Aufzählung nicht.
- Folgerung aus den drei Aussagen: Nach einem erfolgreichen `setuid` auf eine UID ungleich 0 besitzt der Prozess weder CAP_SETUID noch CAP_SETGID; `setgroups` und `setgid` auf fremde Kennungen müssen davor stehen.
- `initgroups(3)`: „The initgroups() function initializes the group access list by reading the group database /etc/group and using all groups of which user is a member. The additional group group is also added to the list.“ Fehler `EPERM`: „The calling process has insufficient privilege. See the underlying system call setgroups(2).“
- CERT POS36-C [S21]: „the order of revocation must be correct“; das konforme Beispiel ruft `setgid` vor `setuid` auf. Abschnitt „Supplementary Group IDs“: „it is recommended that a program relinquish supplementary group IDs immediately before relinquishing root privileges“. Die Regel „POS37-C. Ensure that privilege relinquishment is successful“ steht im selben Regelverzeichnis (Seite nicht gelesen, nur der Titel).

Beitrag der fünf genannten PAM-Module:
- `pam_limits` (`pam_limits(8)`, Linux-PAM 1.7.3): „The pam_limits PAM module sets limits on the system resources that can be obtained in a user-session. Users of uid=0 are affected by this limits, too.“ Quellen der Grenzen: `/etc/security/limits.conf` und die Dateien `*.conf` in `/etc/security/limits.d/`. „The module must not be called by a multithreaded application.“ Modultyp: nur `session`. Vererbung: `getrlimit(2)` „A child process created via fork(2) inherits its parent's resource limits. Resource limits are preserved across execve(2).“ [S05][S01]
- `pam_loginuid`: „The pam_loginuid module sets the loginuid process attribute for the process that was authenticated. This is necessary for applications to be correctly audited. This PAM module should only be used for entry point applications like: login, sshd, gdm, vsftpd, crond and atd.“ und „You should not use it for applications like sudo or su as that defeats the purpose by changing the loginuid to the account they just switched to.“ Modultyp: nur `session`. Kernel-ABI zu `/proc/$pid/loginuid`: „If it is unset, permissions are not needed to set it. The accessor must have CAP_AUDIT_CONTROL in the initial user namespace to write it if it has been set. It cannot be written again if AUDIT_FEATURE_LOGINUID_IMMUTABLE is enabled.“ [S05][S13]
- `pam_systemd` (`pam_systemd(8)`, systemd 262.1): „pam_systemd registers user sessions with the systemd login manager systemd-logind.service(8), and hence the systemd control group hierarchy.“ Bei der Anmeldung: Das Laufzeitverzeichnis `/run/user/$UID` wird angelegt oder gemountet und dem Benutzer übereignet; `$XDG_SESSION_ID` wird gesetzt („If auditing is available and pam_loginuid.so was run before this module (which is highly recommended), the variable is initialized from the auditing session id (/proc/self/sessionid).“); für die Sitzung entsteht eine Scope-Einheit; bei der ersten gleichzeitigen Sitzung des Benutzers startet `user@.service`. „$XDG_RUNTIME_DIR is not set if the current user is not the original user of the session.“ Ohne systemd als Init-System: „this module does nothing and immediately returns PAM_SUCCESS“. Sitzungsklassen laut Handbuch: `user`, `user-early`, `user-light` (v258), `user-early-light` (v258), `user-incomplete`, `greeter`, `lock-screen`, `background`, `background-light` (v256), `manager`, `manager-early`, `none` (v258; „Skips registering this session with logind. No session scope will be created, and the user service manager will not be started.“). Die Klasse folgt aus dem Parameter `class=`, aus `$XDG_SESSION_CLASS` oder automatisch: `user` ist „the default class for sessions for which a TTY or X display is known“, `background` ist „the default class for sessions for which no TTY or X display is known“, `user-early` ist die Vorgabe für Sitzungen von root, die sonst `user` wären. Modultyp: nur `session`. [S06]
- `pam_env` (`pam_env(8)`): „allows the (un)setting of environment variables“; liest Regeln aus `/etc/security/pam_env.conf`, Variablen aus `/etc/environment` (und `/etc/environment.d/*`) und aus `$HOME/.pam_environment` (Optionen `user_envfile`, `user_readenv`). „This module is only executed if the main application calls pam_setcred(3) or pam_open_session(3). The module does nothing and returns PAM_IGNORE if called by pam_authenticate(3).“ „this module should be the last one on the stack“. [S05]
- `pam_keyinit`: „ensures that the invoking process has a session keyring other than the user default session keyring.“ „The session keyring of the invoking process will thenceforth be inherited by all its children unless they override it.“ „This module is intended primarily for use by login processes.“ „This module should not, generally, be invoked by programs like su, since it is usually desirable for the key set to percolate through to the alternate context.“ Optionen: `debug`, `force`, `revoke`. systemd richtet für Dienste selbst ein Sitzungs-Keyring ein (exec-invoke.c:4201-4231, Aufruf 5939). #### 2.1.4 Kontrollterminal und Pseudoterminal

Kernel- und libc-Regeln [S01][S02]:
- `TIOCSCTTY(2const)`: „The calling process must be a session leader and not have a controlling terminal already. For this case, arg should be specified as zero. If this terminal is already the controlling terminal of a different session group, then the ioctl fails with EPERM, unless the caller has the CAP_SYS_ADMIN capability and arg equals 1, in which case the terminal is stolen, and all processes that had it as controlling terminal lose it.“
- `setsid(2)`: „setsid() creates a new session if the calling process is not a process group leader.“ „Initially, the new session has no controlling terminal.“ Fehler `EPERM`: „The process group ID of any process equals the PID of the calling process. Thus, in particular, setsid() fails if the calling process is already a process group leader.“
- `grantpt(3)`: „The user ID of the slave is set to the real UID of the calling process. The group ID is set to an unspecified value (e.g., tty). The mode of the slave is set to 0620 (crw--w----).“
- `TIOCSTI(2const)`: „Since Linux 6.2, this operation may require the CAP_SYS_ADMIN capability (if the dev.tty.legacy_tiocsti sysctl variable is set to false).“ Die Kernel-Konfiguration `CONFIG_LEGACY_TIOCSTI` ist in Debian (Branch debian/latest, `debian/config/config:5055`) und in Fedora (kernel-ark os-build, `redhat/configs/fedora/generic/CONFIG_LEGACY_TIOCSTI`) mit „# CONFIG_LEGACY_TIOCSTI is not set“ eingetragen [S19][S20].
- `runuser.1`, Abschnitt SECURITY NOTES: „If runuser shares a terminal with the original session, it is potentially vulnerable to privilege escalation through TIOCSTI/TIOCLINUX ioctl command injection. There are two built-in ways to prevent this: Either you can use runuser with the -c option, which starts a new session via setsid(2) without a controlling terminal. Or, if your use case requires a controlling terminal, for example an interactive session, you can instruct runuser to use a pseudo terminal with the --pty or -P option.“ [S04]

### 2.2 Frage 2: Nicht-root-Worker

#### 2.2.0 Ausgangslage im Bestand und im Kernel

- `systemd.exec(5)`, `User=`: „For user services of any other user, switching user identity is not permitted, hence the only valid setting is the same user the user's service manager is running as.“ [S06] Der gelesene se-Code verbindet sich bei euid ungleich 0 mit dem Benutzer-Bus (`ESY:85-95`); die dort gestartete transiente Einheit gehört dem Benutzer-Dienstmanager.
- Ohne CAP_SETGID und CAP_SETUID schlagen `setgroups`, `setgid` und `setuid` auf fremde Kennungen mit `EPERM` fehl [S01]. Folgerung: Der Kennungswechsel `ESA:46-66` gelingt nur in einem Prozess mit beiden Capabilities. Der se-Code ruft `account::switch_to` unabhängig von der euid auf (`ES:327-340`); bei einem Prozess ohne CAP_SETGID scheitert `setgroups` (`ESA:47`) mit `EPERM`, und der Start endet mit `SupervisorEvent::Error` (`ES:120-126`).
- `execve(2)`: „If the set-user-ID bit is set on the program file referred to by path, then the effective user ID of the calling process is changed to that of the owner of the program file.“ Diese Umwandlung unterbleibt laut Handbuch: „The aforementioned transformations of the effective IDs are not performed (i.e., the set-user-ID and set-group-ID bits are ignored) if any of the following is true:“ mit drei Aufzählungspunkten: „the no_new_privs attribute is set for the calling thread (see prctl(2));“, „the underlying filesystem is mounted nosuid (the MS_NOSUID flag for mount(2)); or“ und „the calling process is being ptraced.“ „The capabilities of the program file (see capabilities(7)) are also ignored if any of the above are true.“ [S01] Kernel-Dokumentation `no_new_privs`: „Once the bit is set, it is inherited across fork, clone, and execve and cannot be unset.“ und „Note that no_new_privs does not prevent privilege changes that do not involve execve(). An appropriately privileged task can still call setuid(2) and receive SCM_RIGHTS datagrams.“ [S13] Ob der se-Worker oder seine Einheit `no_new_privs` setzt, ist in den gelesenen Dateien nicht bestimmbar; die Eigenschaften der transienten Einheit (`ESY:48-64`) enthalten kein `NoNewPrivileges`. `systemd.exec(5)`, `NoNewPrivileges=`: „Note that this setting only has an effect on the unit's processes themselves (or any processes directly or indirectly forked off them). It has no effect on processes potentially invoked on request of them through tools such as at(1), crontab(1), systemd-run(1), or arbitrary IPC services.“ [S06]

#### 2.2.1 sudo mit Drop-in-Regel

Quelle: sudoers(5), sudo(8) von sudo.ws (die Seiten nennen keine Versionsnummer; neuester GitHub-Tag `v1.9.17p2`, Veröffentlichung 2025-07-26) [S08].

Regelsprache
- Zugriffsregel: `Cmnd_Spec ::= Runas_Spec? Option_Spec* (Tag_Spec ':')* Cmnd`, `Runas_Spec ::= '(' Runas_List? (':' Runas_List)? ')'`. Zielkonto: „If only the first is specified, the command may be run as any user in the list and, optionally, with any group the target user belongs to.“ Ohne `Runas_Spec`: „the command may only be run as the runas_default user (root by default)“.
- Authentifizierung: „A password is not required if the invoking user is root, if the target user is the same as the invoking user, or if the policy has disabled authentication for the user or command. Unlike su(1), when sudoers requires authentication, it validates the invoking user's credentials, not the target user's (or root's) credentials.“ `NOPASSWD`: „By default, sudo requires that a user authenticate before running a command. This behavior can be modified via the NOPASSWD tag.“
- Befehlsbeschränkung: „If no command line arguments are specified, the user may run the command with any arguments they choose.“ „If a Cmnd has associated command line arguments, the arguments in the Cmnd must match those given by the user on the command line.“ Muster: Shell-Wildcards, ab Version 1.9.10 reguläre Ausdrücke (`^…$`); `""` bedeutet „no arguments“. „Wildcards can match any character, including white space.“ `ALL`: „Using ALL can be dangerous since in a command context, it allows the user to run any command on the system.“
- Drop-in-Verzeichnis: `@includedir /etc/sudoers.d` (älter `#includedir`); „skipping file names that end in ‘~’ or contain a ‘.’ character“; „Files are parsed in sorted lexical order.“ Die Hauptdatei muss die Direktive enthalten.
- Dateimodus: „The sudoers file must not be world-writable, the default file mode is 0440 (readable by owner and group, writable by none).“ (Aussage über `/etc/sudoers`; ob dieselbe Prüfung für Dateien in `sudoers.d` gilt: Lücke L-11.) `visudo -c`: „Enable check-only mode. The existing sudoers file (and any other files it includes) will be checked for syntax errors.“ `visudo -f <Datei>` prüft eine alternative Datei.

Aufruf und Sitzung
- `sudo -u <Konto>`: „Run the command as a user other than the default target user (usually root).“ `-i`: „Run the shell specified by the target user's password database entry as a login shell … sudo attempts to change to that user's home directory before running the shell. The command is run with an environment similar to the one a user would receive at log in.“ `-n`: „Avoid prompting the user for input of any kind. If a password is required for the command to run, sudo will display an error message and exit.“ `-s`: Shell aus `SHELL` oder aus dem Passwd-Eintrag des Aufrufers.
- Umgebung: „By default, the env_reset flag is enabled. This causes commands to be executed with a new, minimal environment. … The HOME, MAIL, SHELL, LOGNAME and USER environment variables are initialized based on the target user and the SUDO_* variables are set based on the invoking user.“
- PAM: `pam_session` (Standard an): „sudo will create a new PAM session for the command to be run in.“ `pam_setcred` (Standard an): „sudo will attempt to establish credentials for the target user“. `pam_service` und `pam_login_service` (bei `-i`) haben den Standardwert „sudo“. „If PAM session support is disabled, resource limits may not be updated for the command being run.“
- Terminal: `use_pty`: „If set, and sudo is running in a terminal, the command will be run in a new pseudo-terminal.“ Standard: „This flag is on by default for sudo 1.9.14 and above.“ `requiretty`: Standard „off“.

Einrichtungsschritte (Syntaxformen, nicht ausgeführt)
1. Zielkonto anlegen (Abschnitt 2.4).
2. Datei `/etc/sudoers.d/<Name>` (Name ohne „.“ und nicht auf „~“ endend) anlegen mit der Zeile `<Worker-Konto> ALL=(<Zielkonto>) NOPASSWD: ALL` oder mit einer Befehlsliste statt `ALL`.
3. Eigentümer root, Modus 0440 (Standardmodus laut Handbuch).
4. Prüfen mit `visudo -c -f /etc/sudoers.d/<Name>`.
5. Voraussetzung: `/etc/sudoers` enthält `@includedir /etc/sudoers.d` oder `#includedir /etc/sudoers.d`. Fedora 44: Zeile 120 der ausgelieferten `sudoers` lautet `#includedir /etc/sudoers.d` [S20]. Debian und Ubuntu: Inhalt der ausgelieferten `sudoers` nicht gelesen (Lücke L-11).

Sicherheitsfolgen (Tatsachen)
- Die Regel wird für die UID des aufrufenden Prozesses ausgewertet („The sudoers policy plugin determines a user's sudo privileges.“); jeder Prozess unter der UID des Worker-Kontos kann sie nutzen.
- Ein Programm mit gesetztem set-user-ID-Bit wie `sudo` erlangt keine Rechte, wenn `no_new_privs` gesetzt ist, das Dateisystem mit `nosuid` eingehängt ist oder der Prozess ge-ptrace-d wird (`execve(2)`, Abschnitt 2.2.0).
- CVE-2025-32463: „An attacker can leverage sudo's -R (--chroot) option to run arbitrary commands as root, even if they are not listed in the sudoers file. Sudo versions affected: Sudo versions 1.9.14 to 1.9.17 inclusive are affected.“ (Advisory vom 2025-06-30) [S08]
- sudo-rs ist Standard in Ubuntu 25.10 und 26.04: „sudo-rs is installed and enabled by default; you can control which sudo version is being used by running“ (danach folgt im README in einem Codeblock der Befehl `update-alternatives --config sudo`); Version 25.10 „based on v0.2.8“, 26.04 LTS „based on v0.2.13“. In Debian 13 ist `sudo-rs` Version 0.2.5 „missing sudoedit, NOEXEC:, and many other usability and compatibility improvements“ (README). FAQ: „we haven't implemented features/settings we think should be deprecated or don't actually solve a problem (such as require_tty), and have made things the out-of-the-box default if they were enabled in all common packaged versions of sudo, for example use_pty and env_reset“. [S09] Die Abdeckung der sudoers-Syntax durch sudo-rs (`@includedir`, `Runas_Spec`, `NOPASSWD`, `pam_session`) ist nicht gelesen (Lücke L-12).

Folgerung: Ein Prozess ohne logind-Sitzung wird mit `allow_any` bewertet (der Rückgabewert der Sitzungsabfrage für einzelne Prozessarten ist nicht gelesen).

#### 2.2.3 `su` mit Passwort über ein Pseudoterminal

#### 2.2.4 Eigenes set-user-ID- oder Dateifähigkeiten-Hilfsprogramm

Quellen: `execve(2)`, `capabilities(7)` [S01]; Kernel-Dokumentation `no_new_privs` [S13].

- Mechanismus: Ein Programm mit gesetztem set-user-ID-Bit setzt die effektive UID des Prozesses auf die des Dateieigentümers (`execve(2)`). Die kopierte effektive UID wird zur gespeicherten UID. Ausnahmen: `no_new_privs`, `nosuid`-Einhängung, ptrace (Abschnitt 2.2.0).
- Dateifähigkeiten (`capabilities(7)`, „File capabilities“): „Since Linux 2.6.24, the kernel supports associating capability sets with an executable file using setcap(8). The file capability sets are stored in an extended attribute (see setxattr(2) and xattr(7)) named security.capability. Writing to this extended attribute requires the CAP_SETFCAP capability.“
- `CAP_SETUID` (drei Aufzählungspunkte): „Make arbitrary manipulations of process UIDs (setuid(2), setreuid(2), setresuid(2), setfsuid(2));“, „forge UID when passing socket credentials via UNIX domain sockets;“, „write a user ID mapping in a user namespace (see user_namespaces(7)).“ `CAP_SETGID` (drei Aufzählungspunkte): „Make arbitrary manipulations of process GIDs and supplementary GID list;“, „forge GID when passing socket credentials via UNIX domain sockets;“, „write a group ID mapping in a user namespace (see user_namespaces(7)).“ `CAP_CHOWN`: „Make arbitrary changes to file UIDs and GIDs“ (für `fchown` des Terminals nötig).
- Kernel-Dokumentation `no_new_privs`: „The dynamic loader handles LD_* environment variables differently if a program is setuid.“
- Einrichtungsschritte: Binärdatei als root installieren und entweder das set-user-ID-Bit setzen oder per `setcap` die Fähigkeiten `cap_setuid` und `cap_setgid` (für `fchown` zusätzlich `cap_chown`) zuweisen. Ein Helfer, der als euid root läuft, sieht den Aufrufer über die reale UID (`getuid`). Authentifizierung des Aufrufers und Beschränkung des Zielkontos sind Sache des Helfers (kein Systemmechanismus).
- Die Datei darf nicht auf einem `nosuid`-Dateisystem liegen. Dateisysteme ohne Unterstützung für erweiterte Attribute können `security.capability` nicht speichern (Annahme: aus der Beschreibung als erweitertes Attribut abgeleitet).

#### 2.2.7 Privilegierter systemd-Systemdienst als Hilfsdienst (Socket-Aktivierung, `SO_PEERCRED`)

Quellen: systemd.socket(5), systemd.exec(5) [S06]; unix(7), socket(7) [S01]; kernelnewbies Linux 6.5 [S15].

- Socket-Unit: `ListenStream=` mit Pfad: „If the address starts with a slash (/), it is read as file system socket in the AF_UNIX socket family.“ `SocketUser=`/`SocketGroup=`: Vorgabe „the nodes are owned by the root user/group (if run in system context)“. `SocketMode=`: „Defaults to 0666.“ `DirectoryMode=`: „Defaults to 0755.“ `Accept=`: Vorgabe nein; ja = „a service instance is spawned for each incoming connection“, was „enables stronger security (since the various sandboxing options can be used to isolate parallel connections from each other, as each is serviced by a separate service instance and process)“. `PassCredentials=` (Vorgabe false) steuert `SO_PASSCRED`; `PassPIDFD=` (Vorgabe false) steuert `SO_PASSPIDFD`.
- `SO_PEERCRED` (unix(7)): „This read-only socket option returns the credentials of the peer process connected to this socket. The returned credentials are those that were in effect at the time of the call to connect(2), listen(2), or socketpair(2).“ „The use of this option is possible only for connected AF_UNIX stream sockets and for AF_UNIX stream and datagram socket pairs created using socketpair(2).“
- `SCM_CREDENTIALS` (unix(7)): „The credentials which the sender specifies are checked by the kernel. A privileged process is allowed to specify values that do not match its own.“ Der Sender muss seine eigene PID angeben (ohne CAP_SYS_ADMIN), seine reale oder effektive oder gespeicherte UID (ohne CAP_SETUID) und die entsprechenden GIDs (ohne CAP_SETGID). Kernel 6.5 (kernelnewbies): „SCM_PIDFD … contains pidfd instead of plain pid, which allows programmers not to care about PID reuse problem. SO_PEERPIDFD allows to get pidfd of peer socket holder pidfd, analogous of SO_PEERCRED which allows to get plain PID“; Konstanten `SO_PASSPIDFD` 76 und `SO_PEERPIDFD` 77 (Kernel-Header `socket.h`).
- Härtung des Dienstes (systemd.exec(5)): `CapabilityBoundingSet=`: „If this option is not used, the capability bounding set is not modified on process execution, hence no limits on the capabilities of the process are enforced.“ `NoNewPrivileges=`: Abschnitt 2.2.0 (Wirkung nur auf die Einheit selbst).
- Zusammenspiel Socket und Dienst (systemd.socket(5)): „For each socket unit, a matching service unit must exist, describing the service to start on incoming traffic on the socket.“ Bei `Accept=no` gehört zu `foo.socket` der Dienst `foo.service`; bei `Accept=yes` muss die Vorlage `foo@.service` existieren, „from which services are instantiated for each incoming connection“. „No implicit WantedBy= or RequiredBy= dependency from the socket to the service is added.“
- Einrichtungsschritte: Hilfsprogramm installieren; `/etc/systemd/system/<Name>.socket` und `<Name>.service` anlegen; die Socket-Unit aktivieren (der Befehl `systemctl enable --now <Name>.socket` ist in den gelesenen Quellen nicht belegt; Handbuch systemctl(1) nicht gelesen). Ob se bereits Unit-Dateien dieser Art ausliefert, ist nicht gelesen (Lücke L-17).
- Authentifizierung des Aufrufers: nach `SO_PEERCRED` (UID/GID/PID zum Verbindungszeitpunkt) oder, für Abfragen an polkit, nach dem Aufrufer-Subjekt; D-Bus-basierte Dienste (Richtlinie unter `/etc/dbus-1/system.d`, polkit-`CheckAuthorization`) sind in dieser Recherche nicht gelesen (Lücke L-18).

### 2.3 Frage 3: Einschränkung ohne zweites Konto

Gemeinsame Tatsache: Keiner der fünf Mechanismen ändert das Konto, unter dem der Kernel Zugriffe auf Dateien des Wirtssystems prüft; die Prozesse behalten die Rechte des Aufrufers und die Mechanismen verengen sie zusätzlich. #### 2.3.3 Landlock

Quellen: Kernel-Dokumentation `userspace-api/landlock` (Autor Mickaël Salaün, Datum „August 2026“, Seitenkopf „7.3.0-rc7“) [S13]; man-pages 6.19 `landlock(7)`, `landlock_restrict_self(2)` [S01]; Distributionsquellen [S18][S19][S20].

- Zweck: „The goal of Landlock is to enable restriction of ambient rights (e.g. global filesystem or network access) for a set of processes. Because Landlock is a stackable LSM, it makes it possible to create safe security sandboxes as new security layers in addition to the existing system-wide access-controls.“ „Landlock empowers any process, including unprivileged ones, to securely restrict themselves.“ Wirkung: „A set of rules is aggregated in a ruleset, which can then restrict the thread enforcing it, and its future children.“ (`landlock_restrict_self(2)`: „the constraints of each past and future composed rulesets will restrict the thread and its future children for their entire life“).
- Voraussetzung zum Aktivieren: „either the caller must have the CAP_SYS_ADMIN capability in its user namespace, or the thread must already have the no_new_privs bit set.“ Kernel: „Landlock was first introduced in Linux 5.13 but it must be configured at build time with CONFIG_SECURITY_LANDLOCK=y. Landlock must also be enabled at boot time like other security modules. The list of security modules enabled by default is set with CONFIG_LSM.“ Aktivierung per Kommandozeile `lsm=landlock,[...]`; Prüfung: „landlock: Up and running“ im Kernel-Log; Laufzeitprüfung `landlock_create_ruleset(NULL, 0, LANDLOCK_CREATE_RULESET_VERSION)` mit `ENOSYS` („not supported by the current kernel“) und `EOPNOTSUPP` („currently disabled“).
- ABI-Versionen (`landlock(7)`, man-pages 6.19, Tabelle VERSIONS): ABI 1 = Kernel 5.13 (Dateisystemrechte `EXECUTE`, `WRITE_FILE`, `READ_FILE`, `READ_DIR`, `REMOVE_DIR`, `REMOVE_FILE`, `MAKE_CHAR`, `MAKE_DIR`, `MAKE_REG`, `MAKE_SOCK`, `MAKE_FIFO`, `MAKE_BLOCK`, `MAKE_SYM`); ABI 2 = 5.19 (`REFER`); ABI 3 = 6.2 (`TRUNCATE`); ABI 4 = 6.7 (`NET_BIND_TCP`, `NET_CONNECT_TCP`); ABI 5 = 6.10 (`IOCTL_DEV`); ABI 6 = 6.12 (`SCOPE_ABSTRACT_UNIX_SOCKET`, `SCOPE_SIGNAL`); ABI 7 = 6.15 (Audit-Protokollflags `LOG_SAME_EXEC_OFF`, `LOG_NEW_EXEC_ON`, `LOG_SUBDOMAINS_OFF`); ABI 8 = 7.0 (`RESTRICT_SELF_TSYNC`); ABI 9 = 7.1 (`FS_RESOLVE_UNIX`). Die Kernel-Dokumentation nennt zusätzlich ABI 10 mit UDP-Regeln: „Network rules (since ABI v4 for TCP and v10 for UDP)“, `LANDLOCK_ACCESS_NET_BIND_UDP`, `LANDLOCK_ACCESS_NET_CONNECT_SEND_UDP`. landlock(7): „Users should use the Landlock ABI version rather than the kernel version to determine which features are available. … Kernels from other sources may contain backported features, and their version numbers may not match.“
- Dateisystem nur lesbar: Rechte nur mit `READ_FILE`/`READ_DIR`/`EXECUTE` vergeben, alle schreibenden Rechte als „handled“ ohne Regel; „Files or directories opened before the sandboxing are not subject to these restrictions.“
- Netzwerk: Regeln für TCP-Ports (bind/connect, ab ABI 4) und UDP-Ports (ab ABI 10); Erratum 1 betrifft die Abgrenzung von TCP zu SMC, MPTCP und SCTP. Die Dokumentation nennt Netzwerkregeln nur für TCP und UDP. Scope-Flags (ab ABI 6) isolieren abstrakte UNIX-Sockets und Signale; `FS_RESOLVE_UNIX` (ab ABI 9) betrifft Pfad-UNIX-Sockets.
- Grenzen (Kernel-Dokumentation und `landlock(7)`, CAVEATS): „It is currently not possible to restrict some file-related actions accessible through these syscall families: chdir(2), stat(2), flock(2), chmod(2), chown(2), setxattr(2), utime(2), fcntl(2), access(2).“ „Threads sandboxed with filesystem restrictions cannot modify filesystem topology, whether via mount(2) or pivot_root(2). However, chroot(2) calls are not denied.“ „There is a limit of 16 layers of stacked rulesets.“ Kernel-Dokumentation: Dateien ohne sichtbares Dateisystem (Pipe, Socket), die über `/proc/<pid>/fd/*` erreichbar sind, und „some special kernel filesystems such as nsfs“ (`/proc/<pid>/ns/*`) „cannot currently be explicitly restricted“. IOCTL: „pre-existing file descriptors like stdin, stdout and stderr are unaffected.“ „TTY devices have traditionally permitted to control other processes on the same TTY through the TIOCSTI and TIOCLINUX IOCTL commands. Both of these require CAP_SYS_ADMIN on modern Linux systems, but the behavior is configurable for TIOCSTI. On older systems, it is therefore recommended to close inherited TTY file descriptors, or to reopen them from /proc/self/fd/* without the LANDLOCK_ACCESS_FS_IOCTL_DEV right, if possible.“
- Distributionen:
  - Ubuntu: Launchpad-Fehler 1953192 „Enable Landlock by default“ (Beschreibung: „The Landlock security feature is built in Ubuntu kernel since 5.13 … The CONFIG_LSM option needs to be prepended by "landlock," to make Landlock system calls available without modifying the kernel boot arguments.“); Status „Fix Released“, 2022-01-17 (Paket `linux`); Kernel-Team-Nachricht 2021-12-22 „APPLIED[J]“ (Jammy). Konfigurationsdatei für 24.04 und 26.04 nicht lesbar (Launchpad-Git liefert HTTP 403): Lücke L-3.
  - Debian: `debian/config/config` (Branch `debian/latest`) enthält `CONFIG_SECURITY_LANDLOCK=y` (Zeile 7595) und `CONFIG_LSM="landlock,lockdown,yama,loadpin,safesetid,integrity,apparmor,selinux,smack,tomoyo,bpf,ipe"` (7526). Kernel-Versionen der Quellpakete `linux`: Debian 12 6.1.176-1, Debian 13 6.12.107-1 (sources.debian.org).
  - Fedora: kernel-ark Branch `os-build`: `redhat/configs/common/generic/CONFIG_SECURITY_LANDLOCK` = `CONFIG_SECURITY_LANDLOCK=y`; `redhat/configs/fedora/generic/CONFIG_LSM` = `CONFIG_LSM="lockdown,yama,integrity,selinux,bpf,landlock,ipe"`.
  - firejail nutzt Landlock nur über experimentelle Optionen (2.3.2).

#### 2.3.4 seccomp

Quellen: `seccomp(2)` [S01]; Kernel-Dokumentation `seccomp_filter` und `no_new_privs` [S13].

- Funktion: „Seccomp filtering provides a means for a process to specify a filter for incoming system calls. The filter is expressed as a Berkeley Packet Filter (BPF) program, as with socket filters, except that the data operated on is related to the system call being made: system call number and the system call arguments.“ „BPF programs may not dereference pointers which constrains all filters to solely evaluating the system call arguments directly.“ Folgerung: Ein Filter kann keine Pfadnamen auswerten; Pfadbeschränkungen (Dateisystem nur lesbar) sind damit nicht ausdrückbar.

#### 2.3.5 Unprivilegierte User-Namespaces

This affects all programs on the system that are unprivileged and unconfined. A default AppArmor profile is provided that allows the use of user namespaces for unprivileged and unconfined applications but will deny the subsequent use of any capabilities within the user namespace.“ Abschaltung: `echo 0 | sudo tee /proc/sys/kernel/apparmor_restrict_unprivileged_userns` (bis zum Neustart) oder `/etc/sysctl.d/60-apparmor-namespace.conf` mit `kernel.apparmor_restrict_unprivileged_userns=0` — „This is similar to the previous behaviour, but it does not mitigate against kernel exploits that abuse the unprivileged user namespaces feature.“ Maßnahmen laut Canonical-Dokumentation (Thema 58007): `kernel.apparmor_restrict_unprivileged_unconfined=1` (verhindert, dass ein unprivilegierter, unconfined Prozess per `aa-exec` ein günstigeres Profil annimmt); breite Profile (busybox, nautilus) lassen sich abschalten; „Ubuntu ships with default unconfined profiles for several applications that allow the creation of user namespaces.“ Das Profil für bwrap: Abschnitt 2.3.1. Ubuntu 22.04: Die Dateilisten des Pakets `apparmor` (jammy und jammy-updates, Version 3.0.4-2ubuntu2.5) enthalten weder `/etc/apparmor.d/unprivileged_userns` noch `/etc/apparmor.d/lxc-usernsexec`; die Dateilisten von noble und noble-updates enthalten beide Dateien, die von resolute zusätzlich `/etc/apparmor.d/bwrap-userns-restrict`. Die Funktion wurde mit 23.10 eingeführt (Blog 2023-10-09: „This feature will be first available as an opt-in in Ubuntu 23.10“); Entwurf laut Blog: „unprivileged processes will only be able to create user namespaces if they are confined and have the "userns," rule in their AppArmor profile (or if they have CAP_SYS_ADMIN)“ — abweichend vom Verhalten laut Release Notes 24.04 (Abschnitt 5).

#### 2.4.1 `useradd` und `userdel` (shadow 4.20.3)

Quelle: `man/useradd.8.xml`, `man/userdel.8.xml`, `man/usermod.8.xml`, `man/passwd.1.xml`, `man/shadow.5.xml`, `src/useradd.c` [S10]; util-linux `nologin.8` [S04]; Linux-PAM `pam_unix` [S05].

Anlegen
- „When invoked without the -D option, the useradd command creates a new user account using the values specified on the command line plus the default values from the system. Depending on command line options, the useradd command will update system files and may also create the new user's home directory and copy initial files.“ „By default, a group will also be created for the new user (see -g, -N, -U, and USERGROUPS_ENAB).“
- Passwort: `-p PASSWORD` erwartet einen verschlüsselten Wert; „Without this option, the new account will be locked and with no password defined, i.e. a single exclamation mark in the respective field of /etc/shadow. This is a state where the user won't be able to access the account or to define a password himself.“
- Systemkonto: `-r`: „Create a system account. System users will be created with no aging information in /etc/shadow, and their numeric identifiers are chosen in the SYS_UID_MIN-SYS_UID_MAX range, defined in /etc/login.defs, instead of UID_MIN-UID_MAX (and their GID counterparts for the creation of groups). Note that useradd will not create a home directory for such a user, regardless of the default setting in /etc/login.defs (CREATE_HOME). You have to specify the -m options if you want a home directory for a system account to be created.“
- Heimatverzeichnis: `-d HOME_DIR` („The directory HOME_DIR is not created by default.“; Anlegen mit `-m` oder `CREATE_HOME` in login.defs, nie mit `-M`); `-m`: „The files and directories contained in the skeleton directory (which can be defined with the -k option) will be copied to the home directory.“
- Shell: `-s SHELL`: „Without this option, the system will use the SHELL variable specified in /etc/default/useradd, or, if that is as well not set, the field for the login shell in /etc/passwd remains empty.“ Der se-Code ersetzt ein leeres oder nicht mit „/“ beginnendes Feld durch `/bin/sh` (`EA:50-52`).
- Gruppen: `-g GROUP` (Primärgruppe), `-G GROUP1[,GROUP2,…]` („The default is for the user to belong only to the initial group.“), `-N`/`--no-user-group`, `-U`/`--user-group`.
- Ablauf des Kontos: `-e EXPIRE_DATE` („Sets the date on which the user account will be disabled.“), `-f INACTIVE`.
- Rechte: `src/useradd.c` enthält keine ausdrückliche Prüfung der UID (keine Treffer für `getuid`, `geteuid`, „Permission denied“); der Schreibzugriff beginnt mit `pw_lock()` (useradd.c:1731) mit der Fehlermeldung „cannot lock %s; try again later.“ (1732). Folgerung: Ohne Schreibzugriff auf die Kontodateien schlägt `useradd` an diesen Sperren fehl. Annahme: Schreibzugriff auf `/etc/passwd`, `/etc/shadow`, `/etc/group` haben nur root-Prozesse (Dateimodi nicht gelesen).

Sperren, Ablauf, Shell, Anmeldearten
- shadow(5): „If the password field begins with an exclamation mark !, the password is locked.“
- passwd(1) `-l`: „Lock the password of the named account. This option disables a password by changing it to a value which matches no possible encrypted value (it adds a ´!´ at the beginning of the password). Note that this does not disable the account. The user may still be able to login using another authentication token (e.g. an SSH key). To disable the account, administrators should use usermod --expiredate 1 (this sets the account's expire date to 1970-01-02).“ usermod(8) `-L`: „Note: if you wish to lock the account (not only access with a password), you should also set the EXPIRE_DATE to 1.“
- `pam_unix`-Kontoprüfung: `check_shadow_expiry` (Linux-PAM 1.7.3, passverify.c:276-310) liefert `PAM_ACCT_EXPIRED`, wenn `sp_expire >= 0 && curdays >= sp_expire` (283-285), und `PAM_AUTHTOK_EXPIRED` über `sp_inact` (304-310). In `pam_unix_acct.c` gibt es keinen Vergleich mit dem Präfix „!“ (Suche nach „locked“, `'!'` und `"!"` ohne Treffer).
- sshd: Ist `UsePAM` aus, lehnt sshd Konten mit gesperrtem Passwort ab (auth.c:108-112); mit `UsePAM yes` entfällt die Prüfung (2.2.8).
- `nologin(8)`: „nologin displays a message that an account is not available and exits non-zero. It is intended as a replacement shell field to deny login access to an account.“ „The exit status returned by nologin is always 1.“ Der se-Code übernimmt eine Shell wie `/usr/sbin/nologin` ohne Prüfung (`EA:50-52`).
- Debian `adduser(8)` (3.152) [S11]: „adduser and addgroup are intended as a policy layer“; `adduser --system`: „the default home directory for a new system user is /nonexistent. This directory should never exist on any Debian system, and adduser will never create it automatically.“ „Unless a shell is explicitly set with the --shell option, the new system user will have the shell set to /usr/sbin/nologin. adduser --system does not set a password for the new account. Skeletal configuration files are not copied.“ Optionen `--disabled-login`, `--disabled-password`, `--home`, `--no-create-home`, `--shell`, `--comment`. Folgerung für den se-Code: ein Konto aus `adduser --system` mit Standardwerten hat ein nicht vorhandenes Heimatverzeichnis (`ESA:61`, `ES:333`: Rückfall auf „/“) und die Shell `/usr/sbin/nologin`.

Entfernen
- userdel(8): „userdel will not allow you to remove an account if there are running processes which belong to this account. In that case, you may have to kill those processes or lock the user's password or account and remove the account later. The -f option can force the deletion of this account. You should manually check all file systems to ensure that no files remain owned by this user.“ Rückgabewert 8: „user currently logged in“.
- `-r`: „Files in the user's home directory will be removed along with the home directory itself and the user's mail spool. Files located in other file systems will have to be searched for and deleted manually.“ `-f`: „This option forces the removal of the user account and any other requested actions, skipping any safety checks. Note: This option is dangerous and may leave your system in an inconsistent state.“
- Gruppe: „If USERGROUPS_ENAB is defined to yes in /etc/login.defs, userdel will delete the group with the same name as the user. To avoid inconsistencies in the passwd and group databases, userdel will check that this group is not used as a primary group for another user, and will just warn without deleting the group otherwise.“
- Vor- und Nachbereitung: „/etc/shadow-maint/userdel-pre.d/*, /etc/shadow-maint/userdel-post.d/* Run-part files to execute during user deletion. … If a script exits non-zero then execution will terminate.“
- Prozesse eines Kontos beenden: Handbuch `userdel` nennt „kill those processes“; Befehle zum Beenden von Prozessen eines Kontos sind in den gelesenen Quellen nicht belegt (Lücke L-20).

#### 2.4.2 `systemd-sysusers` (Deklarativ, nur Systemkonten)

Quelle: `sysusers.d(5)` systemd 262.1 [S06].
- „systemd-sysusers uses the files from sysusers.d directory to create system users and groups and to add users to groups, at package installation or boot time. This tool may be used to allocate system users and groups only, it is not useful for creating non-system (i.e. regular, "human") users and groups, as it accesses /etc/passwd and /etc/group directly, bypassing any more complex user databases, for example any database involving NIS or LDAP.“

This is recommended, since logins should typically not be allowed for system users. With or without the exclamation mark an invalid password is set. For u!, the account is also locked, which makes a difference for non-password forms of authentication, such as SSH or similar.“
- `systemd.exec(5)`, `User=`: „If DynamicUser= is not used the specified user and group must have been created statically in the user database no later than the moment the service is started, for example using the sysusers.d(5) facility, which is applied at boot or package install time.“

#### 2.4.4 `systemd-homed` als Sonderfall

Quellen: systemd 262.1 (`systemd-homed.service`, `homectl`, `pam_systemd_home`, `nss-systemd`, `pam_systemd`) [S06]; Paketlisten [S19][S18][S20].
- „systemd-homed is a system service that may be used to create, remove, change or inspect home areas (directories and network mounts and real or loopback block devices with a filesystem, optionally encrypted).“ „Each home directory managed by systemd-homed.service synthesizes a local user and group. These are made available to the system using the User/Group Record Lookup API via Varlink“.
- Namensauflösung: `nss-systemd` (`libnss_systemd.so.2`) stellt Benutzer aus dem Varlink-Dienst `systemd-homed.service` bereit: „To activate the NSS module, add systemd to the lines starting with passwd:, group:, shadow: and gshadow: in /etc/nsswitch.conf.“ Annahme: `getpwnam_r` (`EA:28`) löst bei aktiviertem NSS-Modul auch homed-Konten auf.
- Aktivierung: `homectl activate`: „If the LUKS2 mechanism is used, this generally involves: inquiring the user for a password, setting up a loopback device, validating and activating the LUKS2 volume, checking the file system, mounting the file system, and potentially changing the ownership of all included files to the correct UID/GID.“ `pam_systemd_home`: „ensures that home directories managed by systemd-homed.service(8) are automatically activated (mounted) on user login, and are deactivated (unmounted) when the last session of the user ends. For such users, it also provides authentication (when per-user disk encryption is used, the disk encryption key is derived from the authentication credential supplied at login time)“.
- Sitzungsklasse `user-incomplete` (pam_systemd(8)): „Similar to user but for sessions which are not fully set up yet, i.e. have no home directory mounted or similar. This is used by systemd-homed.service(8) to allow users to log in via ssh(1) before their home directory is mounted, delaying the mount until the user provided the unlock password.“
- Folgerung: Ein Kennungswechsel ohne PAM-Sitzung (se heute) aktiviert kein homed-Heimatverzeichnis; ob dann `pw_dir` vorhanden ist, hängt vom Aktivierungszustand ab. Der se-Code fällt bei fehlendem Verzeichnis auf „/“ zurück (`ESA:61`).
- Pakete: `systemd-homed` in Debian 12 (252.39-1~deb12u2), Debian 13 (257.13-1~deb13u1), Ubuntu 24.04 (255.4-1ubuntu8.17 in `noble-updates`; 255.4-1ubuntu8.18 im Zweig `security`) und Ubuntu 26.04 (259.5-0ubuntu3.4); nicht verfügbar in Ubuntu 22.04 (packages.ubuntu.com: „Package not available in this suite“). Fedora 44: Units `systemd-homed.service`, `systemd-homed-activate.service`, `systemd-homed-firstboot.service` in `systemd.spec` (Zeilen 1287-1289); zugehöriges Teilpaket nicht ermittelt.
- Passwortlose Aktivierung für Systemdienste: in den gelesenen Handbüchern nicht beschrieben (Lücke L-13).

## 5 Widersprüchliche oder missverständliche Angaben

1. **`pam_setcred` und Gruppen.** Linux-PAM `pam_setcred(3)`: Gruppenmitgliedschaft sei Sache der Anwendung und müsse „prior to a call to this function“ hergestellt sein („initgroups(2) (or equivalent) should have been performed“). sshd ruft `pam_setcred(PAM_ESTABLISH_CRED)` im Monitor vor dem `initgroups` des Benutzerprozesses (sshd-session.c:1269 vor session.c:1342) und danach erneut (platform.c:104-113, Kommentar: „PAM credentials may take the form of supplementary groups. These will have been wiped by the above initgroups() call. Reestablish them here.“). `login` (login.c:1610-1613): „This should be done before pam_setcred, because PAM modules might add groups during that call.“ systemd führt `initgroups_wrapper` früh aus (exec-invoke.c:905), ruft PAM, und führt danach beide Gruppenlisten zusammen (6129-6139). [S05][S03][S04][S06]
2. **Zeitpunkt von `pam_setcred` relativ zu `pam_open_session`.** ADG: „By convention, this should be the last call to the PAM library before the PAM session is opened.“ `login.c:1069-1083`: „the PAM docs recommend pam_setcred() before pam_open_session()“, „the original RFC … uses pam_setcred() after pam_open_session()“, „The best is probably to follow openssh and call pam_setcred() before and after pam_open_session().“ Umsetzung: `login` ESTABLISH davor und REINITIALIZE danach; sshd ESTABLISH davor (und nach `initgroups` erneut); `su`, `runuser`, systemd nur ESTABLISH davor. [S05][S04][S03][S06]
3. **`setgid` und Gruppenliste.** sshd: `setgid`, dann `initgroups` (session.c:1337/1342). `su`, `login`, `pkexec`, systemd: Gruppenliste vor `setgid` (su-common.c:759-783; login.c:1622-1653; pkexec.c:1077-1087; exec-invoke.c:976-983). CERT POS36-C: `setgid` vor `setuid`; Gruppenliste „immediately before relinquishing root privileges“. Alle Implementierungen setzen alle Gruppenaufrufe vor `setuid`. [S03][S04][S07][S06][S21]
4. **Kontrollterminal vor oder nach dem UID-Wechsel.** sshd und `su --pty` übernehmen es nach dem Wechsel (session.c:589 im Benutzerprozess; pty-session.c:291-293 nach su-common.c:1240); `login` und systemd davor (login.c:1236-1245 vor 1680; exec-invoke.c:351, 5332 vor 6418); se davor (`ES:318`, `ES:334`). [S03][S04][S06]
5. **Argument von `TIOCSCTTY`.** `TIOCSCTTY(2const)`: „For this case, arg should be specified as zero.“ sshd: `NULL` (sshpty.c:119); se: 0 (`EP:154-155`); util-linux: 1 (pty-session.c:293; login.c:1245); systemd: 1 nur bei `StandardInput=tty-force` (exec-invoke.c:351). [S02][S03][S04][S06]
6. **Modus des Terminals.** `grantpt(3)`: 0620. sshd: 0620 mit Gruppe `tty`, sonst 0600 (sshpty.c:169-170). se: 0620 immer (`ESA:21`). `login` und `su`: Modus aus `TTYPERM` in `login.defs` (su-common.c:263). [S01][S03][S04]
7. **„su does not create a real session (by PAM)“.** su.1 sagt dies im Zusammenhang mit systemd-Sitzungen; `su-common.c:458` ruft dennoch `pam_open_session` auf. Die Aussagen lassen sich so vereinbaren: PAM-Sitzung ja; logind-Sitzung nur, wenn der PAM-Stapel `pam_systemd` enthält. Debian 13: `su` bindet `common-session` ein (dort `pam_systemd` mit „Session-Interactive-Only: yes“), `su-l` ergänzt `pam_keyinit`, `runuser` enthält kein `pam_systemd`, `runuser-l` enthält `-session optional pam_systemd.so`. [S04][S19]
8. **`machinectl shell` und `systemd-run` (Rechte).** machinectl.1: „However, note that systemd-run might require higher privileges than machinectl shell.“ Die Standardwerte der Policy-Dateien sind für `org.freedesktop.systemd1.manage-units` und `org.freedesktop.machine1.host-shell` gleich (`allow_any` = `auth_admin`, `allow_inactive` = `auth_admin`, `allow_active` = `auth_admin_keep`). Der Unterschied liegt in den übergebenen polkit-Details (`unit`, `verb` gegenüber `machine`, `user`, `program`, `command_line`). [S06]
9. **`pam_loginuid` und sudo-ähnliche Programme.** `pam_loginuid(8)`: „You should not use it for applications like sudo or su as that defeats the purpose by changing the loginuid to the account they just switched to.“ Die PAM-Vorlage von `run0` (`systemd-run0.in`) enthält `session required pam_loginuid.so`. Die Debian-Dateien `su` und `runuser` enthalten das Modul nicht; `login` (Debian 13) und `sshd` (Fedora 44) enthalten es. [S05][S06][S19][S20]
10. **Landlock-ABI.** `landlock(7)` (man-pages 6.19, Seitenfuß 2026-07-18) endet bei ABI 9 (Kernel 7.1); die Kernel-Dokumentation (Kopf „7.3.0-rc7“, Datum „August 2026“) nennt ABI 10 (UDP-Regeln). [S01][S13]
11. **polkit-Attribut.** `NEWS.md` (polkit 124): „new systemd_unit and no_new_privileges subject attributes“; `polkit.xml`: Attribut `system_unit`. [S07]
12. **Ubuntu: Entwurf und Auslieferung der Namespace-Einschränkung.** Blog 2023-10-09: „unprivileged processes will only be able to create user namespaces if they are confined and have the "userns," rule in their AppArmor profile (or if they have CAP_SYS_ADMIN)“, zunächst nur opt-in in 23.10. Release Notes 24.04: ungeschützte unprivilegierte Programme dürfen Namespaces erzeugen, bekommen darin aber keine Fähigkeiten („will deny the subsequent use of any capabilities within the user namespace“). [S18]
13. **User-Namespaces unter Debian und Ubuntu.** README.Debian: `kernel.unprivileged_userns_clone` „The default is 1 for all modern Debian and Ubuntu kernels.“ Auf Ubuntu 24.04 schränkt zusätzlich AppArmor die Nutzung ein (Release Notes). Beides sind getrennte Mechanismen. [S19][S18]
14. **Gesperrte Konten.** `useradd -p` (fehlend): Konto „locked“, „a state where the user won't be able to access the account“. `usermod -L`/`passwd -l`: „Note that this does not disable the account. The user may still be able to login using another authentication token (e.g. an SSH key).“ sshd lehnt gesperrte Konten nur bei `UsePAM no` ab (auth.c:108-112). `sysusers.d(5)`: `u!` „locked, which makes a difference for non-password forms of authentication, such as SSH“. [S10][S03][S06]

## 7 Annahmen

- **A-1** „Root-Worker“ ist ein Worker mit euid 0, „Nicht-root-Worker“ ein Worker mit euid ungleich 0; Grundlage `ESY:85-95`.
- **A-2** Schreibzugriff auf `/etc/passwd`, `/etc/shadow`, `/etc/group` haben nur root-Prozesse (Dateimodi nicht gelesen; `useradd.c` enthält keine UID-Prüfung).
- **A-3** `getpwnam_r` (`EA:28`) löst bei aktivem NSS-Modul `systemd` (`nss-systemd`) auch Konten von `systemd-homed` auf.
- **A-4** Dateisysteme ohne Unterstützung erweiterter Attribute können `security.capability` nicht speichern.
- **A-5** Ubuntu übernimmt die Debian-Konfiguration von sshd (`UsePAM yes`) und die PAM-Dateien von util-linux unverändert.
- **A-6** Die Zweigköpfe `f43` und `f44` in src.fedoraproject.org entsprechen näherungsweise den ausgelieferten Paketversionen.
- **A-7** Die Wirkung der PAM-Dienstdatei `other` bei fehlender Dienstdatei folgt `pam.conf-syntax` (Standardregeln); ihr Inhalt je Distribution ist nicht gelesen.
- **A-8** Dass ein Prozess ohne logind-Sitzung von polkit mit `allow_any` bewertet wird, ist aus `polkitbackendinteractiveauthority.c:1304-1331` abgeleitet, nicht durch einen Lauf bestätigt.
- **A-9** Die Folgerung, eine polkit-Regel für `org.freedesktop.systemd1.manage-units` könne `User=` nicht einschränken, ist aus `dbus-manager.c:1205-1248`, `dbus-util.c:161-201` und `dbus-execute.c:37-41, 1872-1873` abgeleitet, nicht durch einen Lauf bestätigt.
