# Fernzugriff-Rechtemodelle: Faktenrecherche mit Primärquellen

Stand und Abrufdatum 2026-10-17

Erzeugt für `docs/plaene/2026-10-17-rechte-desktop-tresore/plan.md`, Abschnitt A, Ergebnisse E1 und E2. Dieses Dokument sammelt und belegt Fakten. Es enthält keine Empfehlung und keine Entscheidung; Bewertung und Auswahl trifft der Hauptagent.

## 1. Ziel und Fragen

**Ziel.** Belegen, wie zwölf Produkte bzw. Produktteile Rechte für Fern-Terminal, Fernbefehle und Fernsteuerung modellieren und welchen Bedienweg ein Mensch zur Einrichtung gehen muss. Die zwölf sind: Tailscale SSH, Tailscale PAM (Beta), Teleport, OpenSSH, RustDesk, AnyDesk, TeamViewer, MeshCentral, Chrome Remote Desktop, Cockpit, Windows Admin Center, Webmin.

**Bezug zum Auftrag (plan.md, Abschnitt A, Zitate des Nutzers):**
- E1: "I want it to be user bound not typing every individual allowed command"; "design a proper fleshed out permission system".
- E2: "i would prefer support of setting a user, a different user then se is running as when wished, for the incoming terminal connections so permissions can be handled on the actual operating system".

**Fragen (Reihenfolge und Inhalt wie im Auftrag):**
1. Tailscale SSH: ACL-/Grants-Form (`src`, `dst`, `users`, `autogroup:nonroot`, `autogroup:self`); Aktion `accept` gegenüber `check`; `checkPeriod` und Neuanmeldung; Standardrichtlinie einer neuen Tailnet-Installation; Bestimmung des Zielkontos auf dem Server; Sicht des Server-Besitzers.
2. Teleport: Rollen mit `logins` (einschließlich `{{internal.logins}}`), Node-Labels, Session-Recording, per-session MFA, Access Requests, moderierte Sitzungen; Standardrollen (`access`, `editor`, `auditor`).
3. OpenSSH: `authorized_keys`-Optionen (`restrict`, `command=`, `from=`, `no-pty`, `permitopen`, `expiry-time`), `sshd_config` (`ForceCommand`, `Match User`, `Match Group`, `ChrootDirectory`); Rechtesteuerung über das Zielkonto.
4. RustDesk, AnyDesk, TeamViewer, MeshCentral, Chrome Remote Desktop: Berechtigungsschalter je Sitzung (Tastatur/Maus, Zwischenablage, Dateiübertragung, Terminal/Kommandozeile, Neustart, Aufzeichnung, Audio); unbeaufsichtigter Zugriff (Passwort, Whitelist); Rückfrage beim Host (Annehmen/Ablehnen); Gerätegruppen und Benutzerrechte; Rollen- oder Profilvorlagen.
5. Cockpit, Windows Admin Center, Webmin: Anmeldung als OS-Konto per PAM bzw. Windows-Anmeldung; Rechteerhöhung (`sudo`, "administrative access"); was der Nutzer einrichten muss.
6. Anzahl der Handlungen, die ein Mensch in jedem dieser Produkte braucht, um einem neuen Gerät oder Nutzer Terminalzugriff mit den Rechten eines bestimmten OS-Kontos zu geben; dokumentierter Bedienweg.

### 1.1 Kennzeichnung, Methode und Grenzen

- **Kennzeichnung im Text.** "Dokumentation:" bedeutet: die Aussage steht auf einer Herstellerseite; der Seitenvermerk (Last validated, Last Modified, updated, Versionskopf) steht beim Produkt. "Quelltext:" bedeutet: die Aussage stammt aus dem öffentlichen Quelltext des Herstellers; sie belegt das Verhalten des genannten Standes und ist keine Zusicherung des Herstellers. "Annahme:" kennzeichnet eine Schlussfolgerung, die keine Quelle ausdrücklich sagt. "Lücke:" benennt genau eine Tatsache, die nicht ermittelt wurde.
- **Zitate** sind wörtlich, englisch und in Anführungszeichen. Wo eine Quelle durch die Umwandlung von HTML zu Text Leerzeichen verloren hatte, wurde der Satz nicht zitiert, sondern sinngemäß wiedergegeben.
- **Lesemethode.** Jede Seite wurde als Rohseite per HTTP geladen (Arbeitsverzeichnis des Auftrags, nicht im Repository), mit einem Python-Standardbibliothek-Skript (`html.parser`) zu Text umgewandelt, und die genannten Abschnitte wurden vollständig im Rohtext gelesen. Seiten mit Markdown-Fassung (Tailscale, Teleport, AnyDesk) wurden zusätzlich in der Markdown-Fassung gelesen. Zusammenfassungen eines Lese-Hilfsmodells (WebFetch) und Suchtreffer (WebSearch) dienten nur dem Auffinden von URLs und der ersten Orientierung und gelten nicht als Beleg.
- **Quelltext-Stände.** Rohdateien wurden von `raw.githubusercontent.com` (Zweig `main` bzw. `master`, bei Teleport zusätzlich `branch/v18`) oder `chromium.googlesource.com` (`refs/heads/main`) geladen. Die genannten HEAD-Commits stammen aus `git ls-remote` desselben Tages. Annahme: Zwischen Dateiabruf und `git ls-remote` wurde in diesen Zweigen kein Commit eingespielt.
- **Zählregel für Schritte (Frage 6).** Zähleinheit ist eine Handlung des Menschen, die die Quelle ausdrücklich nennt (nummerierter Schritt, Aufzählungspunkt, Befehl oder Klick). Installation der Produktsoftware und die erstmalige Anmeldung beim Dienst zählen nicht. Die Zahl ist die Zählung dieses Dokuments, keine Herstellerangabe; der Bedienweg steht zum Nachzählen daneben.
- **Grenze.** Kein Produkt wurde installiert oder ausgeführt. Alle Aussagen beruhen auf Lesen von Dokumentation und Quelltext, nicht auf beobachtetem Verhalten.

**B1 Regelform (Frage 1).**
- Dokumentation [TS-A]: "SSH access rules are defined in the tailnet policy file, which you can edit through the Access controls page of the admin console, or through the Tailscale API." Für eine erlaubte Verbindung braucht die Richtlinie zwei Regeln: "An allowed connection from the source to the destination." und "An allowed SSH connection from the source to the destination and the given SSH users."
- Regelvorlage wörtlich aus [TS-A]:
  ```json
  {
    "action": "check", // "accept" or "check"
    "src": [list-of-sources],
    "dst": [list-of-destinations],
    "users": [list-of-ssh-users],
    "checkPeriod": "20h", // optional, only for check actions. default 12h
    "acceptEnv": [ "GIT_EDITOR", "GIT_COMMITTER_*", "CUSTOM_VAR_V?" ] // optional, allowlists environment variables that can be forwarded from clients to the host
  },
  ```
  [TS-B] ergänzt das Feld `srcPosture` ("optional, permit access only if the list of posture conditions apply"); [TS-D] ergänzt die Felder `recorder` und `enforceRecorder`.
- `src` [TS-A]: "This can be a user, group, tag, user:*@<domain>, or autogroup." und "This cannot be a bare wildcard *."
- `dst` [TS-A]: "This can be a user, tag, or autogroup." und "Unlike ACLs, a port cannot be specified. Only port 22 is allowed, and does not need to be specified as it is used by default." [TS-B] schränkt genauer ein: "The destination can be a tag, autogroup:self (if the source contains only users or groups), or a single named user (if the source contains only the same named user)." Begründung dort: "Tailscale does not let a user start a Tailscale SSH session on a user-owned device, unless the source is a device owned by the same user."
- `autogroup:self` [TS-B]: "autogroup:self only applies to user-owned devices. It does not apply to tagged devices."
- Erlaubte Verbindungsarten [TS-B]: "From a user to their own devices (as any user, including root)."; "From a user to a tagged device (as any user, including root)."; "From a tagged device to another tagged device (for any tags). An SSH access rule from a tagged device cannot be in check mode."; "From a user to a tagged device that has been shared with them, as long as the destination host has Tailscale configured with SSH and the destination's ACL lets the user connect over SSH."
- Auswertungsreihenfolge [TS-A]: "SSH access rules are evaluated considering the most restrictive policies first:" gefolgt von "Check policies" und "Accept policies". [TS-A] im Abschnitt Limitations: Gibt es für eine Verbindung eine `check`- und eine `accept`-Regel, gilt die `check`-Regel, und der Nutzer wird nur durch deren `users` eingeschränkt.
- Server-Seite einschalten [TS-A]: Auf dem Zielgerät `tailscale set --ssh`. "This SSH initialization only needs to be done once per host." Abschalten: `tailscale set --ssh=false`.
- Plattform [TS-A]: "Tailscale SSH's server component is only available on:" Linux und "macOS open source tailscale + tailscaled CLI devices"; Mindestversion "Tailscale v1.24 or later"; "You can connect from any device running Tailscale, regardless of platform." Außerdem "Tailscale SSH assumes you use port 22 for SSH." und "Restarting the Tailscale daemon (tailscaled), for example, by performing an upgrade, will stop any existing Tailscale SSH session."

**B2 Aktion `accept` gegenüber `check`, `checkPeriod` (Frage 1).**
- [TS-A]: "accept accepts connections from users already authenticated in the tailnet." und "check requires users to periodically reauthenticate according to the checkPeriod."
- [TS-A]: "Check mode requires re-authentication on the device initiating the connection. The SSH initialization provides a URL for signing in. The sign-in attempt may also trigger any identity provider multifactor authentication (MFA) or other risk-based challenges."
- [TS-A]: "When action is check, checkPeriod specifies the time period for which to allow a connection before requiring a check. This can be specified in minutes or hours, with a minimum of one minute and a maximum of 168 hours (one week)." Standard "12 hours"; Wert "always" erzwingt die Prüfung bei jeder Verbindung ("Choosing to always require check mode may cause unexpected behavior with automation tools that open many SSH connections in a short time span, like Ansible.").
- [TS-A]: "Once re-authenticated to a destination, the user can access the device and any other device in the tailnet without re-verification for the next 12 hours." Bei abweichender Frist gilt sie nur für dieses Gerät.
- [TS-A]: "Check mode is optional and not enabled by default." Die Standardrichtlinie enthält dagegen eine `check`-Regel (B3). Annahme: Der Satz bezieht sich auf selbst geschriebene Regeln; die Quelle sagt es nicht ausdrücklich.
- Planbindung [TS-B]: Beim Feld `checkPeriod` steht "This policy is available for only on the Premium and Enterprise plans." (Wortlaut der Quelle). Siehe Abschnitt 4, Widerspruch W1.

**B3 Standardrichtlinie einer neuen Tailnet-Installation (Frage 1).**

- Wörtlicher Inhalt [TS-A]:

  "ssh": [
    {
      // any user can use Tailscale SSH to connect to their own devices
      // in check mode as a root or non-root user
      "action": "check",
      "src": ["autogroup:member"],
      "dst": ["autogroup:self"],

Die zugehörige Netzregel lautet dort `"acls": [{"action": "accept", "src": ["*"], "dst": ["*:*"]}]` (die Quelle zeigt dieselben Felder und Werte auf einzelnen Zeilen; hier in eine Zeile gesetzt).

**B4 Bestimmung des Zielkontos auf dem Server (Frage 1).**
- Dokumentation [TS-A], Feld `users`: "The set of allowed usernames on the host. Like other SSH clients, Tailscale will only use user accounts that already exist on the host, not create new accounts." Weiter: "Specify autogroup:nonroot to allow any user that is not root." und "Specify localpart:*@<domain> to allow the user on the host whose name matches the local-part of the user's login, if and only if the user's login email is in <domain>." Beispiel der Quelle: "if the login is dave+sshuser@example.com, Tailscale will map this to the SSH user dave+sshuser."
- Das Zielkonto wählt der Client beim Verbinden: [TS-A] "To use a user different from the local user, specify the user, for example, ubuntu:" mit dem Befehl `ssh ubuntu@device`. [TS-B]: "If no user is specified, Tailscale will use the local host's user. That is, if the user is logged in as alice locally, then connects with SSH to another device, Tailscale SSH will try to log in as user alice."
- [TS-B]: `localpart:*@<domain>` ist laut Quelle nur in den Plänen Premium und Enterprise verfügbar (Wortlaut: "This method is available only on the Premium and Enterprise plans."); `autogroup:nonroot` in allen Plänen.
- Quelltext [TS-Q] `tailssh.go`, Funktion `mapLocalUser`: Der vom Client angeforderte SSH-Benutzername wird in der Tabelle `SSHUsers` der passenden Regel gesucht, bei Fehlen im Eintrag `*`. Der Wert `=` bedeutet: gleicher Name wie angefordert; dann wird per `userLookup` geprüft, dass das Konto existiert, und root wird abgelehnt (Kommentar im Quelltext: "Don't match as root for autogroup:nonroot"). Passt kein Eintrag, entsteht der interne Fehler `errUserMatch`.
- Quelltext [TS-Q] `incubator.go` (Dateikopf): "Tailscaled launches the incubator as the same user as it was launched as. The incubator then registers a new session with the OS, sets its UID and groups to the specified `--uid`, `--gid` and `--groups`, and then launches the requested `--cmd`." Reihenfolge der Startwege laut Quelltext: zuerst das Programm `login` (nur wenn eine Shell mit TTY verlangt ist), dann `su -l <Konto> -c …`, zuletzt "handleSSHInProcess is a last resort if we couldn't use login or su" mit Umstellung von UID, GID und Gruppen im Prozess.

**B8 Bedienweg (Frage 6).**
- Fall A, eigene Geräte desselben Menschen, Richtlinie unverändert, Zielkonto `ubuntu` (ein Konto ohne Rootrechte, gedeckt durch `autogroup:nonroot`): 3 Handlungen: (1) auf dem Zielgerät `tailscale set --ssh`; (2) auf dem Client `ssh ubuntu@device`; (3) wegen `check` die angezeigte URL öffnen und beim Identitätsanbieter anmelden. Quelle [TS-A], Abschnitte "Advertise SSH on the host", "Connect over SSH", "Configure Tailscale SSH with check mode".
- Fall B, Richtlinie anpassen: Anleitung [TS-F] hat im Abschnitt "Configure Tailscale SSH" 5 nummerierte Schritte (Zugang zur VM; `tailscale set --ssh`; `grants`-Eintrag für Port 22; `ssh`-Eintrag mit `"users": ["root","autogroup:nonroot", "<your-local-username>"]`; lokalen Benutzernamen in `users` ergänzen) und im Abschnitt "Use Tailscale SSH" 3 nummerierte Schritte: zusammen 8.
- Fall C, Zugriff für einen zweiten Menschen auf ein Gerät: Wegen "Tailscale does not let a user start a Tailscale SSH session on a user-owned device, unless the source is a device owned by the same user." ist ein Tag-Gerät nötig. Anleitung [TS-G] hat 4 nummerierte Schritte: Tag in `tagOwners` anlegen; Zugriffsregeln (`grants` und `ssh`) schreiben; Auth-Key mit Tag erzeugen; Server mit `tailscale up --auth-key=$TS_AUTHKEY` (bei Bedarf `--advertise-tags=<tags>`) bereitstellen.
- Annahme: Fall C ist der für zwei verschiedene Menschen dokumentierte Weg; jede in [TS-A] und [TS-B] genannte Verbindungsart zwischen verschiedenen Menschen führt über ein Tag-Gerät (B1, Liste der erlaubten Verbindungsarten).

**B1 Rollen und `logins` (Frage 2).**
- [TP-A]: "A Teleport role manages access by having two lists of rules: allow rules and deny rules." Dazu: "Nothing is allowed by default.", "Deny rules get evaluated first and take priority."
- `logins` [TP-A], Kommentar im Beispiel: "The logins array defines the OS/UNIX logins a user is allowed to use. both strings and template variables are supported in this field", Beispielwert `logins: [root, '{{internal.logins}}']`.
- `{{internal.logins}}` [TP-A]: "Substituted with a value stored in Teleport's local user database and logins from a root cluster." und "For local users, Teleport will substitute this with the "allowed logins" parameter used in the tctl users add [user] <allowed logins> command." [TP-B] zeigt die Vorlage: Rolle `devs` mit `logins: ['{{internal.logins}}']`, Benutzer mit `traits: logins: ['admin']` bzw. `['ubuntu']`; "Any role becomes a template once it starts using template variables."

- Rückfrage durch die Person am Zielgerät: wählbar bei RustDesk, AnyDesk, TeamViewer und MeshCentral; fest im Hilfemodus von Chrome Remote Desktop (Dialog "Share"). Bei Teleport (Enterprise: Access Requests, moderierte Sitzungen) und Tailscale SSH (`check`) entscheidet nicht die Person am Zielgerät, sondern ein Prüfer bzw. die Neuanmeldung des Verbindenden. OpenSSH, Cockpit, Windows Admin Center und Webmin kennen keine Rückfrage.
- Bestimmung des Ziel-OS-Kontos, vier Arten: (a) Der Verbindende nennt den Kontonamen, und die Gegenstelle prüft ihn gegen eine Freigabe: Tailscale SSH (Regel-`users`), Teleport (`logins` aus Rollen), OpenSSH (Konto, in dessen Verzeichnis der Schlüssel liegt, oder Principal des Zertifikats). (b) Der Verbindende weist sich mit OS-Zugangsdaten des Kontos aus: TeamViewer Remote terminal (Windows-Zugangsdaten), RustDesk unter Windows (Administrator-Zugangsdaten, dann SYSTEM-Token; ohne Zugangsdaten das Konto des angemeldeten Konsolenbenutzers), Cockpit (Anmeldung mit lokalem Konto), Webmin ("Unix authentication"). (c) Betreiber oder Prozess legen das Konto fest: RustDesk unter Linux und macOS (Annahme: Konto des RustDesk-Prozesses), Webmin Custom Commands (Feld "Run as user"), AnyDesk und Chrome Remote Desktop (Sitzung des angemeldeten Kontos, Annahme). (d) Wahl zwischen Betriebsarten statt zwischen Konten: MeshCentral (Windows: Admin Shell, Admin Powershell, User Shell, User Powershell; Linux: `any`, `root`, `user`, `login`).
