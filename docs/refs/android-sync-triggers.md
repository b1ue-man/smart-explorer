## `registerContentObserver` und `ContentObserver`
```kotlin
// android.content.ContentResolver
final fun registerContentObserver(uri: Uri, notifyForDescendants: Boolean, observer: ContentObserver)  // API 1
final fun unregisterContentObserver(observer: ContentObserver)                                          // API 1
// android.database.ContentObserver
ContentObserver(handler: Handler?)                     // API 1; null = onChange läuft auf dem Binder-Thread
open fun onChange(selfChange: Boolean)                                           // API 1
open fun onChange(selfChange: Boolean, uri: Uri?)                                // API 16
open fun onChange(selfChange: Boolean, uri: Uri?, flags: Int)                    // API 30
open fun onChange(selfChange: Boolean, uris: Collection<Uri>, flags: Int)        // API 30
// ContentResolver.NOTIFY_*: SYNC_TO_NETWORK = 1<<0 (API 24), SKIP_NOTIFY_FOR_DESCENDANTS = 1<<1 (API 24),
//                           INSERT = 1<<2, UPDATE = 1<<3, DELETE = 1<<4 (je API 30)
```
- Standardkette (`ContentObserver.java`): `onChange(selfChange, uris, flags)` ruft je URI `onChange(selfChange, uri, flags)` → `onChange(selfChange, uri)` → `onChange(selfChange)`. Ein Override der Collection-Variante genügt; `onChange(Boolean)` allein liefert keine URI. `flags` ist 0 oder eine Kombination der `NOTIFY_*`-Bits; Javadoc: Anbieter „are strongly recommended“ sie zu senden (optional, nicht garantiert).
- `notifyForDescendants`: `false` ⇒ Meldung bei Änderung genau dieser URI **oder eines Vorfahren**; `true` ⇒ zusätzlich bei Nachfahren (ContentResolver-Javadoc). Quelltext (`ContentService.java:1917-1945`, `:1858-1905`): Meldung für URI X erreicht (a) Beobachter an Vorfahren von X nur mit `notifyForDescendants=true`, (b) Beobachter genau an X immer (außer die Meldung trägt `NOTIFY_SKIP_NOTIFY_FOR_DESCENDANTS` und der Beobachter hat `notifyForDescendants=true`), (c) Beobachter an allen Nachfahren von X unabhängig vom Flag.
- Seit API 26 (Javadoc): „all content notifications must be backed by a valid ContentProvider“. Registrierung (`ContentService.java:365-400`): `checkContentProviderAccess(authority, user)`; gibt es keinen zugänglichen Provider für die Authority, wirft ein Aufrufer mit Target ≥ 26 `SecurityException`, ältere Apps werden stillschweigend ignoriert. Sonst keine Berechtigungsprüfung für die eigene Nutzer-ID; fremde Nutzer brauchen `INTERACT_ACROSS_USERS_FULL`.
- Beobachter sind rein prozessgebunden: `ContentService` verknüpft den Binder mit `linkToDeath` und entfernt den Eintrag beim Prozesstod (`ContentService.java:1670-1720`); über 1000 Registrierungen je Beobachter nur `Slog.wtf` (`TOO_MANY_OBSERVERS_THRESHOLD`, `:107`).
- Minimal (nicht kompiliert):
```kotlin
val obs = object : ContentObserver(Handler(Looper.getMainLooper())) {
    override fun onChange(selfChange: Boolean) = onChange(selfChange, null as Uri?)
    override fun onChange(selfChange: Boolean, uris: Collection<Uri>, flags: Int) {
        val deleted = flags and ContentResolver.NOTIFY_DELETE != 0   // nur ein Hinweis, kein Beleg für den Dateistatus
    }
}
contentResolver.registerContentObserver(MediaStore.Files.getContentUri(MediaStore.VOLUME_EXTERNAL), true, obs)
// … contentResolver.unregisterContentObserver(obs)
```

## Zustellung an Hintergrund- und eingefrorene Prozesse
- `ContentService.ObserverCollector.dispatch()` (`ContentService.java:581-606`, `BACKGROUND_OBSERVER_DELAY = 10 s` `:115`): Beobachter, deren UID `procState <= PROCESS_STATE_IMPORTANT_FOREGROUND` (6) hat, bekommen sofort; **alle anderen werden 10 s verzögert** (`BackgroundThread.getHandler().postDelayed`). Ein FGS-Prozess (4) / gebundener FGS (5) zählt als sofort. `ContentResolver.NOTIFY_NO_DELAY` (`@hide`, `1 << 15`) hebt die Verzögerung für die jeweilige Meldung auf und ist Systemanbietern vorbehalten. Kommentar im Code: gegen „stampeding“ bei CPU/RAM-intensiven Vordergrundaufgaben.
- Zustellung ist ein Binder-Oneway-Aufruf (`IContentObserver.onChangeEtc`). Cached-Apps-Freezer (Android 11+, AOSP-Doku): Prozesse im Cached-Zustand werden ab Android 14 nach 10 s eingefroren; Oneway-Transaktionen an einen eingefrorenen Prozess werden in einem prozessweiten Puffer gesammelt, bei Überlauf wird der Prozess beendet; „If all processes for a particular app are frozen, the system terminates any active TCP sockets“. [A] Ein Beobachter in einer nicht-FGS-App kann bei Änderungsstürmen (Medien-Scan) den Puffer füllen; kein Beleg am Gerät [?].
- Fazit [A]: ContentObserver ist nur ein Beschleuniger für einen laufenden FGS-Prozess; nach Prozessende/Neustart immer per `generation_modified`/Scan abgleichen. Für Auslösen ohne Prozess: JobScheduler-/WorkManager-Content-Trigger (`sync-change-detection.md`).

## Was MediaProvider meldet (android16-release)
- Jede Zeilenänderung der `files`-Tabelle (Insert/Update/Delete, auch Nicht-Medien) wird je Zeile gemeldet: `acceptWithExpansion` (`MediaProvider.java:1282-1330`) → Typ-URI (`Audio.Media`/`Video.Media`/`Images.Media`/Playlist-Zeile; bei Audio zusätzlich die Sammel-URIs `Genres`/`Playlists`/`Artists`/`Albums`), **immer** `MediaStore.Files.getContentUri(volume, id)` (= `content://media/<volume>/file/<id>`), bei Downloads zusätzlich `Downloads.getContentUri`, und bei jedem Volume außer `internal`/`external` dasselbe nochmals für `external`. Flags: `NOTIFY_INSERT`/`NOTIFY_UPDATE`/`NOTIFY_DELETE` | `NOTIFY_SYNC_TO_NETWORK` (`DatabaseHelper.java:950-971`). Meldungen werden je Transaktion gesammelt, nach dem Commit im `ForegroundThread` in Paketen zu 256 URIs gesendet (`NOTIFY_BATCH_SIZE`, `DatabaseHelper.java:187,883-891,997-1004`).
  - Folge: Beobachter auf die Sammel-URI `content://media/external/file` brauchen `notifyForDescendants = true`, sonst erreichen sie die Item-URIs nicht (Vorfahren-Regel oben).
- Volume anhängen/abhängen: `notifyChange(content://media/<volume>)` und (außer `internal`) `content://media/external`, ohne Flags (`MediaProvider.java:11985-11992`, `:12054-12060`). Beobachter an Nachfahren davon (z. B. `…/external/file`) werden flag-unabhängig benachrichtigt (Regel (c)).
- Woher MediaProvider seine Zeilen bekommt: MediaStore-/ContentResolver-Schreibpfade (sofort). Der FUSE-Dämon ruft MediaProvider nur bei Lookup, Open, `create` (`InsertFile` + `OnFileCreated`, Zeile entsteht sofort, außer bei DB-Umgehung, nächster Punkt), `unlink` (`DeleteFile`), `rename` (`Rename`), `mkdir`/`rmdir`/`opendir`/`readdir` auf (`FuseDaemon.cpp`: alle `fuse->mp->…`-Aufrufe); **kein Aufruf bei `write` oder `release`** (`pf_release`, `:1877-1891`). [A] Größe/Zeit nachträglich geänderter Dateien (Schreibzugriff per Dateipfad, auch aus Rust) erfasst MediaProvider erst bei einem Scan: `IdleService` (periodisch 24 h, `setRequiresCharging(true)`, `setRequiresDeviceIdle(true)`, `IdleService.java:64-69`) → `onIdleMaintenance` scannt alle externen Volumes (`MediaProvider.java:1789-1808`, `REASON_IDLE`); Mount (`ACTION_MEDIA_MOUNTED` → `REASON_MOUNTED`, `MediaService.java:88-143`); Auftrag per `MediaStore`/`MediaScannerConnection` (`REASON_DEMAND`). Latenz am Gerät nicht gemessen [?].
- **DB-Umgehung („raw access“)**: Ein Aufrufer mit `MANAGE_EXTERNAL_STORAGE` umgeht die MediaProvider-DB, wenn sein Manifest `android:requestRawExternalStorageAccess="true"` setzt; ohne das Attribut ist der Standard `false` ab Target 31 und `true` darunter (`LocalCallingIdentity.shouldBypassDatabaseInternal`, `LocalCallingIdentity.java:515-565`, Compat `ENABLE_RAW_MANAGE_EXTERNAL_STORAGE_ACCESS` `@EnabledAfter(R)`; `MediaProvider.java:10437-10453`). Für solche Aufrufer überspringen FUSE-`create`/`unlink`/`rename` die DB (`shouldBypassDatabaseAndSetDirtyForFuse`, `:10562-10582`, Aufrufe `:11125`, `:11248`, `:3787`) und merken nur den Elternordner als nicht versteckt (`mNonHiddenPaths`) bzw. markieren ein darüberliegendes `.nomedia`-Verzeichnis als „dirty“ (`onDirectoryDirty`) ⇒ Änderungen **dieser** Apps (Dateimanager mit Raw-Zugriff, Apps mit Target ≤ 30) erzeugen weder Meldungen noch Generationen. Apps mit Standard (Target ≥ 31, Attribut nicht gesetzt) pflegen die DB über FUSE (`insertFileForFuse` bei `create`, `delete(contentUri, …)` bei `unlink`, `:11136-11148`, `:11260-11272`). [A] Ob das eigene `AndroidManifest.xml` das Attribut setzt, liegt außerhalb des Lesebereichs dieser Recherche (offener Punkt 14).
- Sichtbarkeit: `MANAGE_EXTERNAL_STORAGE` gewährt „Access to the contents of the MediaStore.Files table“ (Doku manage-all-files); ohne zeigt `MediaStore.Files` bei Scoped Storage nur Medien, die die App selbst angelegt hat (Doku shared/media, mit `READ_EXTERNAL_STORAGE` Fremdmedien). `.nomedia`, versteckte Ordner und `Android/data` in `Files` nicht geprüft [?].

## „Seit dem letzten Lauf“: `getGeneration`, `getVersion`, `generation_*`
```kotlin
// android.provider.MediaStore (static)
fun getGeneration(context: Context, volumeName: String): Long      // API 30; volumeName ∈ getExternalVolumeNames; IllegalArgumentException bei unbekanntem Volume
fun getVersion(context: Context): String                           // API 12; = getVersion(context, VOLUME_EXTERNAL_PRIMARY)
fun getVersion(context: Context, volumeName: String): String       // API 29
// MediaStore.MediaColumns (API 30, Cursor.FIELD_TYPE_INTEGER, readOnly): GENERATION_ADDED = "generation_added", GENERATION_MODIFIED = "generation_modified"
```
- Javadoc-Wortlaut („monotonically increasing“, erst `getVersion` prüfen, bei Änderung Vollabgleich) steht in `sync-change-detection.md` §MediaStore-Generationen; die Doku-Seite shared/media wiederholt: „Before you rely on the value of getGeneration(), check the media store for updates. If the media store version has changed, perform a full synchronization pass.“
- Ergänzend aus dem Quelltext: `getVersion` = `db.getVersion() + ":" + <UUID aus dem xattr user.uuid der DB-Datei>` (`MediaProvider.java:7588-7612`); neue UUID, wenn die DB gelöscht/beschädigt wurde (`DatabaseHelper.getOrCreateUuid`, `:2397-2417`); bei aktivem Flag `versionLockdown()` und Compat-Änderung `LOCKDOWN_MEDIASTORE_VERSION` (`MediaProvider.java:572,7601-7606,7618-7620`) wird statt dessen ein je UID gehashter Wert geliefert. Doku: „No other assumptions should be made about the meaning of the version“ ⇒ nur auf Gleichheit prüfen. `getGeneration` liest `SELECT generation FROM local_metadata` (`DatabaseHelper.java:185,2479`); der Zähler steigt am **Beginn jeder DB-Transaktion** (`UPDATE local_metadata SET generation=generation+1`, `:842`) und wird in die geänderten Zeilen eingetragen; Index `generation_modified_index` auf `files(generation_modified)` (`:1743`).
- Abfragerezept [A], nicht kompiliert: erst `val gen = MediaStore.getGeneration(ctx, vol)` lesen, dann `contentResolver.query(MediaStore.Files.getContentUri(vol), arrayOf(MediaStore.MediaColumns._ID, MediaStore.MediaColumns.GENERATION_MODIFIED), "generation_modified > ?", arrayOf(letzte.toString()), null)`; Baseline erst nach erfolgreicher Verarbeitung auf `gen` setzen (Leseweg ohne Transaktion sieht nur festgeschriebene Werte). Je Volume eigene Baseline und eigene `getVersion`.
- Löschungen: kein öffentlicher Tombstone (`deleted_media` ist intern; in `MediaStore.java` nicht vorhanden) ⇒ Löschungen nur per ID-Abgleich oder per `NOTIFY_DELETE` bei laufendem Prozess [A].
- Grenze: Generationen gelten nur für Zeilen, die MediaProvider kennt; siehe FUSE/Scan oben.

## Stolperfallen ContentObserver/MediaStore
1. Ein Schreibvorgang erzeugt mehrere URIs (Typ-URI, Files-URI, `external`-Spiegel); je Transaktion gebündelt, aber nicht dedupliziert über Transaktionen.
2. `onChange(Boolean)` allein genügt nicht (keine URI); `onChange(…, uris, flags)` überschreiben.
3. Kein Überlauf-/Verlustsignal (anders als RDCW/inotify-Rescan in `sync-change-detection.md`): Benachrichtigungen sind Best Effort; Abgleich per Generation/Scan ist Pflicht.
4. Dateien, die MediaProvider nicht indiziert (Schreibzugriffe ohne Scan, Apps mit DB-Umgehung/Raw-Zugriff, `Android/data`, andere Apps ohne Berechtigung), erzeugen weder Meldung noch Generation.
5. `registerContentObserver` ist an die Sichtbarkeit des Providers gebunden (`SecurityException` bei Target ≥ 26, wenn die Authority nicht zugänglich ist).

- Ein Alarm mit gleichem `Intent.filterEquals` ersetzt den alten (`set`-Javadoc). `triggerAtMillis` in der Vergangenheit ⇒ „triggered immediately“ (Javadoc); im Quelltext frühestens nach `MIN_FUTURITY` 5 s (siehe unten). - Zustellung: `PendingIntent` ist ein Broadcast; AlarmManager hält einen CPU-WakeLock („*alarm*“) nur, bis `onReceive()` zurückkehrt (Javadoc, Doku „Identify wake locks“). Danach Arbeit an WorkManager/JobScheduler/Dienst übergeben.
- `PendingIntent`-Flags: `FLAG_IMMUTABLE` angeben (`android-apis.md` §2.4).

## Berechtigungen: `SCHEDULE_EXACT_ALARM` oder `USE_EXACT_ALARM`
- Target ≥ 31: `setExact`, `setExactAndAllowWhileIdle`, `setAlarmClock` ohne Recht ⇒ `SecurityException` („Caller X needs to hold SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM to set exact alarms.“, `AlarmManagerService.java:2804`). Ausgenommen: `OnAlarmListener`-Alarme, Apps auf der Power-Allowlist (Nutzer: `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), Systemapps (`isExemptFromExactAlarmPermissionNoLock`, `:2670-2679`; Doku Android-14-Seite „Exemptions“). Target < 31: Recht nicht nötig. API-30-Geräte kennen das Recht nicht.
- `canScheduleExactAlarms()` gibt `true` bei Target < 31, bei Allowlist/Systemausnahme, bei erteiltem `SCHEDULE_EXACT_ALARM` oder erteiltem `USE_EXACT_ALARM` (`AlarmManagerService.java:2839-2853`; die Javadoc erwähnt `USE_EXACT_ALARM` nicht).
- `SCHEDULE_EXACT_ALARM`: Schutzstufe `signature|privileged|appop`, Sonderzugriff „Alarme & Erinnerungen“; ab Android 14 bei Neuinstallation mit Target ≥ 33 **standardmäßig verweigert** (Doku Android-14-Seite; Compat-Änderung `SCHEDULE_EXACT_ALARM_DENIED_BY_DEFAULT`, `@EnabledSince(TIRAMISU)`, `AlarmManager.java:301`); bestehende Apps behalten ein vorhandenes Recht beim Upgrade; nach Backup-Restore wieder verweigert. Nutzer **und** System können es entziehen; Entzug löscht die exakten Alarme (Javadoc `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED`) und beendet die App („your app stops, and all future exact alarms are canceled“, Doku Schedule alarms). Seit Target 34 hält das Recht den Standby-Bucket nicht mehr auf `WORKING_SET` oder besser (`SCHEDULE_EXACT_ALARM_DOES_NOT_ELEVATE_BUCKET`, `@EnabledSince(UPSIDE_DOWN_CAKE)`, `AlarmManager.java:312`). Weitere Gates im selben File: `REQUIRE_EXACT_ALARM_PERMISSION` und `ENFORCE_MINIMUM_WINDOW_ON_INEXACT_ALARMS` ab Target 31 (`:266`, `:281`), `ENABLE_USE_EXACT_ALARM` ab Target 33 (`:291`).
- `USE_EXACT_ALARM` (API 33, Schutzstufe `normal`, bei Installation gewährt, nicht widerrufbar): „only intended for use by apps that rely on exact alarms for their core functionality“; Halter bleiben im Bucket `WORKING_SET` oder besser; nur eines der beiden Rechte anfordern, bei Umstieg `SCHEDULE_EXACT_ALARM` mit `android:maxSdkVersion="32"` (Manifest-Doku `core/res/AndroidManifest.xml:6199-6224`). Play: nur für Wecker-/Timer-/Kalender-Apps mit Ereignisbenachrichtigung („restricted permission … subject to review“, Play-Seite); für Sideload gibt es keine Store-Prüfung, die Installation gewährt es trotzdem (`normal`) [A].
- Ablauf laut Doku Android-14-Seite: `canScheduleExactAlarms()` prüfen; sonst `Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM)` (mit `package:`-URI; Ergebnis `RESULT_OK` bei erteilt), in `onResume()` erneut prüfen, auf `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` hören (Vordergrund-Broadcast an Manifest- und Laufzeit-Empfänger, **kommt nicht** beim Entzug; Empfang erlaubt FGS-Start), nach Erteilung alle Alarme neu setzen (wie bei `BOOT_COMPLETED`), bei Verweigerung degradieren (`setWindow`/`setAndAllowWhileIdle`).

## Doze, Quoten, Mindestabstände
- Javadoc `setAndAllowWhileIdle`/`setExactAndAllowWhileIdle`: „Under normal system operation, it will not dispatch these alarms more than about every minute …; when in low-power idle modes this duration may be significantly longer, such as 15 minutes.“; beim Zustellen steht die App ca. 10 s auf der temporären Power-Ausnahmeliste (WakeLocks erlaubt); die Alarme dürfen untereinander umsortiert werden. Doku-Zahlen: Doze-Seite „once per nine minutes“ (`android-background-reachability.md` §1.5), Power-Details „While-idle alarms: Limited to 7 per hour“ (Doze aktiv), Standby-Buckets Active unbegrenzt / Working 10 / Frequent 2 / Rare 1 je Stunde / Restricted 1 je Tag.
- AOSP-Standardwerte (`AlarmManagerService.java:725-756`, DeviceConfig-überschreibbar): idle-Alarme mit `FLAG_ALLOW_WHILE_IDLE` (`setExactAndAllowWhileIdle` mit Recht) 72 je 1 h; alle übrigen idle-Alarme (`setAndAllowWhileIdle`, inexakt) `FLAG_ALLOW_WHILE_IDLE_COMPAT` 7 je 1 h (`:2764-2771`, `:2824`); Nutzer-Allowlist: alle Alarme `FLAG_ALLOW_WHILE_IDLE_UNRESTRICTED`, ohne Quote (`:2735-2742`); Standby-Quoten Active 720 (Doku: „No execution limits“), Working 10, Frequent 2, Rare 1, Never 0 je 1 h, Restricted 1 je 24 h (`:735-745`).
- Weitere Grenzen: Mindestvorlauf 5 s (`MIN_FUTURITY`, `:2202`, nicht für Systemapps), Wiederholintervall ≥ 60 s, `setWindow`: Fenster werden bei Target ≥ 31 auf `min(10 min, 75 % des Vorlaufs)` verlängert (`getMinimumAllowedWindow`, `:1342-1348`; Doku: Werte unter 600000 werden „typically clipped“), Fenster > 1 Tag auf 1 Tag, höchstens 500 gleichzeitige Alarme je UID (`IllegalStateException`, `:2238-2247`). Inexakte Alarme (`set`, `setAndAllowWhileIdle`, `setInexactRepeating`) ab Android 12 binnen 1 Stunde ab Triggerzeit, sofern kein Doze/Battery Saver (Doku Schedule alarms).
- `setWindow` hat keine „AllowWhileIdle“-Variante: im Doze „Regular alarms: Deferred to doze maintenance window“ (Power-Details). `setImplLocked` verwirft den Alarm still, wenn `isAppStartModeDisabled` (Log „package not allowed to start“, `:2265-2268`); wann der Modus `DISABLED` ist, nicht ausgewertet [?].

## FGS-Start aus einem Alarm
- Exakt (`setExactAndAllowWhileIdle`): Doku „allowed to start a foreground service even if the app is in the background“; Alarm-Doku: „exact alarms aren't affected by foreground service launch restrictions“. Quelltext: temporäre Allowlist 10 s vom Typ `FOREGROUND_SERVICE_ALLOWED` (`mOptsWithFgs`, `:881-883`).
- Inexakt-idle (`setAndAllowWhileIdle`): Typ `FOREGROUND_SERVICE_NOT_ALLOWED`, Grund `REASON_DENIED` (`mOptsWithoutFgs`, `:888-889`) ⇒ der Empfänger darf **keinen** FGS starten (außer andere Ausnahme, `android-background-reachability.md` §3). Dort stattdessen Expedited-Work oder `OneTimeWorkRequest` einreihen; Alarm-Doku: „To perform longer work, schedule it using WorkManager or JobScheduler from your alarm's BroadcastReceiver. To perform work while the device is in Doze, create an inexact alarm using setAndAllowWhileIdle(), and start a job from the alarm.“

## Lebensdauer (Neustart, Update, Force-Stop)
- Neustart: „By default, all alarms are canceled when a device shuts down“ (Doku); `BOOT_COMPLETED` erreicht die App nur, wenn der Nutzer sie mindestens einmal gestartet hat (Doku, `android-background-reachability.md` §4); FGS-Typ-Grenzen aus `BOOT_COMPLETED` ebd. §3.
- Update: `ACTION_PACKAGE_REMOVED` mit `EXTRA_REPLACING` ⇒ „This package is being updated; don't kill its alarms.“ (`AlarmManagerService.java:4998-5005`); bei `ACTION_PACKAGE_ADDED` mit `EXTRA_REPLACING` werden exakte Alarme entfernt, wenn die App das Recht verloren hat (`CHECK_EXACT_ALARM_PERMISSION_ON_UPDATE`, `:4984-4993`). Alarme überleben also das Selbst-Update; `MY_PACKAGE_REPLACED` nur, wenn die App vorher gestartet war (`android-background-reachability.md` §4).
- Force-Stop (`ACTION_PACKAGE_RESTARTED`), Deinstallation (`ACTION_PACKAGE_REMOVED` ohne `EXTRA_REPLACING`) und Auswerfen der SD-Karte, auf der die App liegt (`ACTION_EXTERNAL_APPLICATIONS_UNAVAILABLE`): Alarme gelöscht (`removeLocked(uid, …)`/`removeLocked(pkg, …)`, `AlarmManagerService.java:5007-5030`); Daten löschen: `removeAlarmsForUid`/`REMOVE_REASON_DATA_CLEARED` (`:2580-2583`); `ACTION_USER_STOPPED`: Alarme des Nutzers gelöscht (`:4961-4968`). Task-Manager-Stopp (Android 13+): Alarme bleiben (`android-background-reachability.md` §3).

## Alarm oder WorkManager `setInitialDelay`?
- Genauigkeit: `setExact*` „as nearly as possible“; `setInitialDelay` ist ein Mindestwert (Doku: „The exact time … also depends on the constraints … and on system optimizations“; `WorkInfo.nextScheduleTimeMillis`-KDoc: „Work will almost never run at this time in the real world“). Umsetzung: `JobInfo.setMinimumLatency(offset)` plus Constraints (`SystemJobInfoConverter.java:100-113`), zusätzlich im lebenden Prozess ein `Handler.postDelayed` des GreedyScheduler (`DelayedWorkTracker`, `DefaultRunnableScheduler`: Haupt-Looper, Uptime-Uhr, weckt nicht).
- Doze: Alarme `…AllowWhileIdle` feuern mit Quote; reguläre Jobs/WorkManager werden bis zum Wartungsfenster verschoben („Doesn't let JobScheduler run“, Doze-Doku; Ausnahme Nutzer-Allowlist: `android-background-reachability.md` §1.4); Expedited- und UIDT-Jobs dürfen im Doze laufen (`JobStatus.canRunInDoze`, JobScheduler-Abschnitt).
- Berechtigung: exakt braucht Recht/Allowlist; WorkManager nichts.
- Neustart: Alarme weg; WorkManager plant neu: `SystemJobInfoConverter.java:125-127` setzt `setPersisted(false)` mit Kommentar „we reschedule these jobs on BOOT_COMPLETED“; `UnfinishedWorkListener` aktiviert den Manifest-`RescheduleReceiver` (`BOOT_COMPLETED`) nur, solange unfertige Arbeit existiert; Initialisierung per `androidx.startup`.
- FGS-Start: aus exaktem Alarm ja; aus einem Worker nur über eine andere Ausnahme: `PowerExemptionManager` (`REASON_*`, android16-release) führt keinen Job-/WorkManager-Grund, und `ListenableWorker.setForegroundAsync` schlägt bei FGS-Beschränkung mit `IllegalStateException` fehl (WorkManager-Abschnitt) [A].
- Doku „Data transfer background task options“ (`https://developer.android.com/about/versions/15/changes/datasync-migration`): WorkManager `setExpedited` ist „especially useful if you're scheduling the work in response to a broadcast, exact-alarm, or high-priority FCM message“ ⇒ Muster Alarm → Receiver → Expedited-Work.

```kotlin

val pi = PendingIntent.getBroadcast(ctx, 1, Intent(ctx, SyncAlarmReceiver::class.java),
    PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT)
val at = SystemClock.elapsedRealtime() + delayMs
if (Build.VERSION.SDK_INT < Build.VERSION_CODES.S || am.canScheduleExactAlarms())
    am.setExactAndAllowWhileIdle(AlarmManager.ELAPSED_REALTIME_WAKEUP, at, pi)
else
    am.setAndAllowWhileIdle(AlarmManager.ELAPSED_REALTIME_WAKEUP, at, pi)
```
1. Nach jedem Neustart, jedem erteilten Recht und beim Start der App neu setzen (kein Alarm überlebt den Neustart).
2. `ELAPSED_REALTIME*` für „in N Minuten“ (Doku: nicht von Zeitzone/Uhr abhängig); `RTC*` nur für Uhrzeiten.
3. Inexakte Idle-Alarme starten keinen FGS; der Receiver muss kurz bleiben (Wakelock nur bis `onReceive` Ende).
4. Alarm-Sturm: Jitter bei Netzwerkarbeit (Doku Schedule alarms „Add randomness (jitter)“).

## Wo ein Worker läuft
- **GreedyScheduler** (`impl/background/greedy/GreedyScheduler.java`): „schedules unconstrained, non-timed work. It intentionally does not acquire any WakeLocks, instead trying to brute-force them as time allows before the process gets killed“ (`:62-64`). Startet Arbeit **im lebenden Prozess**, sobald Constraints erfüllt sind (eigene Constraint-Beobachtung; nicht bei Device-Idle- oder Content-URI-Constraints, `GreedyScheduler.java:164-171`); verspätete Arbeit per `Handler.postDelayed` (Haupt-Looper). Zeitlimit hier `TimeLimiter` 90 min ⇒ `STOP_REASON_TIMEOUT` (`TimeLimiter.kt:30`). Ab dem 6. Wiederholungsversuch im selben Prozess +30 s je Versuch (`NON_THROTTLE_RUN_ATTEMPT_COUNT = 5`, `:76`).
- **JobScheduler** (`SystemJobScheduler`/`SystemJobService`): Rückfall und einziger Weg ohne lebenden Prozess; startet der Job, obwohl der GreedyScheduler denselben Worker schon ausführt, ist `startWork()` ein No-op (Kommentar `SystemJobService.java:170-176`). Alle WorkManager-Jobs sind `setPersisted(false)` (`SystemJobInfoConverter.java:127`). Doku: „WorkManager uses JobScheduler to schedule tasks when the app is not visible“ (Power-Details). Limits siehe Abschnitt JobScheduler.
- `startWork()` läuft auf dem Haupt-Thread, `CoroutineWorker` standardmäßig auf `Dispatchers.Default` (`CoroutineWorker.kt`), `Worker.doWork()` auf dem WorkManager-Executor (`Worker.kt:64`).

## `Result.retry()`, Backoff, Fehler
```kotlin
// androidx.work.ListenableWorker.Result
Result.success() / Result.success(outputData: Data) / Result.retry() / Result.failure() / Result.failure(outputData: Data)
// androidx.work.ListenableWorker:  final fun getRunAttemptCount(): Int     // bei periodischer Arbeit je Periode zurückgesetzt
```
- `retry()` ⇒ Zustand `ENQUEUED`, `lastEnqueueTime = jetzt`, `stopReason = STOP_REASON_NOT_STOPPED` (`WorkerWrapper.kt:461-463`, `reschedule`). Nächster Lauf frühestens `lastEnqueueTime + min(delay, 5 h)`; `LINEAR`: `backoffDelay × runAttemptCount`, `EXPONENTIAL`: `backoffDelay × 2^(runAttemptCount−1)` (`WorkSpec.kt:431-436`). Doku: Backoff-Verzögerung nie unter 10 s, „inexact … could vary by several seconds“, Standard `EXPONENTIAL` mit 30 s (Beispiel `LINEAR` 10 s ⇒ 10, 20, 30, 40 s). Periodische Arbeit backt bei `retry()` ebenfalls (`PeriodicWorkRequest`-KDoc).
- `runAttemptCount` steigt bei **jedem Start** (`trySetRunning`, `WorkerWrapper.kt`), auch nach Stopps durch das System. `isBackedOff` = `ENQUEUED && runAttemptCount > 0` (`WorkSpec.kt:195`): ein vom System gestoppter Worker bekommt ohne `setBackoffForSystemInterruptions()` kein neues `lastEnqueueTime` (Kommentar „We want to preserve time when work was enqueued“, `resetWorkerStatus`, `:423-445`); die Sperrzeit läuft ab dem ursprünglichen Einreihen und liegt bei kurzen Läufen meist in der Vergangenheit [A]. Mit der experimentellen Methode wird wie bei `retry()` ab jetzt gerechnet.
- Eine aus `doWork()` geworfene Ausnahme (nicht `CancellationException`) ⇒ `Resolution.Failed` ⇒ `FAILED` für Einmalarbeit (kein Retry!), bei periodischer Arbeit nächste Periode (`WorkerWrapper.kt:385`, `onWorkFailed` `:408-416`); eine vom Worker selbst ausgelöste `CancellationException` zählt ebenfalls als Fehlschlag (`:108-112`). Für Netz-/Server-Fehler daher selbst fangen und `Result.retry()` geben. `Result.failure()` bricht bei Einmalarbeit abhängige Ketten ab.
- JobScheduler-Backoff gilt nicht im Doze: „A job running while the device is dozing will not be rescheduled with the normal back-off policy“, sondern im nächsten Wartungsfenster (`JobService.jobFinished`-Javadoc).

## Stopp eines Workers: Gründe und Mechanik
```kotlin
// androidx.work.ListenableWorker
final fun isStopped(): Boolean
@RequiresApi(31) final fun getStopReason(): Int            // WorkInfo.STOP_REASON_*; STOP_REASON_NOT_STOPPED solange nicht gestoppt
open fun onStopped()                                       // CoroutineWorker: final, nicht überschreibbar
// WorkInfo.stopReason: Int  (@RequiresApi(31), nach dem Lauf lesbar; nur gültig bei state == ENQUEUED && runAttemptCount > 0)
```
- Gründe (Doku manage-work): ausdrücklich abgebrochen (`cancelWorkById`/`cancelUniqueWork`); `ExistingWorkPolicy.REPLACE` (alter Auftrag sofort „cancelled“); Constraints nicht mehr erfüllt; Systemvorgabe (z. B. Ausführungsfrist von 10 Minuten überschritten). Doku: „You should cooperatively abort any work …“; „WorkManager ignores the Result set by a Worker that has received the onStop signal“; „In the event that a constraint becomes unmet while your work is running, WorkManager will stop your worker. The work will then be retried when all the constraints are met.“
- `WorkInfo.STOP_REASON_*` (`WorkInfo.kt:245-349`): `FOREGROUND_SERVICE_TIMEOUT = -128`, `NOT_STOPPED = -256`, `UNKNOWN = -512`; gespiegelt aus `JobParameters.STOP_REASON_*`: `CANCELLED_BY_APP 1`, `PREEMPT 2`, `TIMEOUT 3`, `DEVICE_STATE 4`, `CONSTRAINT_BATTERY_NOT_LOW 5`, `CONSTRAINT_CHARGING 6`, `CONSTRAINT_CONNECTIVITY 7`, `CONSTRAINT_DEVICE_IDLE 8`, `CONSTRAINT_STORAGE_NOT_LOW 9`, `QUOTA 10`, `BACKGROUND_RESTRICTION 11`, `APP_STANDBY 12`, `USER 13`, `SYSTEM_PROCESSING 14`, `ESTIMATED_APP_LAUNCH_TIME_CHANGED 15`. `getStopReason()` ist `@RequiresApi(31)` (unter minSdk 30 mit Wächter aufrufen); `SystemJobService.onStopJob` setzt auf API ≤ 30 `STOP_REASON_UNKNOWN` (`SystemJobService.java:181-206`).
- Mechanik (`WorkerWrapper.kt`): Stopp ⇒ `interrupt(reason)` ⇒ `workerJob.cancel(WorkerStoppedException)`; `awaitWithin` ruft `worker.stop(reason)` (setzt den Grund, ruft `onStopped()`) und dann `future.cancel(false)` (`:650-668`); die Auflösung `Stopped` wird **sofort** verarbeitet (Zustand wieder `ENQUEUED`, `stopReason` gespeichert, neu planen, `resetWorkerStatus`), ohne auf das Ende des Worker-Codes zu warten.
  - `CoroutineWorker`: Das Future-Abbruch-Callback ruft `job.cancel()` des Worker-Coroutine-Kontexts (`ListenableFuture.kt:39`); `doWork()` bricht kooperativ an Suspendierungspunkten ab (kotlinx.coroutines 1.11.0: „coroutines only react to cancellation when they cooperate by suspending or checking for cancellation explicitly“).
  - `Worker` (blocking): `doWork()` läuft auf einem Executor-Thread; der Abbruch setzt nur ein Flag, das vor dem Start geprüft wird (`Worker.kt:94-100`); **kein** `Thread.interrupt()`. Der Code muss `isStopped()` pollen bzw. in `onStopped()` (leichtgewichtig, beliebiger Thread) signalisieren (Javadoc).
- Nach einem Stopp entsteht beim nächsten Lauf ein **neues Worker-Objekt**; das alte wird nicht wiederverwendet (`Worker`-KDoc). Es gibt kein Warten auf das Ende des alten Codes [A]: läuft der Alt-Code (z. B. native Arbeit) weiter, kann eine neue Instanz parallel starten.

## Laufzeitmodell regulärer Jobs (und damit WorkManager-Worker)
- Doku (Power-Details): Quoten je Standby-Bucket für reguläre Jobs: Active bis 20 min je rollierende 60 min (neu ab Android 16, vorher unbegrenzt), Working Set 10 min je 4 h, Frequent 10 min je 12 h, Rare 10 min je 24 h, Restricted einmal täglich bis 10 min; Expedited: Active 30 min / 24 h, Working Set 15, Frequent 10, Rare 10, Restricted 5; Netzzugriff nach Bucket (Spalte „Network“): Active/Working Set/Frequent „No restrictions“, Rare/Restricted „Disabled“ ([A]: für Apps ohne Vordergrund-/FGS-Zustand; Tabelle „app state“: FGS-Prozess „No restrictions“); Ladegerät: „No execution limits except for restricted standby bucket“. App sichtbar: keine Grenze; App mit FGS: Grenzen nach Bucket (ab Android 16; „Prior to Android 16 there was no execution limit when the app was running a foreground service“); Nutzer „unrestricted“: großzügig. Werte „not a guarantee“.
- Android-16-Seite: Quoten gelten auch für Jobs, die im Top-Zustand starten und danach im Hintergrund weiterlaufen, und für Jobs, die gleichzeitig mit einem FGS laufen; betrifft WorkManager, JobScheduler, DownloadManager. Test: `adb shell am compat enable OVERRIDE_QUOTA_ENFORCEMENT_TO_TOP_STARTED_JOBS|OVERRIDE_QUOTA_ENFORCEMENT_TO_FGS_JOBS <pkg>`, Bucket mit `adb shell am set-standby-bucket <pkg> active|working_set|frequent|rare|restricted`. `JobScheduler.getPendingJobReasonsHistory` neu in 16.
- AOSP-Standardwerte (`JobSchedulerService.java:790-804`, `getMinJobExecutionGuaranteeMs` `:4192-4236`, `getMaxJobExecutionTimeMs` `:4239-4268`): reguläre Jobs 10 min garantiert (`RUNTIME_MIN_GUARANTEE_MS`); danach nur Abbruch, wenn `shouldStopRunningJobLocked` einen Grund nennt (dann `STOP_REASON_DEVICE_STATE`), sonst läuft der Job weiter bis zur Obergrenze `min(30 min (RUNTIME_FREE_QUOTA_MAX_LIMIT_MS, 10 min bei wiederholten Timeouts), verbleibende Bucket-Quote)` ⇒ `STOP_REASON_TIMEOUT` (`JobServiceContext.java:1448-1500`). Expedited: 3 min garantiert, Obergrenze 10 min. Damit passt die Doku-Angabe „10 Minuten“ zur Garantie; die tatsächliche Grenze hängt von Quote und Druck ab.
- Doze/Battery Saver: Ein Job läuft im Doze nur, wenn `JobStatus.canRunInDoze()` (`JobStatus.java:1849-1856`) gilt: App auf der Doze-Allowlist, `FLAG_WILL_BE_FOREGROUND`, **UIDT** oder **Expedited** (außer ein dynamischer Constraint verlangt „nicht dozing“); Battery Saver analog (`canRunInBatterySaver`, `:1858-1863`). Reguläre Jobs nur über die Allowlist: die Sonderregel für `FLAG_IMPORTANT_WHILE_FOREGROUND` (App im Vordergrund oder temporär auf der Allowlist, z. B. nach einem `setAndAllowWhileIdle`-Alarm) gilt nur, solange das Flag `ignore_important_while_foreground` aus ist (`DeviceIdleJobsController.java:222-229`; Flags in `job.aconfig`); in Android 16 ist die Methode laut Doku wirkungslos ⇒ [A] ein regulärer WorkManager-Job aus einem Idle-Alarm läuft im Doze nicht, ein Expedited-Job oder UIDT schon (Doku Define-work: „Power management restrictions, such as Battery Saver and Doze, are less likely to affect expedited work“).
- Wakelock: Während `onStartJob` bis `jobFinished`/`onStopJob` hält das System einen WakeLock für die App („acquired before this method is invoked“; „Once this method returns (or times out), the system releases the wakelock“, `JobService`-Javadoc). `*job*`-WakeLock-Namen: Android ≤ 15 `*job*[u]/@<ns>@/<pkg>/<class>`, ab 16 QPR2 `*job*{r|e|u}/@<ns>@/#<trace_tag>#/<pkg>/<class>`; WorkManager: `*job*/<pkg>/androidx.work.impl.background.systemjob.SystemJobService` (Doku Identify wake locks).
- `JobService.onStartJob` läuft auf dem Haupt-Thread; `onStopJob`-Javadoc: „You are solely responsible for the behavior of your application upon receipt of this message; your app will likely start to misbehave if you ignore it.“; Beispiel dort: WLAN-Constraint, Nutzer schaltet WLAN ab. Rückgabe `true` ⇒ Neuplanung mit Backoff; die Deadline-Bedingung entfällt für den Neulauf. `JobScheduler.schedule(job)` ersetzt einen gleichnamigen Job und **stoppt einen laufenden mit derselben ID** (Javadoc); „the system may throttle calls to this API“.
- Android 16: `JobInfo.Builder.setImportantWhileForeground` wirkt nicht mehr (WorkManager setzt es standardmäßig weiter für nicht-expedited, sofortige Arbeit: `markJobsAsImportantWhileForeground = true`, `Configuration.kt:293`, `SystemJobInfoConverter.java:108-113`; die Wirkung entfällt); neuer Stoppgrund `STOP_REASON_TIMEOUT_ABANDONED = 16` (`@FlaggedApi handle_abandoned_jobs`) für Jobs, deren `JobParameters` vom GC eingesammelt wurden, bevor `jobFinished` kam ⇒ `JobParameters` stark referenzieren.

# `PowerManager.WakeLock` (API 30–36): lange Läufe wach halten

- Stufe `PARTIAL_WAKE_LOCK`: „Ensures that the CPU is running; the screen and keyboard backlight will be allowed to go off.“ Doku set-wakelock: Tag mit Paket-/Klassen-/Methodenbezug als **fester** Text (kein `getName()`, wegen Obfuskation; keine Zähler/IDs; keine personenbezogenen Daten, sonst `_UNKNOWN`); Namensschema der Javadoc: eindeutiges Präfix mit Doppelpunkt (`app:tag`), kein `*alarm*`-Präfix.
- Timeouts: Doku release-wakelock: „It's best to acquire the wake lock with WakeLock.acquire(long timeout) … However, you should still release the wake lock explicitly“, `acquire` im `try`, `release` im `finally`; Beispiel der Doku: 10 min (`acquire(60 * 10 * 1000)`). Implementierung: das Timeout ist ein `Handler.postDelayed` auf dem **Haupt-Thread-Handler der App** (`PowerManager.java:4060-4064`; `SystemServiceRegistry.java:646-647`) [A]: blockierter Haupt-Thread verzögert die Freigabe. Ein `release()` nach abgelaufenem Timeout wirft nicht (`mReleaser` ruft `release(RELEASE_FLAG_TIMEOUT)`, dabei bleibt `mExternalCount` unverändert, `:3991`, `:4114-4141`) [A]; mehr `release()` als `acquire()` wirft `RuntimeException("WakeLock under-locked …")` (`:4137-4139`).
- Wann überhaupt: Entscheidungsbaum der Doku („Choose the right API to keep the device awake“): Läuft **kein** FGS ⇒ keinen WakeLock halten; läuft ein FGS und würde ein Suspend bei ausgeschaltetem Bildschirm die Nutzererfahrung stören ⇒ ein WakeLock „might“ nötig, aber erst prüfen, ob eine API ihn schon hält. Ein FGS allein hält die CPU nicht wach: „A foreground service is a lifecycle API that signals to the system that an app is performing user-perceptible work and should not be killed to reclaim memory, but it does not automatically prevent the CPU from sleeping when the screen turns off“; ein manueller Partial-WakeLock sei „only necessary in conjunction with a foreground service for the duration of the CPU activity“ (Android-Blog „Battery Technical Quality Enforcement is Here“, 2026-03-04). Dort auch: für periodische/einmalige Syncs **keinen** manuellen WakeLock, sondern WorkManager; für nutzerinitiierte Up-/Downloads UIDT. Automatisch gehalten (nicht doppelt anfordern): WorkManager/JobScheduler/DownloadManager („the system or library acquires a wake lock that is attributed to your app“), AlarmManager bis `onReceive` endet, Audio, Wake-up-Sensoren; WorkManager-Namen siehe JobScheduler-Abschnitt.
- Best Practices (Doku): WakeLock in einem FGS halten (Benachrichtigungspflicht), Logik einfach halten, immer im `finally` freigeben; „If a foreground service isn't the right choice for your app, you probably shouldn't be using a wake lock, either.“ Für nutzerinitiierte Down-/Uploads **keinen** manuellen WakeLock, sondern UIDT (identify-wls).
- Doze/gecacht: im Doze werden WakeLocks von Apps ohne Allowlist/FGS ignoriert, gecachte Prozesse dürfen keine halten (`android-background-reachability.md` §1.1); `setStateListener` meldet das Aus-/Einschalten durch das System (API 33).

## Grenzen und Android-14/15-Hinweise
- Android 14, 15 und 16: In `behavior-changes-all` (14, 15, 16) und `behavior-changes-14/15/16` keine WakeLock-Regel gefunden (Seiten nach „wake lock“ durchsucht, 0 Treffer); die Alarm-Seite `schedule-exact-alarms` ändert nur Berechtigungen. WakeLock-Namen für Jobs wurden mit Android 16 QPR2 erweitert (siehe oben).
- Play-Vitals (nur Store-Wertung, für Sideload nicht verbindlich, aber als Richtwert): „Excessive partial wake locks“ = nicht ausgenommene WakeLocks bei ausgeschaltetem Bildschirm, App im Hintergrund oder mit FGS, **zusammen ≥ 2 h in 24 h** bei mehr als 5 % der Sitzungen (28-Tage-Mittel); ausgenommen Audio, Location und JobScheduler-UIDT; seit 2026-03-01 kann Play betroffene Titel aus Empfehlungen nehmen (Blog). „Stuck partial wake locks“: mindestens ein WakeLock von mehr als einer Stunde je Sitzung, nur im Hintergrund erhoben (Play-Console-Hilfe 9844486, Stand der Abruf-Seite).
- Stolperfallen: kein Acquire ohne Timeout/`finally`; Tag nie dynamisch; bei WorkManager-Workern keinen eigenen WakeLock für die Dauer des Jobs; Arbeit **nach** `onStopJob`/Worker-Stopp hält das System nicht mehr wach (Wakelock des Jobs weg).

## Was „WLAN“ und „unmetered“ bedeuten
- Doku NetworkCapabilities: `NOT_METERED` = Netz, das den Verbrauch nicht abrechnet; gilt für WLAN **und** Mobilfunk. Doku Android-11-5G-Seite: `NOT_METERED` ist dauerhaft: „A network with this capability will disconnect automatically if it loses the capability (becomes metered)“ ([A]: etwa wenn der Nutzer das WLAN als getaktet markiert, wird das Netz getrennt/neu aufgebaut; Auslöser im Einzelnen nicht geprüft); `TEMPORARILY_NOT_METERED` (API 30) kann **ohne Trennung** wegfallen („applications are responsible for stopping any data transfer that should not occur on a metered network“); ein Netz hat nie beides; „unmetered“ prüfen mit `hasCapability(NOT_METERED) || hasCapability(TEMPORARILY_NOT_METERED)`; „INTERNET … may or may not actually provide connectivity; the VALIDATED bit indicates that the system found actual connectivity“.
- WLAN-Erkennung: `hasTransport(TRANSPORT_WIFI)`. Ein VPN-Netz trägt die Transporte der zugrunde liegenden Netze (`TRANSPORT_VPN` + `TRANSPORT_WIFI`; `NOT_METERED` nur, wenn der Agent es deklariert und alle zugrunde liegenden Netze unmetered sind) (`ConnectivityService.applyUnderlyingCapabilities`, `:10336-10401`). Deklariert die VPN-App keine Underlying-Netze (`null`), verfolgt das System das Standardnetz ihrer UID (`underlyingNetworksOrDefault`, `:7486-7494`); ohne irgendein Underlying-Netz gilt das VPN als `metered` (`:10385-10391`). Standardnetz mit VPN über WLAN erfüllt also `TRANSPORT_WIFI`; ein reines `NOT_VPN`-Request nicht.
- Anfrage für „unmetered WLAN, auch mit VPN“ (nicht kompiliert; Muster aus `NetworkTypeCompat.kt`, Transport ergänzt):

- `Constraints.Builder.setRequiredNetworkRequest(networkRequest: NetworkRequest, networkType: NetworkType)` (WorkManager ≥ 2.10): ab API 28 gilt die Anfrage (`requiredNetworkType` wird `NOT_REQUIRED`), darunter der `networkType`; eine Anfrage mit `NetworkSpecifier` wirft ab API 31 `IllegalArgumentException` (KDoc nennt zusätzlich `setIncludeOtherUidNetworks` als nicht unterstützt); `setRequiredNetworkType` setzt die Anfrage zurück (letzter Aufruf gewinnt) (`Constraints.kt`).
- JobScheduler-/WorkManager-Netz: `JobParameters.getNetwork()` (API 28) bzw. `ListenableWorker.getNetwork()` (API 28) nennt das Netz, das die Constraint erfüllt; Javadoc `JobInfo`: „be sure to use the specific network returned by getNetwork(), otherwise you'll use the default network which may not meet this constraint“. Einzelsockets: `Network.getSocketFactory()`/`bindSocket`; NDK (`android/multinetwork.h`): `android_setsocknetwork(net_handle_t network, int fd)` und `android_setprocnetwork(net_handle_t network)` (beide API 23; `net_handle_t` = `Network.getNetworkHandle()` als `long`), `android_getprocnetwork` (API 31). `bindProcessToNetwork`: „All Sockets created in the future … will be bound to network. … if network ever disconnects, all Sockets created in this way will cease to work and all host name resolutions will fail“; die Doku bevorzugt einzeln gebundene Sockets.
- `registerNetworkCallback(request, PendingIntent)` [A, `ConnectivityService.java:11018-11080`]: der Intent wird **nur beim ersten** `CALLBACK_AVAILABLE` gesendet (`mPendingIntentSent`), danach wird die Anfrage verzögert freigegeben (`releasePendingNetworkRequestWithDelay`); der Versand hält einen WakeLock bis `onSendFinished` und verbietet Activity-Starts. Taugt als einmaliger Wecker „WLAN ist wieder da“ ohne Prozess; Bestand nach Neustart/Force-Stop nicht geprüft [?]; ein FGS-Start aus dem Empfänger ist nicht abgesichert [A].

# Abbruch bei entfallender Netzbedingung: was mit Arbeit außerhalb des Workers geschieht
Quelle: wie WorkManager-, JobScheduler- und Netz-Abschnitt; `https://source.android.com/docs/core/perf/cached-apps-freezer` (Stand Abruf), `https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.11.0/docs/topics/cancellation-and-timeouts.md` · Abgerufen: 2026-10-02

- **System → Worker** (Constraint `UNMETERED`/Netzanfrage entfällt): JobScheduler ruft `onStopJob` mit `STOP_REASON_CONSTRAINT_CONNECTIVITY (7)`; `SystemJobService.onStopJob` ruft `stopWorkWithReason` und gibt `!isCancelled` zurück (Neuplanung durch JobScheduler, `SystemJobService.java:181-208`). Läuft der Worker greedy im Prozess, meldet der Constraint-Tracker `ConstraintsNotMet(STOP_REASON_CONSTRAINT_CONNECTIVITY)` und stoppt ihn genauso (`GreedyScheduler.java:234-253`, `onConstraintsStateChanged`). Danach: Zustand `ENQUEUED`, läuft wieder, wenn die Constraints stimmen (Doku define-work: „WorkManager will stop your worker. The work will then be retried when all the constraints are met.“).
- **WorkManager → Worker-Code**: nur `onStopped()`/`isStopped()` bzw. Coroutine-Abbruch (Mechanik im WorkManager-Abschnitt). WorkManager wartet nicht, ignoriert danach das Ergebnis und kann bereits einen neuen Worker planen.
- **Nicht betroffen**: eigene Threads, native Aufrufe (Rust über JNI), Coroutines in fremden Scopes, andere Dienste laufen weiter. Folgen [A]: (1) `JobService`-WakeLock des Jobs endet, sobald `onStopJob` zurückkehrt (Javadoc), die CPU darf schlafen; (2) der Prozess verliert die Job-/FGS-Wichtigkeit, wird gecacht und ab Android 14 nach 10 s eingefroren (ab Android 11 abhängig von Gerät/Flag); eingefrorene Apps verlieren aktive TCP-Verbindungen („the system terminates any active TCP sockets“); (3) Ergebnis des Alt-Codes wird ignoriert, er kann aber Dateien/Index halb schreiben, während eine neue Instanz startet.
- Muster [Schluss, nicht kompiliert]: Abbruchsignal in den Kern führen. `CoroutineWorker`: kotlinx.coroutines-Abbruch ist kooperativ (nur an Suspendierungspunkten oder expliziter Prüfung) ⇒ ein blockierender JNI-Aufruf in `withContext(Dispatchers.IO)` sieht den Abbruch erst nach Rückkehr; stattdessen den nativen Lauf in einer `suspendCancellableCoroutine` kapseln und `invokeOnCancellation { core.cancel(handle) }` setzen, oder in einem Kind-Coroutine `try { awaitCancellation() } finally { core.cancel(handle) }`. `Worker`: in `onStopped()` nur das Abbruchflag/`core.cancel(handle)` setzen (leichtgewichtig) und `isStopped()` pollen. Vor dem Stopp Fortschritt persistieren (kein „Ergebnis“ mehr nach dem Signal), Wiederaufnahme idempotent bauen.
- **Pause statt Abbruch bei App-eigenem FGS** (kein WorkManager): das System stoppt nichts; die App wertet `registerDefaultNetworkCallback` (`onCapabilitiesChanged`/`onLost`) selbst aus, pausiert/bricht die Übertragungen im Kern ab und nimmt bei erneutem „erlaubt“ wieder auf; Dienst läuft weiter (Netz im FGS ohne Beschränkung, `android-background-reachability.md` §1.1); `onBlockedStatusChanged(network, blocked)` meldet zusätzlich, wenn Data Saver/Doze das Netz sperren.
- `TEMPORARILY_UNMETERED`: nach Doku und `NetworkType`-KDoc sind Worker selbst verantwortlich, Datentransfer zu stoppen, wenn die Eigenschaft entfällt, ohne dass das Netz getrennt wird.

# Offene Punkte
1. Zustellung von ContentObserver-Meldungen an gecachte/eingefrorene Prozesse (Queue, Entfrieren, Überlauf) nur aus der Freezer-Doku (Async-Binder) abgeleitet; am Gerät nicht gemessen.
2. MediaProvider-Indexierung von Änderungen ohne MediaStore-Weg (reine Dateipfad-Schreibzugriffe): nur aus `FuseDaemon.cpp`/`MediaProvider.java` abgeleitet (kein Hook bei `write`/`release`; Scan bei Idle 24 h/Mount/Anforderung); Latenz, `.nomedia`-/versteckte Ordner und `Android/data` in `MediaStore.Files` nicht geprüft; OEM-Abweichungen offen.
3. Alarm-Quoten: Doku-Zahlen (9 min, 7/h) und AOSP-Code (72/h bzw. 7/h, Active 720/h) weichen ab; OEM-/DeviceConfig-Werte offen; Verhalten von `isAppStartModeDisabled` (Alarm wird verworfen) nicht ausgewertet.
4. Alarme und WorkManager-Jobs über ein App-Update (JobScheduler-Seite) nicht geprüft; Alarme bleiben laut `AlarmManagerService.java:4998-5005`.
5. WorkManager: Verhalten von `GreedyScheduler` bei nicht sichtbarer App (Prozess lebt) vs. JobScheduler-Start in der Praxis nicht gemessen; die 90-min-`TimeLimiter`-Grenze und die 10-/30-min-JobScheduler-Grenze sind Quelltext-Standardwerte; Doku widerspricht sich („longer than 10 minutes“ vs. „rescheduled“).
6. `setForeground` aus dem Hintergrund (periodischer Worker, Android 12+): „kein Job-Grund in `PowerExemptionManager`“ ist ein Negativbefund aus der Quelle, kein Gerätetest.
7. UIDT: Zeitgrenzen (6 h/12 h/24 h) nur AOSP-Standardwerte, in der Doku nicht genannt; `STOP_REASON_TIMEOUT_ABANDONED` ist in API 36 `@FlaggedApi` (Verfügbarkeit je Build offen).
8. `registerNetworkCallback(…, PendingIntent)`: Einmal-Semantik und Freigabeverzögerung (`mReleasePendingIntentDelayMs`) aus Quelltext; Bestand nach Neustart/Force-Stop, Standardwert der Verzögerung nicht gelesen.
9. Unterschied in der Netzauswahl: JobScheduler wertet pro Netz aus und liefert `getNetwork()`, die In-Process-Prüfung von WorkManager (API 30+) nur das Standardnetz (`registerDefaultNetworkCallback`); bei VPN/Mehrfachnetzen können beide abweichen [A].
10. Android 17 (API 37): `behavior-changes-17`/`-all` nach Alarm/Job/WakeLock/`dataSync` durchsucht (nur Audio-Härtung und `ACCESS_LOCAL_NETWORK` gefunden); AOSP-Zweig `android17-release` nicht gelesen, Projekt-`compileSdk` ist 36.
11. Play-Vitals-Schwellen für WakeLocks gelten nur für Play-Verteilung; Systemgrenzen für WakeLocks im Doze/Cached siehe `android-background-reachability.md`.
12. Battery Saver (Energiesparmodus) und die Nutzer-Einstellung „Restricted“: nur `JobStatus.canRunInBatterySaver()` gelesen; Wirkung auf Alarme/WorkManager im Einzelnen, Hersteller-Killer und Hibernation nicht geprüft (siehe `android-background-reachability.md` §7).
13. Stopps durch Absturz/Prozess-Kill/leeren Akku: nur `WorkInfo.STOP_REASON_UNKNOWN` (KDoc „app abruptly stopped due to a crash or … ran out of the battery“) belegt; wie WorkManager solche Läufe wieder anstößt, nicht untersucht.
14. `android:requestRawExternalStorageAccess` im Manifest der eigenen App (außerhalb des Lesebereichs dieser Recherche, nicht geprüft): steht es auf `true`, spiegelt MediaProvider die Dateioperationen der App nicht in `MediaStore`; steht es nicht, gilt für Target 36 der Standard „DB wird gepflegt“ (siehe Abschnitt MediaProvider). Auswirkung auf Meldungen/Generationen **anderer** Apps mit Raw-Zugriff (Dateimanager) nicht gemessen.
