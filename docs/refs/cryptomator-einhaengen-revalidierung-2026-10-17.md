### B2 — Standard je Betriebssystem und gemeldete Zuverlässigkeitsprobleme

**Standard und Begründung (Volume-Type-Doku, abgerufen 2026-10-17, Zitate):**
- Windows, WinFsp / WinFsp (Local Drive): „unlocked vaults are mounted to a random drive letter“; Begründung: „The WinFsp project provides FUSE bindings for Windows.“; Grenze: „Vaults mounted to a drive letter are only accessible to the current user.“ Der Blogbeitrag zu 1.14.0 (2024-09-17) sagt: „"WinFsp" is the default on Windows.“
- Windows, WebDAV (Windows Explorer): „We recommend using WinFsp due to its restrictions.“; Grenzen: 4 GB Dateigröße, 260 Zeichen Pfadlänge, falsche Platzanzeige.
- macOS: ohne installierten FUSE-Treiber WebDAV („On macOS, Cryptomator will use WebDAV volume type by default if no FUSE driver is installed on the system.“, `docs.cryptomator.org/desktop/setup/`); Empfehlung: „Install macFUSE if your Mac comes with an Intel CPU or install FUSE-T if your Mac comes with an Apple Silicon CPU.“ macFUSE: „the most mature FUSE implementation for macOS“, aber Kernel-Erweiterung („Apple has deprecated kernel extensions with macOS 12.3“). FUSE-T: „runs entirely in user space“, aber „less mature than macFUSE and some users have reported occasional malfunctions.“
- Linux, FUSE: Standardort `~/.local/share/Cryptomator/mnt`; „FUSE on Linux works only if the `fuse3` package is installed.“ WebDAV (gio): „support across distributions is not guaranteed.“ Verteilformen laut Setup-Seite: Flatpak, PPA, AUR, AppImage („The easiest and recommended way … is by downloading Cryptomator's AppImage“).
- Alle Systeme, WebDAV (HTTP Address): „always present and comes in handy when all other volume types fail to mount.“

**Geschichte des Windows-Standards (belegt):**
- 1.5.9 (2021): WinFsp eingeführt; Forum, infeo, 2021-05-29: „We implemented support for it because it might lead to less code maintenance in the long term“ und „it showed promising stability and performance in test runs.“ (`community.cryptomator.org/t/winfsp-how-to-use-it/7980`).
- 1.6.7 (Blog, 2022-03-25): Standard wechselt von Dokany zu WinFsp: „The time has come to make this the default choice so we can focus on a common code base.“, „mainly based on the long-term maintenance effort“, „Please note that Dokany 2.x is not yet supported and our existing Dokany 1.x glue code requires a migration.“ (Fundstelle `cryptomator.org/tags/installer`; Direkt-URL des Beitrags nicht ermittelt.)
- 1.7.0: Dokany als Volume Type abgekündigt (laut 1.13.0-Notiz; die 1.7.0-Releaseseite selbst erwähnt Dokany nicht). 1.7.0 ersetzt die FUSE-Implementierung durch jFUSE und führt die MountService-API ein; die Seite warnt vor schweren Fehlern mit Datenbeschädigung in 1.7.0 und empfiehlt 1.7.3 oder neuer.
- 1.13.0 (26 Jun 2024): „Removal of Dokany: We deprecated volume type "Dokany" with version 1.7.0 and now finally removed it.“ Issue #3361 „Remove Dokany Support“ (2024-03-06): Begründung „We deprecated the Dokany volume type a year ago. Furthermore, we have issue #3351.“; Alternative „Implement Dokany 2.0: Currently not feasible for the Cryptomator dev team due to other works“. Issue #3351: Absturz von Cryptomator 1.12.3 im Dialog „Existing Vault“, Crashdump zeigt Zugriffsverletzung in `dokan1.dll` 1.5.1.1000; Maintainer: „Finally! We found the culprit: `dokan1.dll`.“
- 1.14.0 (2024-09-17): „Editing Microsoft Office documents in a Dropbox vault on Windows occasionally led to data loss.“ — „The reason: The "WinFsp" drive type is incompatible with both Microsoft Office and Dropbox“ — neue Dropbox-Tresore erhalten automatisch „WinFsp (Local Drive)“.

### B3 — Android und iOS

**Android (Cryptomator Android 2.0.1 / `develop`):** Ein einziger `<provider>`: `androidx.core.content.FileProvider`, Authority `${applicationId}.fileprovider`, nicht exportiert, `grantUriPermissions=true`; kein `DOCUMENTS_PROVIDER`-Filter, kein `MANAGE_DOCUMENTS` (`presentation/src/main/AndroidManifest.xml` auf `develop`, abgerufen 2026-10-17). Doku (`docs.cryptomator.org/android/access-vault/`): Datei antippen startet „view and edit process“; nach Rückkehr per Zurück-Taste „If the content has changed, the upload process starts.“; Tresor sperrt im Hintergrund („will lock the vault if Cryptomator is in background“) und standardmäßig bei ausgeschaltetem Bildschirm. Anderen Apps stehen Tresore nur über das Teilen-Menü (Datei hinaus- bzw. hineinteilen) zur Verfügung. Issue #35 „Allow vault access by other apps through Document Provider“ ist offen (seit 2017-01-26); Maintainer 2019: „we also consider it as an existential feature“; 2024-02-15: Arbeit Aug.–Okt. 2023, dann pausiert wegen nötigem Umbau der Datenbankverwaltung. Issue #591 (2025) als Duplikat geschlossen und gesperrt. Einzelheiten und Vergleich mit DocumentsProvider-Implementierungen: `docs/refs/android-documents-provider-2026-10-17.md`.

**iOS (`github.com/cryptomator/ios`, Branch `develop`, Commit-SHA nicht ermittelt):** Verzeichnisse `FileProviderExtension` und `FileProviderExtensionUI`; `FileProviderExtension.swift` deklariert „class FileProviderExtension: NSFileProviderExtension {“; `stopProvidingItem` enthält nur „Not implemented in the moment.“ Apple (`developer.apple.com/documentation/fileprovider/nsfileproviderextension`): „The principal class for the nonreplicated File Provider extension.“; `startProvidingItem(at:)`: „Provides an actual file on disk for a placeholder.“ Doku: „Cryptomator for iOS is fully integrated into the Files app of iOS.“ und „In order to access your encrypted data, you have to use the Files app.“ **Folgerung:** iOS stellt Tresordateien als echte Dateien im Container der Erweiterung bereit (entschlüsselte Kopie bei Zugriff), nicht als Strom wie Androids Proxy-FD. Grenzen der Erweiterung (Speicher, Laufzeit) wurden nicht belegt (Lücke L-B4).

### B4 — Belegte Fakten zur Ersetzung oder Ergänzung von Dokany

Fakten:
1. Cryptomator hat Dokany 1.x verwendet, ab 1.6.7 WinFsp zum Standard gemacht und Dokany in 1.13.0 entfernt. Die genannten Gründe sind Wartungsaufwand und eine gemeinsame FUSE-Codebasis für alle Desktopsysteme („focus on a common code base“, „long-term maintenance effort“), fehlende Kapazität für Dokany 2.x (#3361) und ein Absturz in `dokan1.dll` (#3351). Eine Aussage, dass Dokany 2.x unzuverlässiger sei als WinFsp, findet sich in keiner gelesenen Cryptomator-Quelle.
2. Smart Explorer nutzt Dokany 2.3.1 (DLL-API 231, Treiberprotokoll 0x190/400) über eigene Rust-FFI (`docs/lesungen/2026-10-17-laufwerke-kern.md` F5/F6 mit Zitat aus `docs/REMOTE_FS_TRADEOFFS.md:278-283`), nicht Dokany 1.x über Java. Die Cryptomator-Fehler mit Dokany (#1449, #1627, #3351, #949, #960) betreffen Dokany 1.x und Cryptomators Anbindung.
3. Dokany-Releases: v2.3.1.1000 „Latest“ (28 Sep, Jahr auf der Seite nicht angezeigt), v2.3.0.1000 (19 Apr); v2.2.0.1000: „keeping network drives isolated between users when browsing with UNC path“ und ARM64-MSI; v2.1.0.1000: „Few (rare) BSOD fixed.“ (`github.com/dokan-dev/dokany/releases`).
4. WinFsp ist als Treiber weiter aktiv gepflegt; die 2026-Betas beheben acht gemeldete Schwachstellen und vier Deadlocks (B1). Der stabile Stand ist v2.1 (2025).
5. Cryptomators WinFsp-Weg hat eigene offene Fehler mit Office/Dropbox (#2880, seit 2023 offen, Nutzerbericht 2026-10-02), Groß-/Kleinschreibung (#4256), Sperren (#3614), Shell-Overlays (#4192) und WSL (#3587). Die Netzwerk-Variante („WinFsp“) ist laut Cryptomator mit Office und Dropbox inkompatibel; die Local-Drive-Variante ist die Abhilfe.
6. Der Vorbefund §8 belegt WinFsp-Lizenz GPLv3 mit FLOSS-Ausnahme und separater kommerzieller Lizenz; dieser Stand wurde heute nicht erneut gelesen.
7. Linux: Cryptomator nutzt libfuse3 über jFUSE (FFM); fuse-nio-adapter 7.0.0 sucht libfuse per FFI. Voraussetzung ist das Paket `fuse3`; `allow_other`/`allow_root` benötigen `user_allow_other` in `/etc/fuse.conf` (Vorbefund §6, Doku bestätigt). Offene Linux-Fehler: Aushängen beim Abmelden (#3648), gleichnamige Tresore (#3344), erzwungenes Sperren (#1658).
8. Ein Einhänge-Ende-Signal (`whenTerminated`) führt Cryptomator erst mit integrations-api 1.10.0 (2026-10-13) ein, ausdrücklich, weil ein unbemerkt beendetes Einhängen in einen vorhandenen Ordner zu Klartext auf der Platte führt. Für Dokany hatte Cryptomator bereits 2021 die Erkennung externer Aushängungen nachgerüstet (#1508, genannt in #1449).

Folgerungen (keine Entscheidung):
- **Folgerung F1:** Die belegten Cryptomator-Gründe für den Wechsel von Dokany zu WinFsp sind organisatorisch (eine FUSE-Codebasis für drei Systeme, Wartung) und betreffen eine Dokany-1.x-Anbindung, die Smart Explorer nicht hat. Ein Zuverlässigkeitsgewinn eines Wechsels von Dokany 2.3.1 zu WinFsp für Smart Explorer ist durch Cryptomator-Quellen nicht belegt.
- **Folgerung F2:** Die Cryptomator-Fehlerbilder mit WinFsp (Office-Speichern über Umbenennen, Sperren, Groß-/Kleinschreibung) entsprechen den Fällen, die Smart Explorer laut Lesung `laufwerke-kern.md` F6 bei Dokany noch offen hat (Editor-Atomarersatz, Konflikte, Obsidian). Ein Frontendwechsel allein beseitigt diese Fallklasse nach den gelesenen Quellen nicht; sie entsteht in der Dateisystemschicht hinter dem Frontend (Cryptomator: Verzeichniscache in CryptoFS als Hypothese zu #2880).
- **Folgerung F3:** Als Ergänzung (nicht Ersatz) übertragbar sind: (a) ein lokaler WebDAV-Fallback ohne Treiber, wie Cryptomators „WebDAV (HTTP Address)“, „when all other volume types fail to mount“, mit den dokumentierten Windows-Client-Grenzen 4 GB und 260 Zeichen; (b) ein Einhänge-Ende-Signal wie `whenTerminated`, das bei unerwartetem Aushängen sperrt bzw. den Zustand meldet; (c) die Trennung „Laufwerksbuchstabe nur für aktuellen Nutzer“ gegenüber Ordner-Einhängung für andere bzw. erhöhte Nutzer.
- **Folgerung F4:** Für Linux ist libfuse3 der von Cryptomator belegte und einzige FUSE-Weg; die Mount-Engine-Grenze von Smart Explorer (Lesung §3, Ebene D) passt strukturell zu den libfuse-Operationen (open/read/write/flush/release/rename/unlink), was hier nur aus den Signaturen gefolgert, nicht geprüft ist. Für AppImage-Verteilung setzt Cryptomator voraus, dass `fuse3` auf dem Host installiert ist.
- **Folgerung F5:** Auf Android gibt es keinen von Cryptomator genutzten Einhängeweg; Cryptomator bietet anderen Apps nur Kopien über FileProvider. Ein DocumentsProvider wäre für Smart Explorer eine Fähigkeit, die Cryptomator Android selbst nicht hat (Issue #35 offen).

## 4. Widersprüchliche Angaben
