- Minimalbeispiel 6.1.1 (Kanal-Handler, Überlauf und Limit behandeln):
```rust
use notify::{recommended_watcher, ErrorKind, Event, RecursiveMode, Result, Watcher};
use std::{path::Path, sync::mpsc};
fn run(root: &Path) -> Result<()> {
    let (tx, rx) = mpsc::channel::<Result<Event>>();
    let mut watcher = recommended_watcher(tx)?;          // Backend-Thread läuft sofort
    watcher.watch(root, RecursiveMode::Recursive)?;      // synchron: Linux läuft hier den Baum ab
    for res in rx {
        match res {
            Ok(ev) if ev.need_rescan() => { /* Teil-/Vollscan anstoßen */ }
            Ok(ev) => { /* ev.kind, ev.paths */ }
            Err(e) if matches!(e.kind, ErrorKind::MaxFilesWatch) => { /* Watch-Limit: Poll/Vollscan-Fallback */ }
            Err(_e) => {}
        }
    }
    Ok(())
}
```

## Backend inotify (Linux, Android) – Verhalten 6.1.1 (`src/inotify.rs`)
- Watch-Mask je Verzeichnis: `ATTRIB | CREATE | DELETE | CLOSE_WRITE | MODIFY | MOVED_FROM | MOVED_TO`, nur für die Wurzel zusätzlich `DELETE_SELF | MOVE_SELF` (:393-404). Kein `OPEN`, `CLOSE_NOWRITE`, `ACCESS`, `ONLYDIR`, `DONT_FOLLOW`, `EXCL_UNLINK`, `MASK_CREATE`. 7.0/8.x: `+ OPEN` (Ereignisflut durch jeden Lesezugriff; 8.x ohne Abschalter); 9.x: Maske aus `EventKindMask` (`CORE` = Create|Remove|Modify-Data/Meta/Name ohne Access; `CLOSE_WRITE` nur mit `ACCESS_CLOSE`; Test-Kommentar `inotify.rs:1442`: OPEN-Ereignisse „would otherwise flood the queue … causing Rescan“).
- Abbildung: `CREATE` → `Create(File|Folder)`; `DELETE`/`DELETE_SELF` → `Remove(File|Folder)`; `MODIFY` → `Modify(Data(Any))`; `CLOSE_WRITE` → `Access(Close(Write))`; `ATTRIB` → `Modify(Metadata(Any))`; `MOVED_FROM` → `Modify(Name(From))` + `tracker = cookie`; `MOVED_TO` → `Modify(Name(To))` + tracker und, wenn Cookie zum zuletzt gemerkten FROM passt, zusätzlich `Modify(Name(Both))` mit `[alt, neu]`; `MOVE_SELF` → `Modify(Name(From))` (kein To/Both, `// TODO` im Code); `Q_OVERFLOW` → pfadloses `Event::new(EventKind::Other).set_flag(Flag::Rescan)` (:208-211).
- Rekursion = eigener Walk: `WalkDir::new(path).follow_links(true)` + ein `inotify_add_watch` je Verzeichnis (:375-382). **Folgt Verzeichnis-Symlinks** (auch aus dem Baum heraus; in 6.1.1 nicht abschaltbar, ab 8.0 `Config::with_follow_symlinks(false)`). Der **erste** Fehler bricht den Walk ab (`?` :380); bis dahin gesetzte Watches bleiben aktiv (Teilzustand, `watch()` meldet Fehler) – 9.x läuft weiter und meldet je Fehler.
- Neue Unterordner: erst nach dem Lesen der aktuellen Event-Charge werden Watches für `CREATE`/`MOVED_TO`-Verzeichnisse gesetzt (:359-365); Fehler dort mit `.ok()` verworfen ⇒ **Limit-Treffer bleibt in 6.1.1 stumm** (8.2.0 meldet `MaxFilesWatch`, 9.x alle Fehler). Dateien, die zwischen `mkdir` und Watch entstehen, erzeugen kein Event; der Walk meldet bereits vorhandene Einträge nicht [A] (Race laut man inotify(7), siehe Linux-Abschnitt).
- Lesepuffer `[0; 1024]` (:198), `mio::Events::with_capacity(16)`; `poll failed` ⇒ `panic!` im Backend-Thread (:133). `inotify 0.9.6` `read_events` liefert bei `EAGAIN` leere `Events` (nicht `WouldBlock`; `inotify-0.9.6/src/inotify.rs` `read_events`), die Schleife endet bei `num_events == 0`.

## Backend ReadDirectoryChangesW (Windows) – Verhalten 6.1.1 (`src/windows.rs`)
- `const BUF_SIZE: u32 = 16384` (:39) je `watch()`-Aufruf; `bWatchSubtree = TRUE` bei `Recursive` ⇒ **ein** Handle/Puffer je Wurzel, nicht je Verzeichnis. In 8.2.0 und 9.0.0-rc.5 unverändert 16384 (`windows.rs:40` / `:42`).
- Filter (:265-271): `FILE_NOTIFY_CHANGE_FILE_NAME | DIR_NAME | ATTRIBUTES | SIZE | LAST_WRITE | CREATION | SECURITY` (kein `LAST_ACCESS`). Öffnen (:179-187): `CreateFileW(FILE_LIST_DIRECTORY, FILE_SHARE_READ|WRITE|DELETE, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS|FILE_FLAG_OVERLAPPED)`.
- Completion-Routine `handle_event(error_code, _bytes_written, overlapped)` (:313-410): behandelt nur `ERROR_OPERATION_ABORTED`; `_bytes_written` und andere Fehlercodes (u. a. `ERROR_NOTIFY_ENUM_DIR`) werden **ignoriert**; der frisch genullte Puffer ergibt Action 0 ⇒ kein Event. **Kein Überlauf-Signal in 6.1.1 und 8.2.0** (PR-Text #964: „The backend previously ignored the transferred-byte count … consumers received no indication that their view of the filesystem might be stale“). Schlägt `ReadDirectoryChangesW` beim Wiederanstoßen fehl (`ret == 0`, :301-309), wird nur der Semaphor freigegeben – **kein Fehler an den Handler**; der Watch ist danach still tot [A]. 9.0.0-rc.5: `completion_rescan_event` ⇒ pfadloses `Flag::Rescan`-Event bei `ERROR_NOTIFY_ENUM_DIR` oder (`ERROR_SUCCESS` ∧ 0 Bytes) (`windows.rs:528-530`).
- Abbildung: `ADDED` → `Create(Any)` (9.x: `File`/`Folder` per Metadata-Abfrage); `REMOVED` → `Remove(Any)`; `MODIFIED` → `Modify(Any)`; `RENAMED_OLD_NAME` → `Modify(Name(From))`; `RENAMED_NEW_NAME` → `Modify(Name(To))`; **kein Tracker, kein `Both`** (Paarung nur über Datei-IDs im Debouncer).
- Datei-Watch wird als Eltern-Verzeichnis-Watch + Pfadfilter emuliert (:163-170). `watch()` auf Pfad, der weder Datei noch Verzeichnis ist ⇒ `Err(Generic("Input watch path is neither a file nor a directory."))`. `unwatch()` sendet nur und wartet nicht (6.1.1; ab 9.0.0-rc.3 wartet es).

## PollWatcher – Verhalten 6.1.1 (`src/poll.rs`)
- Scan: `WalkDir::new(root).follow_links(true)` (:258-261, folgt Links). Vergleich je Eintrag: `mtime` in **ganzen Sekunden** (`FileTime::seconds()`, :339); `new.mtime > old.mtime` ⇒ `Modify(Metadata(WriteTime))`, sonst bei anderem Hash `Modify(Data(Any))`; **Größe wird nicht verglichen**; neu/verschwunden ⇒ `Create(Any)`/`Remove(Any)`; keine Rename-Erkennung. Änderung innerhalb derselben Sekunde ohne `compare_contents` bleibt unsichtbar. `compare_contents` liest und hasht **jede** Datei bei **jedem** Poll (512-Byte-Lesepuffer, `RandomState`-Hasher, :353-370). 9.x: Nanosekunden-mtime, xxh3.
- `watch()` liefert auch bei fehlendem/nicht lesbarem Pfad `Ok(())` (Fehler nur als Event an den Handler, :576-593; „unreleased“ ändert das); der erste Scan läuft synchron im `watch()`-Aufruf. Wartezeit `recv_timeout(delay)` **nach** dem Scan (:540-568) ⇒ Periode = Scandauer + Intervall. Der Handler läuft im Poll-Thread bei gehaltenen Locks; `watch`/`unwatch` aus dem Handler ⇒ Deadlock [A].

## Thread-Modell, Fehler, Netzlaufwerke (notify)
| Backend | Thread | Handler läuft auf | `watch()`/`unwatch()` |
|---|---|---|---|
| inotify | `notify-rs inotify loop` (mio-Poll + eventfd-Waker) | Backend-Thread | senden Nachricht und **blockieren** auf Antwort (`rx.recv().unwrap()`, `inotify.rs:519,535`) ⇒ Aufruf aus dem Handler = Deadlock [A] |
| Windows | `notify-rs windows loop` (alertable `WaitForSingleObjectEx(…, 100 ms, TRUE)`) | APC-Completion-Routine im Backend-Thread, unter `Mutex` | `watch()` wartet auf Ack, `unwatch()` nicht (6.1.1) |
| Poll | `notify-rs poll loop` | Poll-Thread | Locks s. o. |
- Alle Watcher sind `Send + Sync` (Tests `*_is_send_and_sync`), alle Methoden `&mut self`; Drop beendet den Backend-Thread (Poll: nach dem laufenden Scan, weil mit dem Watcher auch der Poll-Sender geschlossen wird [A]). Handler kurz halten (nur in Kanal senden), sonst staut sich die Kernel-Queue (Linux: `max_queued_events`, Windows: 16-KiB-Puffer).
- Fehlerarten: `MaxFilesWatch` = `ENOSPC` aus `inotify_add_watch` (`inotify.rs:416-418`); `EMFILE` aus `inotify_init1` (Instanzlimit) bleibt `ErrorKind::Io` [A]; `PathNotFound`/`Io(NotFound)` bei fehlendem Pfad; Windows: `Generic(...)`.
- lib.rs-Doku „Known Problems“ (6.1.1, unverändert in 8.2.0): NFS u. ä. „may not emit any events“ (WSL-Zugriff auf Windows-Pfade #254), Workaround `PollWatcher`; `/proc`, `/sys` ⇒ `PollWatcher` mit `compare_contents`; „When watching a very large amount of files, notify may fail to receive all events. For example the linux backend is documented to not be a 100% reliable source“ (#412); Linux „Bad File Descriptor / No space left on device“ = Watch-Limit, „the PollWatcher is not restricted by this limitation“; Löschung von `/a/b` nur sichtbar, wenn `/a` beobachtet wird.

## Stolperfallen notify (Zusammenfassung)
1. Windows: Überlauf (16 KiB, Burst) bleibt in 6.1.1/8.2.0 **lautlos**; erst 9.0.0-rc.5 (Pre-Release) sendet `Flag::Rescan`. Mit 6.1.1/8.x braucht jede Windows-Wurzel einen periodischen Vollscan oder einen eigenen RDCW-Pfad.
2. Linux/Android: Watch-Limit in 6.1.1 für neue Unterordner stumm; `watch(Recursive)` kann nach Fehler teilweise aktiv bleiben; Walk folgt Symlinks (Konflikt mit „Links sind geschützte Auslassungen“ – erst ab 8.0 abschaltbar, bei Poll/inotify/kqueue).
3. 7.x/8.x abonnieren `IN_OPEN` ⇒ Ereignisflut durch jeden Lesezugriff (Indexer, Virenscanner); 8.x hat keinen Schalter, 9.x `with_event_kinds(CORE | ACCESS_CLOSE)` (`EventKindMask`-Konstanten in `notify-types 2.1.0`).
4. `crossbeam-channel` ist ab 7.0 standardmäßig aus (Handler-Typ `crossbeam_channel::Sender` kompiliert dann nicht).
5. PollWatcher: Sekundengenauigkeit, keine Größenprüfung, folgt Links, `watch()` meldet fehlenden Pfad nicht; `compare_contents` = Vollhashing je Poll.
6. `watch()`/`unwatch()` nicht aus dem Handler aufrufen (Deadlock); Handler ohne Blockieren.
7. Windows-Namen können 8.3-Kurznamen sein (laut MS „unspecified“ welcher Name; siehe RDCW-Abschnitt).
8. debouncer-mini verliert `Rescan` und liefert keine Ereignisart; debouncer-full 0.3.2 braucht `add_root` (sonst kein Datei-ID-Cache) und teuren Cache-Walk.

- Erstaufruf-Zitat (MS, wörtlich): „When you first call ReadDirectoryChangesW, the system allocates a buffer to store change information. This buffer is associated with the directory handle until it is closed and its size does not change during its lifetime. Directory changes that occur between calls to this function are added to the buffer and then returned with the next call. If the buffer overflows, ReadDirectoryChangesW will still return true, but the entire contents of the buffer are discarded and the lpBytesReturned parameter will be zero, which indicates that your buffer was too small to hold all of the changes that occurred.“ – für `…ExW` identischer Wortlaut.
- Null Bytes: „If the number of bytes transferred is zero, the buffer was either too large for the system to allocate or too small to provide detailed information on all the changes that occurred in the directory or subtree. In this case, you should compute the changes by enumerating the directory or subtree.“ Zweites Überlaufsignal: „fails with ERROR_NOTIFY_ENUM_DIR when the system was unable to record all the changes to the directory. In this case, you should compute the changes by enumerating the directory or subtree.“ (`ERROR_NOTIFY_ENUM_DIR` = 1022 (0x3FE): „A notify change request is being completed and the information is not being returned in the caller's buffer. The caller now needs to enumerate the files to find the changes.“). Bei asynchronem Aufruf ist `lpBytesReturned` undefiniert – die Byte-Zahl kommt aus dem Abschluss (Completion-Routine/`GetOverlappedResult`/Port). Notify 9.0.0-rc.5 wertet beides aus: Rescan bei (Fehler 1022) oder (Fehler 0 ∧ 0 Bytes).
- Der Puffer lebt so lange wie das Handle und hat die Größe des **ersten** Aufrufs (Kernel puffert zwischen zwei Aufrufen bis zu dieser Größe) ⇒ Puffergröße einmal großzügig wählen; **DWORD-ausgerichtet** (sonst `ERROR_NOACCESS`). Satzgröße [A]: 12 Byte Kopf + 2×Namenslänge (UTF-16, ohne NUL), auf 4 Byte aufgerundet ⇒ 16 KiB fassen bei 40 Zeichen Pfad (≈ 92 Byte) rund 178 Sätze.
- **Netzwerk**: „fails with ERROR_INVALID_PARAMETER when the buffer length is greater than 64 KB and the application is monitoring a directory over the network“ (Paketgrößenlimit der Dateifreigabeprotokolle) ⇒ ≤ 65 536 Byte (Syncthing-Fork `syncthing/notify` nutzt 4096 Byte je Verzeichnis, `watcher_readdcw.go:23` [S]). „If the network redirector or the target file system does not support this operation, the function fails with ERROR_INVALID_FUNCTION.“ Unterstützt laut MS ab Windows 8/Server 2012: SMB 3.0, SMB-3.0-TFO, Scale-out-Dateiserver, CsvFS, ReFS.
- SMB-Protokoll (MS-SMB2): Anfrage `SMB2 CHANGE_NOTIFY` mit `Flags` (`SMB2_WATCH_TREE = 0x0001`), `OutputBufferLength` = „maximum number of bytes the server is allowed to return“, `CompletionFilter` (zusätzlich `FILE_NOTIFY_CHANGE_EA 0x80`, `STREAM_NAME 0x200`, `STREAM_SIZE 0x400`, `STREAM_WRITE 0x800`). Server: `OutputBufferLength > Connection.MaxTransactSize` ⇒ „SHOULD fail … STATUS_INVALID_PARAMETER“; „If the underlying object store does not support change notifications … STATUS_NOT_SUPPORTED“; je Anfrage „at most, one response“ (der Client muss neu anfragen), „the server can choose to aggregate multiple changes“; passt der Inhalt nicht in den Puffer: Antwort mit `OutputBufferLength = 0` und **`STATUS_NOTIFY_ENUM_DIR`** („a change occurred but it could not be fit within the buffer“). Erste Anfrage je Open legt `CompletionFilter`/`WATCH_TREE` fest, spätere werden ignoriert.
- Nicht gemeldet: „The function does not report changes to the specified directory itself“ (Wurzel-Löschung/-Umbenennung nur über den Elternordner; 9.x ergänzt Remove bei `ERROR_ACCESS_DENIED`). `FindFirstChangeNotification` und `ReadDirectoryChangesW` sind „mutually exclusive. - **`ReadDirectoryChangesExW`**: ab Windows 10 Version 1709 (Client) / Windows Server 2019 (Funktionsseite; Strukturseite: Server 2016), **nur NTFS** („currently supported only for the NTFS file system“). Mit `ReadDirectoryNotifyExtendedInformation` (=2) liefert es `FILE_NOTIFY_EXTENDED_INFORMATION { NextEntryOffset, Action, CreationTime: i64, LastModificationTime: i64, LastChangeTime: i64, LastAccessTime: i64, AllocatedLength: i64, FileSize: i64, FileAttributes: u32, <ReparsePointTag oder EaSize>: u32, FileId: i64, ParentFileId: i64, FileNameLength: u32, FileName }`: Attribute, Größe, Zeiten, Reparse-Tag und Datei-ID stehen im Satz, ein `stat` je Ereignis entfällt (FileSize laut MS: „the new size … or the old size if the size is unchanged“). If you need more information, you should have been remembering it.“ (R. Chen, 2026-03-06) ⇒ eigenen Index (Pfad → Typ/Größe/ID) führen. `ReadDirectoryNotifyFullInformation = 3` ist als Konstante in windows-sys 0.59 vorhanden, die zugehörige Struktur dort nicht [?].

## Offiziell dokumentiert (Administratorrechte)
- Das Journal (NTFS und ReFS; „The target volume for USN operations must be ReFS or NTFS 3.0 or later“) hält je Änderung einen Satz: Art der Änderung und Objekt, **keine** Rücknahmeinformation; mehrere gleichartige Änderungen ohne Close/Reopen ergeben nur **ein** Reason-Flag im laufenden Satz; nach dem letzten Close ein Satz mit `USN_REASON_CLOSE`. Das System „may delete old records to conserve space“, dann muss neu indiziert werden.
- MS-Doku „Using the Change Journal Identifier“: „To perform this and all other change journal operations, you must have system administrator privileges. That is, you must be a member of the Administrators group.“ Das MS-Beispiel öffnet `\\.\c:` mit `GENERIC_READ | GENERIC_WRITE`, `FILE_SHARE_READ | FILE_SHARE_WRITE`. Journal wird von Administratoren angelegt/gelöscht („Change journals are not necessarily created at startup“); fehlt es: `ERROR_JOURNAL_NOT_ACTIVE` = 1179 „The volume change journal is not active.“; Löschen läuft: `ERROR_JOURNAL_DELETE_IN_PROGRESS` = 1178; Satz weggeschnitten: `ERROR_JOURNAL_ENTRY_DELETED` = 1181 „The journal entry has been deleted from the journal.“
- Nicht unterstützt über SMB: `FSCTL_QUERY_USN_JOURNAL`/`FSCTL_READ_USN_JOURNAL` laut MS-Tabelle „SMB 3.0: No“, „CsvFS: Yes“ (Hinweis: „false positives on CsvFs pause/resume“). FAT/exFAT: die MS-Doku nennt das Journal nur für NTFS/ReFS („The volume must be NTFS“ bei `FSCTL_QUERY_USN_JOURNAL`) ⇒ dort keins [A].
- Belegte Eigenschaften für den Kaltstart: `FSCTL_QUERY_USN_JOURNAL` liefert `USN_JOURNAL_DATA` (`UsnJournalID`, `FirstUsn` = „number of first record that can be read“, `NextUsn` = „number of next record to be written“, `LowestValidUsn`, `MaxUsn`, `MaximumSize`, `AllocationDelta`). `READ_USN_JOURNAL_DATA`: „If a nonzero USN is specified that is less than the first USN in the change journal, then an error occurs and the ERROR_JOURNAL_ENTRY_DELETED error code is returned.“; passt `UsnJournalID` nicht zur aktuellen, schlägt `DeviceIoControl` fehl (neue ID über `FSCTL_QUERY_USN_JOURNAL`); „The NTFS file system can miss putting events in the change journal if the change journal is stopped and restarted or deleted and re-created. If either of these events occurs, the NTFS file system gives the journal a new identifier.“ `LowestValidUsn`: „In this case, LowestValidUsn may indicate a discontinuity in the journal, in which changes to some or all files or directories on the volume may have occurred that are not recorded in the change journal.“ Das Journal wird am Anfang gekürzt, sobald es `MaximumSize + AllocationDelta` überschreitet (Checkpoint); Standardgröße laut Blog [S] (meziantou.net, „Reading USN Journal with .NET“): „By default, the size on the system drive is about 32MB. With all the writes in the temp folder or AppData, you can quickly fill the journal“ – „you may miss changes if the journal is full“ (Vergrößern „may require admin permissions“). Ausgabepuffer: erste 8 Byte = nächste USN („Use this value to continue reading records from the end boundary forward“), danach `USN_RECORD_V2/V3`-Sätze (`RecordLength` je Satz; Name nicht NUL-terminiert, `FileNameLength` nutzen). Umbenennung = zwei Sätze (`RENAME_OLD_NAME`, `RENAME_NEW_NAME`).
- Kaltstart-Ablauf (Folgerung [A] aus den Zitaten): je Volume `(UsnJournalID, NextUsn)` persistieren; beim nächsten Start Journal abfragen; **gleiche ID und gespeicherter USN ≥ max(`FirstUsn`, `LowestValidUsn`)** ⇒ ab dem gespeicherten USN lesen, bis `NextUsn` erreicht ist (gespeichert = aktuell ⇒ nichts geändert); andernfalls (andere ID, Fehler 1181, Fehler 1179, Journal fehlt) Vollscan des Volumes bzw. Baums.

Belege: `windows-sys 0.59.0` `Win32::System::Ioctl`: `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL: u32 = 590763` (= `0x000903AB` = `CTL_CODE(FILE_DEVICE_FILE_SYSTEM, 234, METHOD_NEITHER, FILE_ANY_ACCESS)`, identisch im mingw-w64-Header); `FSCTL_QUERY_USN_JOURNAL = 590068` (`0x000900F4`, Funktion 61, `METHOD_BUFFERED`); `FSCTL_READ_USN_JOURNAL = 590011` (`0x000900BB`, Funktion 46, `METHOD_NEITHER`).
- **Ab welcher Windows-Version [A, schwach]**: der mingw-w64-Header (spiegelt die SDK-Guards) definiert die Konstante im Block `#if (_WIN32_WINNT >= _WIN32_WINNT_WIN10_RS1)` ⇒ SDK-seitig ab Windows 10 Version 1607 / Server 2016. Wann NTFS/ReFS den Code tatsächlich bedienen, ist nicht belegt; eine Microsoft-Angabe dazu gibt es nicht [?].
- Öffnen (zwei unabhängige Community-Implementierungen [S]): (a) `CreateFileW("\\\\.\\X:", FILE_TRAVERSE, FILE_SHARE_READ | FILE_SHARE_WRITE, NULL, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL)` – libUSNJournal-README: „using FILE_TRAVERSE, and FSCTL_READ_UNPRIVILEGED_USN_JOURNAL are required to get this working without admin perms. This behavior is completely undocumented“; Meziantou `ChangeJournal.Open(drive, unprivileged: true)` öffnet ebenso mit `FILE_TRAVERSE` und wählt dann `ReadUnprivilegedUsnJournal` (`0x000903AB`). (b) Pointbreak (PR #840): Verzeichnis-Handle auf die **Volume-Wurzel** `\\?\Volume{GUID}\` (aus `GetVolumePathNameW` + `GetVolumeNameForVolumeMountPointW`) mit Leserecht und `FILE_FLAG_BACKUP_SEMANTICS`, darauf `FSCTL_QUERY_USN_JOURNAL` und `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL`; Eingabe `READ_USN_JOURNAL_DATA_V1 { …, MinMajorVersion: 2, MaxMajorVersion: 2 }`, Lesepuffer 64 KiB; Doku dort: „two read-only, unprivileged calls … file names stripped by the OS“.
- Verhalten im unprivilegierten Modus [S]: nur lesen, **Dateinamen können fehlen** (Meziantou: „the file names may not be available in unprivileged mode … you can still use the file reference number“); Pointbreak filtert nur über die FRN/Eltern-FRN. Folge [A]: Pfade nur über eigenen Index `FileReferenceNumber → Pfad` (aus dem letzten Scan, z. B. `FILE_ID_INFO`) oder `OpenFileById`; für gelöschte Dateien existiert kein Pfad mehr.
- **Ob das mit einem Standardbenutzer-Token tatsächlich funktioniert, ist hier nicht belegt [?]**: Pointbreaks Windows-Läufe liefen auf GitHub-`windows-latest` (Administrator-Runner [A]); libUSNJournal/Meziantou behaupten es, ohne Versionsangabe. Vor Verwendung auf Win10/11 mit nicht erhöhtem Konto prüfen. Pointbreak-Fund: auf `windows-latest` hat Volume `D:` **kein** aktives Journal (`fsutil usn queryjournal D:` ⇒ Fehler 1179), Systemlaufwerke normalerweise schon; anlegen kann es nur ein Administrator (`fsutil usn createjournal m=<größe> a=<delta> D:`).

# Linux: inotify
Quelle: `https://man7.org/linux/man-pages/man7/inotify.7.html`, `…/man2/inotify_add_watch.2.html` (man-pages 6.19, Stand 2026-09-09), Kernelquelle `https://raw.githubusercontent.com/torvalds/linux/master/fs/notify/inotify/inotify_user.c`, Commit `92890123749b` (GitHub-API `repos/torvalds/linux/commits/92890123749b…`; Vergleich mit `v5.10`/`v5.11-rc1`), `https://raw.githubusercontent.com/torvalds/linux/master/fs/fuse/*.c`, Samba `https://www.samba.org/samba/docs/current/man-html/smb.conf.5.html` · Abgerufen: 2026-10-02

## Grenzen und Standardwerte
- `/proc/sys/fs/inotify/max_queued_events` **16384** (je Instanz; „Events in excess of this limit are dropped, but an IN_Q_OVERFLOW event is always generated“), `max_user_instances` **128** (je reale Benutzer-ID), `max_user_watches` (je reale Benutzer-ID): bis **Linux 5.10 fest 8192** (seit 2005); ab **5.11** (Commit „inotify: Increase default inotify.max_user_watches limit to 1048576“, Autor-Datum 2020-11-09, erstmals in `v5.11-rc1`) `clamp(((totalram − totalhigh) / 100 << PAGE_SHIFT) / INOTIFY_WATCH_COST, 8192, 1048576)` mit `INOTIFY_WATCH_COST = sizeof(struct inotify_inode_mark) + 2 × sizeof(struct inode)` (`inotify_user.c:46,807-817,841-843`). Commit-Text: „a 64-bit system with 128GB or more memory will likely have the maximum value of 1048576“ ⇒ rund 1,3 KB je Watch, also ≈ 8 000 Watches je GiB RAM [A] (8 GiB ≈ 65 000, 16 GiB ≈ 131 000).
- Je **Verzeichnis** ein Watch (nicht je Datei); Watch pinnt das Inode. Fehler: `ENOSPC` bei `inotify_add_watch` = „The user limit on the total number of inotify watches was reached or the kernel failed to allocate a needed resource“; `EMFILE` bei `inotify_init` = Instanzlimit [A]. Syncthing wertet `errno` 24 (EMFILE) oder 28 (ENOSPC) als „Limit erreicht“ (`lib/fs/basicfs_watch_errors_linux.go`).
- Lesen: Puffer mindestens `sizeof(struct inotify_event) + NAME_MAX + 1` (= 16 + 256), sonst seit 2.6.21 `EINVAL`; Ereignisse mit identischem (wd, mask, cookie, name) werden zusammengefasst, solange das ältere ungelesen ist („an application can't use inotify to reliably count file events“).
- Flags: `IN_ONLYDIR` (2.6.15, race-freie Verzeichnisprüfung), `IN_DONT_FOLLOW` (2.6.15), `IN_EXCL_UNLINK` (2.6.36), `IN_MASK_CREATE` (4.18; `EEXIST` statt Maskenänderung), `IN_MASK_ADD`; Ergebnis-Bits `IN_IGNORED`, `IN_ISDIR`, `IN_Q_OVERFLOW` (`wd = -1`), `IN_UNMOUNT`. Existiert für das Objekt schon ein Watch, wird dessen Deskriptor zurückgegeben und die **Maske ersetzt** (ohne `IN_MASK_ADD`).

- Minimalbeispiel (C, aus den man-Seiten):
```c
#include <sys/inotify.h>
int fd = inotify_init1(IN_CLOEXEC | IN_NONBLOCK);                 // EMFILE: max_user_instances
int wd = inotify_add_watch(fd, "/data/dir", IN_CREATE | IN_DELETE | IN_MODIFY | IN_CLOSE_WRITE | IN_MOVED_FROM | IN_MOVED_TO | IN_ATTRIB
                                           | IN_ONLYDIR | IN_DONT_FOLLOW | IN_EXCL_UNLINK);   // ENOSPC: max_user_watches; neuer Unterordner ⇒ Watch setzen, DANN readdir
char buf[4096] __attribute__((aligned(__alignof__(struct inotify_event))));
ssize_t len = read(fd, buf, sizeof buf);   // struct inotify_event { int wd; uint32_t mask, cookie, len; char name[]; }
// wd == -1 && (mask & IN_Q_OVERFLOW) ⇒ Ereignisse verloren ⇒ Rescan; IN_IGNORED ⇒ Watch ist weg (Verzeichnis gelöscht/unmount)
```

## Semantik, Rennen, Netz/FUSE
- „Inotify monitoring of directories is not recursive … additional watches must be created. This can take a significant amount time for large directory trees.“ **Rennen**: „by the time you create a watch for the new subdirectory, new files (and subdirectories) may already exist inside the subdirectory. Therefore, you may want to scan the contents of the subdirectory immediately after adding the watch (and, if desired, recursively add watches for any subdirectories that it contains).“ Muster: erst Watch setzen, **dann** Verzeichnis lesen (Unison macht es so, s. u.).
- Überlauf: „Note that the event queue can overflow. In this case, events are lost. Robust applications should handle the possibility of lost events gracefully … rebuild part or all of the application cache“; empfohlen robuster Abgleich gegen das Dateisystem („It is probably wise to do some consistency checking“).
- Nicht erfasst: Änderungen auf **Remote**-Dateisystemen („it does not catch remote events that occur on network filesystems. (Applications must fall back to polling the filesystem to catch such events.)“); Pseudo-Dateisysteme (`/proc`, `/sys`, `/dev/pts`); Zugriffe über `mmap`/`msync`/`munmap`; Quelle des Ereignisses (kein Prozess/Benutzer); Name kann bei Auswertung schon umbenannt/gelöscht sein; Mount auf einem überwachten Verzeichnis erzeugt kein Ereignis. Rename-Paarung über `cookie` (Paar `IN_MOVED_FROM`/`IN_MOVED_TO`); Verzeichnis-Umbenennungen betreffen mehrere zwischengespeicherte Pfade.
- **FUSE** [A]: Ereignisse entstehen im VFS bei Operationen **über** den Mount; die kernel-seitige FUSE-Implementierung ruft `fsnotify` nicht selbst auf (`fs/fuse/{dir,inode,dev,file,notify}.c` master: nur ein Kommentar in `dir.c:2274`; Server-Benachrichtigungen enden in `d_invalidate`/`d_delete`, `dir.c:360,1629,1656`) ⇒ Änderungen „hinter“ dem FUSE-Dämon erzeugen keine inotify-Ereignisse.
- **Samba-Server** (smb.conf): `change notify = yes` (Standard), `kernel change notify = yes` („only used when your kernel supports change notification … using the inotify interface“) ⇒ Notifies für lokale Änderungen auf dem Server hängen dort an dessen inotify-Limits.
- Kein Verlaufsjournal unter Linux: inotify/fanotify liefern nur Ereignisse **nach** dem Anlegen der Marke ⇒ Erkennung „seit dem letzten Lauf“ nur per Vollscan/Index-Vergleich [A].

Ein Aufrufbeispiel ist bewusst weggelassen (nicht gegen einen Kernel geprüft).
- **Unprivilegiert seit Linux 5.13 (Backport 5.10.220)**: „Prior to Linux 5.13 (and 5.10.220), calling fanotify_init() required the CAP_SYS_ADMIN capability.“ Beschränkungen (man `fanotify_init(2)` VERSIONS): kein `FAN_UNLIMITED_QUEUE`/`FAN_UNLIMITED_MARKS`; keine Klassen `FAN_CLASS_CONTENT`/`FAN_CLASS_PRE_CONTENT` (keine Permission-Events); „The user is required to create a group that identifies filesystem objects by file handles, for example, by providing the FAN_REPORT_FID flag“; „limited to only mark inodes … FAN_MARK_MOUNT or FAN_MARK_FILESYSTEM … not permitted“; kein `pid` in Ereignissen (außer eigene). Kernelprüfung (`fanotify_user.c:1606-1609`): `EPERM`, wenn Admin-Flags (`FANOTIFY_ADMIN_INIT_FLAGS` = Permission-Klassen, `FAN_REPORT_TID`, `FAN_REPORT_PIDFD`, `FAN_REPORT_FD_ERROR`, `FAN_UNLIMITED_QUEUE`, `FAN_UNLIMITED_MARKS`) gesetzt sind **oder** kein FID-Bit (`FANOTIFY_FID_BITS` = `FAN_REPORT_DFID_NAME_TARGET`) bzw. `FAN_REPORT_MNT` (6.14) gesetzt ist.
- **Markenarten**: nur `FAN_MARK_INODE`. `FAN_EVENT_ON_CHILD` meldet „the immediate children of marked directories … events are not generated for children of the subdirectories … To monitor complete directory trees it is necessary to mark the relevant mount or filesystem.“ ⇒ je Verzeichnis eine Marke wie bei inotify, **kein** Rekursionsvorteil. `FAN_ONDIR` nötig, um Unterordner-Einträge (mkdir/rmdir) zu bekommen. `FAN_MARK_EVICTABLE` (5.19, 5.15.154, 5.10.220): Inode nicht gepinnt, die Marke geht mit dem Inode bei Speicherdruck verloren (Folgerung [A]: für Sync nicht verwenden).
- **FID-Ereignisse**: `FAN_CREATE`, `FAN_DELETE`, `FAN_DELETE_SELF`, `FAN_MOVED_FROM`/`FAN_MOVED_TO`, `FAN_MOVE_SELF`, `FAN_ATTRIB` (alle seit 5.1, brauchen FID-Gruppe), `FAN_RENAME` (5.17, 5.15.154, 5.10.220; ein Ereignis mit bis zu 2 Infosätzen, nur auf Verzeichnis-Marken), `FAN_MODIFY`, `FAN_CLOSE_WRITE`. Gruppenflags: `FAN_REPORT_FID` (5.1), `FAN_REPORT_DIR_FID` (5.9), `FAN_REPORT_NAME` (5.9, nur mit `DIR_FID`), `FAN_REPORT_DFID_NAME` = `DIR_FID|NAME` (liefert Verzeichnis-Handle + Name), `FAN_REPORT_TARGET_FID` (5.17, 5.15.154, 5.10.220; Kind-Handle bei Dirent-Ereignissen), `FAN_REPORT_DFID_NAME_TARGET` = `DFID_NAME|FID|TARGET_FID`.
- Limits (`/proc/sys/fs/fanotify/…`, Kernel master `fanotify_user.c:30-43,2166-2199`; die man-Seite schreibt `max_user_group`, der Kernel `max_user_groups`): `max_queued_events` 16384 (vor 5.13 fest), `max_user_groups` 128 (vor 5.13 fest), `max_user_marks` RAM-skaliert `clamp(1 % RAM / INODE_MARK_COST, 8192, 1048576)` (vor 5.13: fest 8192 je **Gruppe**); Überlauf ⇒ `FAN_Q_OVERFLOW`; Marken-Limit ⇒ `ENOSPC`.
- Grenzen: `FAN_REPORT_FID`-Gruppen und FUSE: `ENODEV` bei Dateisystem mit Null-`fsid` („e.g., fuse(4)“; ab 6.8 auch für Mount-/FS-Marken), `EOPNOTSUPP` wenn das Dateisystem keine Datei-Handles kodiert (Test: `name_to_handle_at(…, AT_HANDLE_FID)` ab 6.5), `EXDEV` bei btrfs-Subvolumes. `open_by_handle_at(2)` verlangt „CAP_DAC_READ_SEARCH“ ⇒ unprivilegiert lassen sich gemeldete Handles nicht öffnen; Zuordnung Handle → Pfad nur über eigene Tabelle (`name_to_handle_at` der markierten Verzeichnisse) [A, nicht verifiziert]. `fanotify(7)` „Limitations and caveats“: „it does not catch remote events that occur on network filesystems“; „Fanotify monitoring of directories is not recursive … additional marks must be created … This approach is racy, because it can lose events that occurred inside the newly created subdirectory, before a mark is added“ – race-freie Baumüberwachung gibt es nur mit Mount-/Filesystem-Marken (Root); `mmap`-Zugriffe werden nicht gemeldet.
- **Android**: `fanotify_init`/`fanotify_mark` stehen weder in bionic `libc/SYSCALLS.TXT` noch in `SECCOMP_ALLOWLIST_{COMMON,APP}.TXT`; die App-seccomp-Maske ist `(SYSCALLS.TXT − Blocklist) ∪ Allowlist` (`libc/tools/genseccomp.py:59-64`, „applied only to zygote spawned processes“) ⇒ in App-Prozessen gesperrt [A].
- Folgerung [A]: Für einen Sync-Client ohne Root bringt fanotify gegenüber inotify nur Datei-Handles/Namen und `FAN_RENAME`, keine Rekursion, keine Verlaufsdaten, ab 5.13, nicht auf Android, nicht auf FUSE.

## FileObserver (Quelltext `main`; `FileObserver(File)`/`(List<File>)` ab API 29)
```java

    // Konstanten: ACCESS=0x1 MODIFY=0x2 ATTRIB=0x4 CLOSE_WRITE=0x8 CLOSE_NOWRITE=0x10 OPEN=0x20 MOVED_FROM=0x40 MOVED_TO=0x80 CREATE=0x100 DELETE=0x200 DELETE_SELF=0x400 MOVE_SELF=0x800 ALL_EVENTS=0xFFF
}
```
(API 29: Tags `android-9.0.0_r1` – nur `String`-Konstruktoren; `android-10.0.0_r1` – `File`/`List<File>`.)
- Javadoc: „Monitors files (using inotify) to fire an event after files are accessed or changed by any process on the device (including this one).“; „If a directory is monitored, events will be triggered for all files and subdirectories inside the monitored directory“ (inotify-bedingt gemeint: unmittelbare Kinder; **keine Rekursion** eingebaut); „If a FileObserver is garbage collected, it will stop sending events“ (`finalize()` ruft `stopWatching()`); Handler „must not throw exceptions“.
- Implementierung [A, aus Quelltext]: **eine** inotify-Instanz je Prozess (`inotify_init1(IN_CLOEXEC)`, statischer `ObserverThread`), Lesepuffer 512 Byte, ein Thread für alle Observer des Prozesses (langsamer `onEvent` verzögert alle); bei einem Lesefehler außer `EINTR` beendet sich die Lese-Schleife dauerhaft („got a short event“, `android_util_FileObserver.cpp:63-70`) und **alle** FileObserver des Prozesses sind still. `startWatching` ruft `inotify_add_watch(fd, path, mask)` je Pfad und speichert nur Rückgaben ≥ 0 – **Fehler (ENOSPC, EACCES, ENOENT) bleiben unbemerkt**, `startWatching()` hat keinen Rückgabewert. `IN_Q_OVERFLOW` (wd = −1) findet keinen Observer ⇒ **Überlauf wird verworfen**, nie gemeldet. Das rohe `mask` geht an `onEvent`: Bits wie `IN_ISDIR` (0x40000000), `IN_IGNORED` (0x8000), `IN_UNMOUNT` (0x2000) können gesetzt sein ⇒ mit `FileObserver.ALL_EVENTS` maskieren. Zwei Observer auf demselben Inode im selben Prozess teilen sich den Watch-Descriptor: Maske wird ersetzt (kein `IN_MASK_ADD`), `mRealObservers.put(wfd, …)` überschreibt den ersten Observer.
- Minimalbeispiel (Kotlin, API 29+): `val o = object : FileObserver(File(dir), FileObserver.CREATE or FileObserver.DELETE or FileObserver.MOVED_FROM or FileObserver.MOVED_TO or FileObserver.CLOSE_WRITE or FileObserver.DELETE_SELF or FileObserver.MOVE_SELF) { override fun onEvent(event: Int, path: String?) { val e = event and FileObserver.ALL_EVENTS; … } }; o.startWatching()` – Referenz im Aufrufer halten, je Unterverzeichnis ein eigener Observer, bei jedem `CREATE`/`MOVED_TO` eines Verzeichnisses sofort Observer anlegen **und** Verzeichnis nachlesen.

## Wer sieht welche Änderungen auf `/storage/emulated/0` (FUSE, Passthrough)
- Android ≥ 11 (AOSP-Doku „Scoped storage“): „SDCardFS is deprecated and MediaProvider becomes the file system handler (for FUSE) for external storage, making the file system on external storage and the MediaProvider database consistent.“ (Android ≤ 10: SDCardFS). Normale Apps (auch mit `MANAGE_EXTERNAL_STORAGE`) erhalten Mountmodus `MOUNT_EXTERNAL_DEFAULT` (bzw. `INSTALLER`): `/storage` ist Bind-Mount von `/mnt/user/<user>` = **FUSE** (`Zygote.cpp:867-879`, `StorageManagerService.getMountModeInternal`); nur Prozesse mit der MediaProvider-UID („isExternalStorageService“) bekommen `MOUNT_EXTERNAL_PASS_THROUGH` = `/mnt/pass_through/<user>` = Bind-Mount des **Lower-Dateisystems** (`vold Utils.cpp MountUserFuse`: `BindMount(absolute_lower_path, pass_through_path)`; FUSE-Mount mit `allow_other`, `MS_NOSUID|MS_NODEV|MS_NOEXEC|MS_NOATIME|MS_LAZYTIME`). DownloadProvider/ExternalStorageProvider: `ANDROID_WRITABLE`.
- Folge [A, aus Quelltext, **nicht am Gerät gemessen**]: `inotify`/`FileObserver` einer App hängt an FUSE-Inodes. VFS-Ereignisse entstehen für Operationen **über** den FUSE-Mount; Operationen anderer Apps auf `/sdcard` laufen über denselben FUSE-Mount ⇒ werden gemeldet. FUSE-Passthrough (AOSP-Doku, Seitenstand 2026-10-02: „FUSE passthrough is supported in the android12-5.4, android12-5.10, and android-mainline (testing only) kernels“ – neuere GKI-Zweige nicht aufgeführt; Property `persist.sys.fuse.passthrough.enable=true`; „Most file access permissions are checked at file open time, with additional permissions checks occurring when reading from and writing to that file“) leitet nur Lese-/Schreibzugriffe der geöffneten FUSE-Datei am Dämon vorbei auf die Lower-Datei; ob dabei `IN_MODIFY` am FUSE-Inode ausgelöst wird, ist hier nicht am Kernelcode des Passthrough-Pfads geprüft [?] (erwartbar ja, weil das äußere `vfs_write` auf der FUSE-Datei läuft).
- **Nicht gemeldet** [A]: Änderungen, die MediaProvider selbst im Lower-Dateisystem ausführt. `openFileAndEnforcePathPermissionsHelper` (`MediaProvider.java:9909-10075`) gibt Apps bei `ContentResolver.openFileDescriptor/openOutputStream` standardmäßig einen **Lower-FS-Deskriptor** (`FileUtils.openSafely(file, modeBits)`; Log „Open with lower FS for …“); nur bei Redaktion/Transcoding oder bereits auf dem FUSE-Mount geöffneter Datei (`shouldOpenWithFuse`) ein FUSE-Deskriptor. Nach dem Schließen eines Schreib-Deskriptors (nicht bei `IS_PENDING`): `invalidateFuseDentry(file)` + `scanFileAsMediaProvider(file)`. Auch `renameInLowerFsAndInvalidateFuseDentry` (`Os.rename` im Lower-FS, dann `FuseDaemon.invalidateFuseDentryCache`, `:2123-2128`). Solche Schreib-/Umbenennvorgänge erzeugen keine FUSE-Inode-Ereignisse; das verlässliche Signal ist dort MediaStore (nach dem Scan). `FuseDaemon.cpp:2269` meldet FUSE-`create` per `OnFileCreated(child_path)` an MediaProvider.
- Zugriff: `inotify_add_watch` braucht Lesezugriff auf den Pfad („the caller must have read permission“); fremde `Android/data`/`Android/obb` sind ohne Sonderwege (Shizuku o. ä., siehe `android-data-obb-access.md`) nicht erreichbar; Scoped-Storage-Sicht je App (nur eigene Dateien/Medien ohne `MANAGE_EXTERNAL_STORAGE`). SELinux-`watch`-Berechtigung der App-Domänen auf `fuse`-Dateien nicht geprüft [?].
- Syncthing-Forum [S] (2021-03-13, Maintainer-Vermutung, nicht belegt): Android 11 leite „native filesystem calls“ durch das Storage Access Framework, das „hardly implements inotify“; einzelne Nutzer lösten Watcher-Fehler mit `/sdcard/…` statt `/storage/emulated/0/…`.

## Limits der Kernel (Android)
- `max_user_watches` je reale UID (= je App [A]): GKI `android12-5.10` **fest 8192**, `android13-5.15`, `android14-6.1`, `android15-6.6`, `android16-6.12` RAM-skaliert wie Linux ≥ 5.11 (`kernel/common`, `inotify_user.c`); `init.rc` setzt keinen eigenen Wert (grep `inotify` ohne Treffer); OEM-Kernel/-sysctl können abweichen [?]. `max_user_instances` 128, `max_queued_events` 16384 (Kernel-Standard).
- Hintergrund (AOSP-Doku; Doze/FGS-Details in `android-background-reachability.md`): Cached-Apps-Freezer „Android 11 (API level 30) or higher supports the cached apps freezer“ (aktivierbar „using a system configuration flag or a developer option“); „In Android 14 (API level 34) and higher … App processes in the cached state are frozen 10 seconds after entering the cached state. The system immediately unfreezes a frozen app process during a lifecycle event“ (u. a. Intent, Start eines Job-Service, Activity); „When an app process is frozen, all of its threads are suspended and can't perform CPU work until unfrozen“ ⇒ Ereignisse sammeln sich in der Kernel-Queue (16384) und gehen bei Überlauf verloren, **ohne** dass `FileObserver` es meldet. Der Prozess kann jederzeit beendet werden ⇒ Watcher sind nie Zustandsquelle, nur Beschleuniger; beim Start Abgleich per Scan/MediaStore.

## MediaStore-Generationen (API 30) – „Was hat sich seit dem letzten Lauf geändert“
- `MediaStore.getGeneration(Context, String volumeName): long` (nur `Context`-Variante öffentlich), `MediaColumns.GENERATION_ADDED = "generation_added"`, `MediaColumns.GENERATION_MODIFIED = "generation_modified"`; `MediaStore.getVersion(Context[, String volumeName]): String`. Quelle Javadoc: „Generation numbers are monotonically increasing over time, and can be safely arithmetically compared. Detecting media changes using generation numbers is more robust than using DATE_ADDED or DATE_MODIFIED, since those values may change in unexpected ways when apps use File#setLastModified(long) or when the system clock is set incorrectly. … before comparing these detailed generation values, you should first confirm that the overall version hasn't changed by checking getVersion(Context, String), since that indicates when a more radical change has occurred. If the overall version changes, you should assume that generation numbers have been reset and perform a full synchronization pass.“ In `android-11.0.0_r1` vorhanden, in `android-10.0.0_r1` nicht (dort nur `getVersion`).
- Volumes: `MediaStore.VOLUME_EXTERNAL = "external"` (zusammengeführte Sicht aller angeschlossenen Geräte; „you can't insert new content into this volume“), `VOLUME_EXTERNAL_PRIMARY = "external_primary"`, `MediaStore.getExternalVolumeNames(Context): Set<String>` = je gemountetes Speichergerät (inkl. SD-Karte) `StorageVolume.getMediaStoreVolumeName()` (nur Zustand `MEDIA_MOUNTED`/`MEDIA_MOUNTED_READ_ONLY`). `MediaStore.Files.getContentUri(String volumeName)`; `Files.EXTERNAL_CONTENT_URI = getContentUri("external")`.
- Grenzen [A/?]: erfasst nur, was MediaProvider indiziert und der App sichtbar ist (Berechtigungen/Scoped Storage); der Scan-Zeitpunkt nach Schreibzugriffen ist nicht dokumentiert; Zähler pro Volume.

## SD-Karten (`/storage/XXXX-XXXX`)

## Syncthing: Watcher + periodischer Vollscan
- Doku (`syncing.rst`): „There are two methods how Syncthing detects changes: By regular full scans and by notifications received from the filesystem ('watcher'). By default the watcher is enabled and full scans are done once per hour. … the actual scan interval is a random time between 3/4 and 5/4 of the given scan interval. Even with watcher enabled it is advised to keep regular full scans enabled, as it is possible that some changes aren't picked up by it.“; „It accumulates changes for 10s (adjustable by fsWatcherDelayS) and deleted files are further delayed for 1min.“
- Standards (`folderconfiguration.go:57-60`): `rescanIntervalS = 3600`, `fsWatcherEnabled = true`, `fsWatcherDelayS = 10`, `fsWatcherTimeoutS` leer/0 ⇒ berechnet (`notifyTimeout`): Delay < 10 s ⇒ 6× Delay; 10 ≤ Delay < 60 ⇒ 60 s; ≥ 60 s ⇒ gleich Delay. `fsWatcherDelayS ≤ 0` schaltet den Watcher ab (`:300-301`). `rescanIntervalS = 0` erlaubt externe Auslöser (`config.rst`).
- Aggregation (`aggregator.go`): `maxFiles = 512` ausstehende Pfade ⇒ danach „Scan entire folder“; `maxFilesPerDir = 128` je Verzeichnis ⇒ stattdessen das Elternverzeichnis scannen; Löschungen werden zuletzt/zeitversetzt gescannt (`isOld`, `delayRem`); Pfade, die Syncthing gerade selbst schreibt (`ItemStarted`/`ItemFinished`), werden ignoriert („Skipping path we modified“).
- Überlauf (`basicfs_watch.go`): `backendBuffer = 500`; ist der Kanal voll (`len(backendChan) == backendBuffer`), wird er geleert und ein Ereignis für die **ganze Wurzel** erzeugt („When next scheduling a scan, do it on the entire folder as events have been lost“). Ignorierte Pfade (`.stignore`, `CanSkipDir`) werden gar nicht beobachtet (spart Watches). Event-Masken: inotify `InCreate|InMovedTo|InDelete|InDeleteSelf|InModify|InMovedFrom|InMoveSelf|InAttrib` (kein `CLOSE_WRITE`, kein `OPEN`); Windows `FileNotifyChange{FileName,DirName,Size,Creation,LastWrite}` (+ `Attributes`, wenn Rechte nicht ignoriert werden).
- Fehler/Limit (`folder.go:1098-1180`): Start-Fehler des Watchers (z. B. inotify-Limit: Meldung „failed to set up inotify handler. Please increase inotify limits, see https://docs.syncthing.net/users/faq.html#inotify-limits“) ⇒ Warnung „Failed to start filesystem watcher“, **sofort ein Vollscan** (`scanOnWatchErr` ⇒ `DelayScan(0)`), Wiederholung nach 1 min, Verdopplung bis 60 min; Watcher-Fehler im Betrieb ⇒ Neustart-Versuch nach `pause − Laufzeit`. FAQ (`usage.rst`): „Linux typically restricts the number of watches per user (usually 8192)“, Empfehlung `fs.inotify.max_user_watches=204800`. Maintainer (Forum 2020-12-22 [S]): Fehler „has nothing to do with being root or not and it is not specific to android“; Warnung nur durch höheres Limit oder Abschalten des Watchers wegzubekommen.
- Windows-Backend (Fork `syncthing/notify`, `watcher_readdcw.go`): `readBufferSize = 4096` Byte **je Verzeichnis**; Kommentar: bei Netzwerk-Überwachung höchstens 64 KB; in `loop()` wird ein Abschluss mit `n == 0` ohne Auswertung übersprungen (`else if n != 0 { r.loopevent(n, overEx) }`, „TODO: error handling“) ⇒ auch Syncthing verliert RDCW-Überläufe lautlos und heilt sie nur durch den periodischen Vollscan [A].
- Android: offizielle App `syncthing/syncthing-android` **archiviert** (letzter Push 2024-12-03); Fortführung als Syncthing-Fork (`researchxxl/syncthing-android`, Push 2026-10-01); Go-Kern nutzt dieselbe `syncthing/notify`-inotify-Anbindung. Forum [S]: Limit 8192 und Android-11-Probleme (siehe Android-Abschnitt); Aussagen der Maintainer zur Android-Sicht auf inotify sind Vermutungen.

## Unison, rclone bisync
- Unison: `-repeat watch` = „Unison relies on an external file monitoring process to synchronize whenever a change happens“, `-repeat watch+3600` „will react to changes immediately and additionally do a full scan every hour“ (`uicommon.ml:130-143`). Das Monitor-Programm (`unison-fsmonitor`, Zeilenprotokoll `START/DIR/LINK/DONE/CHANGES/WAIT/RESET`, `fswatch.ml`) bekommt `DIR <path>` **bevor** Unison das Verzeichnis scannt und muss erst nach dem Beginn der Überwachung mit `OK` antworten ⇒ **erst Watch, dann Scan** (löst das inotify-Rennen bei neuen Ordnern); `CHANGES hash` liefert geänderte Pfade seit der letzten Abfrage („`RECURSIVE path`“).
- rclone bisync: **kein Watcher**. Vergleich von Listings (`--compare size,modtime,checksum`, Listing-Dateien je Lauf, `--resync` initial/nach Änderung von `--compare`), Betrieb über Planer: „On Linux or Mac, consider setting up a crontab entry. bisync can safely run in concurrent cron jobs thanks to lock files it maintains.“ (`bisync`-Doku). Kein Vorbild für Echtzeit, nur für den Abgleichsteil.

# Offene Punkte
1. **Windows-Mindestversion/-Rechte von `FSCTL_READ_UNPRIVILEGED_USN_JOURNAL`**: nur aus mingw-w64-Header-Guard (`WIN10_RS1`) und Community-Code; Verhalten mit nicht erhöhtem Standardbenutzer-Token auf Win10/11 nicht belegt (Pointbreak-CI vermutlich als Administrator). Standardgröße (≈ 32 MB auf dem Systemlaufwerk) nur aus einem Blog [S], von Microsoft nicht dokumentiert; Sekundärvolumes können ohne Journal sein (Pointbreak-Beobachtung [S]).
2. `ReadDirectoryChangesW` mit `bWatchSubtree` über Junctions/Symlinks/Mount-Punkte: Microsoft-Doku schweigt; Verhalten auf FAT/exFAT/UDF/WebDAV/NFS-Client nicht dokumentiert (nur `ERROR_INVALID_FUNCTION`, wenn Redirector/Dateisystem es nicht unterstützt).
3. SMB: ob Änderungen zwischen Antwort und der nächsten `CHANGE_NOTIFY`-Anfrage serverseitig gepuffert werden, steht nicht im Spec; Puffergrenze und Verhalten von Samba/NAS-Geräten nicht gemessen.
4. `FILE_NOTIFY_FULL_INFORMATION`/`ReadDirectoryNotifyFullInformation` (=3): in windows-sys 0.59 nur die Konstante; Struktur/Doku nicht gefunden.
5. notify 9.0.0-rc.5 ist Pre-Release (API und Verhalten können sich ändern); Entscheidung 6.1.1 → 8.2.0 → 9.x offen: 8.x bringt die `IN_OPEN`-Flut ohne Abschalter und keinen Windows-Rescan; 9.x bringt Rescan und `EventKindMask`, aber MSRV 1.88 und geänderte Event-Pfade. Kosten des `FileIdMap`-Walks (debouncer-full 0.3.2) und Verhalten von 8.2.0 auf Android nicht gemessen.
6. Android: FUSE-/Lower-FS-Sichtbarkeit von Ereignissen (Passthrough-Schreibzugriffe, `FUSE_NOTIFY_*`, SELinux-`watch`-Recht der App-Domänen, OEM-Kernelwerte, API 36/37-Änderungen) aus AOSP-Quelltext abgeleitet, auf keinem Gerät gemessen; MediaStore-Abdeckung für Nicht-Medien-Dateien ohne `MANAGE_EXTERNAL_STORAGE` und MediaProvider-Scan-Latenz nicht dokumentiert.
7. Linux fanotify: unprivilegierte Auflösung von Datei-Handles (`name_to_handle_at`-Tabelle) nicht verifiziert; inotify-Verhalten auf FUSE nur aus Kernelcode abgeleitet.
8. Syncthing-Android-Aussagen stammen aus Forenbeiträgen (Vermutungen); für den Android-Teil gibt es keine belegte Herstellerdoku zu inotify auf `/storage/emulated`.
