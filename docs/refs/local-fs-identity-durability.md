## GetVolumeInformationByHandleW / GetVolumeInformationW
```rust
// windows-sys 0.59.0, Win32::Storage::FileSystem (Feature Win32_Storage_FileSystem; kernel32.dll)
GetVolumeInformationByHandleW(hfile: HANDLE, lpvolumenamebuffer: PWSTR, nvolumenamesize: u32, lpvolumeserialnumber: *mut u32,
    lpmaximumcomponentlength: *mut u32, lpfilesystemflags: *mut u32, lpfilesystemnamebuffer: PWSTR, nfilesystemnamesize: u32) -> BOOL
GetVolumeInformationW(lprootpathname: PCWSTR, /* Rest wie oben */) -> BOOL
```
- Puffer: Volumename und Dateisystemname je höchstens `MAX_PATH+1` WCHAR; die Größenangabe wird ignoriert, wenn der Puffer fehlt (alle Ausgaben außer `hFile` optional). Rückgabe 0 = „not all of the requested information is retrieved“ ⇒ `GetLastError()`.
- `lpVolumeSerialNumber` (32 Bit): „the volume serial number that the operating system assigns when a hard disk is formatted“ – nicht die Hersteller-Seriennummer (die gibt es nur über WMI `Win32_PhysicalMedia.SerialNumber`). Eine Eindeutigkeitsgarantie nennt die Doku nicht; ein zufällig vergebener 32-Bit-Wert kann bei geklonten oder zufällig gleichen Datenträgern kollidieren [A].
- `lpFileSystemFlags` (Doku-Tabelle der Win32-Seite; die Konstanten liegen in windows-sys **nicht** in `Storage::FileSystem`, sondern in `Win32::System::SystemServices`, Feature `Win32_System_SystemServices`): `FILE_CASE_SENSITIVE_SEARCH` 0x1 · `FILE_CASE_PRESERVED_NAMES` 0x2 · `FILE_UNICODE_ON_DISK` 0x4 · `FILE_PERSISTENT_ACLS` 0x8 · `FILE_FILE_COMPRESSION` 0x10 · `FILE_VOLUME_QUOTAS` 0x20 · `FILE_SUPPORTS_SPARSE_FILES` 0x40 · `FILE_SUPPORTS_REPARSE_POINTS` 0x80 · `FILE_VOLUME_IS_COMPRESSED` 0x8000 · `FILE_SUPPORTS_OBJECT_IDS` 0x10000 · `FILE_SUPPORTS_ENCRYPTION` 0x20000 · `FILE_NAMED_STREAMS` 0x40000 · `FILE_READ_ONLY_VOLUME` 0x80000 · `FILE_SEQUENTIAL_WRITE_ONCE` 0x100000 · `FILE_SUPPORTS_TRANSACTIONS` 0x200000 · `FILE_SUPPORTS_HARD_LINKS` 0x400000 · `FILE_SUPPORTS_EXTENDED_ATTRIBUTES` 0x800000 · `FILE_SUPPORTS_OPEN_BY_FILE_ID` 0x1000000 · `FILE_SUPPORTS_USN_JOURNAL` 0x2000000 · `FILE_SUPPORTS_BLOCK_REFCOUNTING` 0x8000000. Zusätzlich in der WDK-Doku `FILE_FS_ATTRIBUTE_INFORMATION` (gleiche Bits, vom Win32-Seitentext nicht gelistet): `FILE_SUPPORTS_REMOTE_STORAGE` 0x100, **`FILE_SUPPORTS_POSIX_UNLINK_RENAME` 0x400** („The file system supports POSIX-style delete and rename operations“), `FILE_SUPPORTS_INTEGRITY_STREAMS` 0x4000000, `FILE_SUPPORTS_SPARSE_VDL` 0x10000000, `FILE_DAX_VOLUME` 0x20000000, `FILE_SUPPORTS_GHOSTING` 0x40000000. windows-sys 0.59 kennt `FILE_SUPPORTS_POSIX_UNLINK_RENAME = 1024` in `SystemServices`.
- `GetVolumeInformationW`: `lpRootPathName` mit **abschließendem Backslash** („specify \\MyServer\MyShare as "\\MyServer\MyShare\", or the C drive as "C:\""); `NULL` = Wurzel des aktuellen Verzeichnisses; bei leerem Wechselmedium (Diskette/CD) erscheint ein Systemdialog, „To prevent … call the SetErrorMode function with SEM_FAILCRITICALERRORS“ (siehe Abschnitt `SetThreadErrorMode`); zeigt der Pfad auf einen Symlink, kommen die Daten des Ziels.
- Remarks-Tabelle (Windows 8/Server 2012) für beide Funktionen: SMB 3.0 **No**, TFO No, SO No, CsvFS Yes, ReFS Yes; „SMB does not support volume management functions.“ Gleichzeitig nennt dieselbe Seite einen UNC-Share-Stamm als gültige Wurzel für `GetVolumeInformationW` – das Verhalten über SMB ist deshalb am Zielsystem zu prüfen [?].
- Das Handle für die `…ByHandleW`-Variante: Doku nur „A handle to the file“. Praxis zum Öffnen mit Zugriff 0 [S]: sysinfo öffnet Volume-Stämme mit `CreateFileW(pfad, 0, FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE, NULL, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS, NULL)` und liest daraus per `GetFileInformationByHandle` die Seriennummer (`src/windows/disk.rs:369-392`). Ob `GetVolumeInformationByHandleW` mit einem solchen Null-Zugriff-Handle läuft, ist hier nicht belegt [?].
- Kernel-Gegenstück (WDK `NtQueryVolumeInformationFile`): `FileFsVolumeInformation` = „volume label, serial number, and creation time“, `FileFsAttributeInformation` = `FILE_FS_ATTRIBUTE_INFORMATION`; „returns zero in any member … that is not supported by the file system“ (nicht unterstützte Felder sind 0, kein Fehler).

## GetFileInformationByHandleEx(FileIdInfo) – FILE_ID_INFO, Dateikennung
```rust
// windows-sys 0.59.0, Win32::Storage::FileSystem
GetFileInformationByHandleEx(hfile: HANDLE, fileinformationclass: FILE_INFO_BY_HANDLE_CLASS, lpfileinformation: *mut c_void, dwbuffersize: u32) -> BOOL
pub struct FILE_ID_INFO { pub VolumeSerialNumber: u64, pub FileId: FILE_ID_128 }   // FILE_ID_128 { pub Identifier: [u8; 16] }
pub const FileIdInfo: FILE_INFO_BY_HANDLE_CLASS = 18;  // FileRenameInfo = 3, FileStorageInfo = 16, FileIdExtdDirectoryInfo = 19, FileRenameInfoEx = 22, FileCaseSensitiveInfo = 23
```
- Doku `FILE_ID_INFO`: „The 128-bit file identifier for the file. The file identifier and the volume serial number uniquely identify a file on a single computer. To determine whether two open handles represent the same file, combine the identifier and the volume serial number for each file and compare them.“ `FileIdInfo` „is not supported before Windows 8 and Windows Server 2012“. Remarks-Tabelle von `GetFileInformationByHandleEx`: SMB 3.0 **Yes**, TFO Yes, SO Yes, ReFS Yes.
- Vorgänger `GetFileInformationByHandle` → `BY_HANDLE_FILE_INFORMATION` (`dwVolumeSerialNumber: u32`, `nFileIndexHigh/Low` = 64 Bit): „File IDs are not guaranteed to be unique over time, because file systems are free to reuse them. In some cases, the file ID for a file can change over time.“ FAT: ID aus erstem Cluster des Elternverzeichnisses + Byte-Offset des Eintrags, „Renaming a file in the FAT file system can also change the file ID, but only if the new file name is longer than the old one.“ NTFS: „a file keeps the same file ID until it is deleted“; `ReplaceFile` behält die ID der **Ersatz**datei. ReFS: 128-Bit-IDs, „The 64-bit identifier in this structure is not guaranteed to be unique on ReFS.“
- Projektbezug: `same-file 1.0.6` (direkte Abhängigkeit) bildet den Schlüssel aus `volume_serial_number` (u32) + `file_index` (u64) von `GetFileInformationByHandle` (`src/win.rs:134-145`); der Dateikopf (`:14-50`) benennt die ReFS-Lücke („requires a distinct syscall to get `FILE_ID_INFO` … It seems straight-forward enough to modify this code to use `FILE_ID_INFO` when available“) und mildert sie nur durch zusätzlichen Größenvergleich. Rust std 1.99.0 füllt `volume_serial_number`/`file_index` ebenfalls aus `GetFileInformationByHandle` (`sys/fs/windows.rs:523-553`); die öffentlichen Zugriffe (`MetadataExt::volume_serial_number`/`file_index`) sind laut sysinfo-Kommentar noch unstable [S].
- Folgerung [A]: Wurzel-Identität = Handle auf die Wurzel (`CreateFileW(root, 0, FILE_SHARE_READ|WRITE|DELETE, NULL, OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS, NULL)`) → `FILE_ID_INFO` (64-Bit-Seriennummer + Datei-ID der Wurzel) **plus** Dateisystemname/-Flags **plus** Volume-GUID-Pfad (wenn vorhanden); die 32-Bit-Nummer allein genügt nicht. Datei-IDs nur für die Dauer eines Laufs und nur zusammen mit der Volume-Seriennummer vergleichen.

## Volume-GUID-Pfade, Mount-Punkte, Volume-Aufzählung
```rust
// windows-sys 0.59.0, Win32::Storage::FileSystem
GetVolumePathNameW(lpszfilename: PCWSTR, lpszvolumepathname: PWSTR, cchbufferlength: u32) -> BOOL
GetVolumeNameForVolumeMountPointW(lpszvolumemountpoint: PCWSTR, lpszvolumename: PWSTR, cchbufferlength: u32) -> BOOL
GetVolumePathNamesForVolumeNameW(lpszvolumename: PCWSTR, lpszvolumepathnames: PWSTR, cchbufferlength: u32, lpcchreturnlength: *mut u32) -> BOOL
FindFirstVolumeW(lpszvolumename: PWSTR, cchbufferlength: u32) -> HANDLE   // FindNextVolumeW(hfindvolume, lpszvolumename, cchbufferlength) -> BOOL; FindVolumeClose(hfindvolume) -> BOOL
```
- `GetVolumePathNameW`: liefert den **Mount-Punkt** (Stamm des Volumes), unter dem der Pfad liegt („the longest prefix that represents a volume“); relative Namen ohne Laufwerk ⇒ Systemlaufwerk (auch bei ungültigem Namen ohne Volume-Angabe); NT-Namensraum-Pfade (`\DosDevices\H:`, `\Device\HardDiskVolume6`) werden **nicht** verstanden (Ergebnis = Systemlaufwerk); folgt Junctions (bei mehreren die ganze Kette, „returns the volume to which the last junction point in the chain refers“); bei Netzfreigaben „the shortest path for which GetDriveType returns DRIVE_REMOTE“; ungültige **nachgestellte** Elemente werden bei lokalen Pfaden ignoriert (`G:\invalid` ⇒ `G:\`), bei Remote-Pfaden macht ein ungültiger Teil den ganzen Pfad ungültig (Fehler 123); Sonderfall: ist der Ausgabepuffer genau ein Zeichen zu kurz, fehlt der abschließende Backslash. Remarks-Tabelle: SMB 3.0 No, ReFS Yes.
- `GetVolumeNameForVolumeMountPointW`: Eingabe (Laufwerksbuchstabe `X:\`, Mount-Ordner oder GUID-Pfad) **muss auf `\` enden**; Ausgabe `\\?\Volume{GUID}\` (Puffer: „A reasonable size … is 50 characters“); „If there is more than one volume GUID path for the volume, only the first one in the mount manager's cache is returned.“ ReFS: **No** („Mount points aren't supported by ReFS volumes.“), SMB No.
- `GetVolumePathNamesForVolumeNameW`: Liste (mehrere NUL-terminierte Strings, zusätzlich NUL beendet) aller Laufwerksbuchstaben/Mount-Ordner des Volumes; `ERROR_MORE_DATA` + benötigte Länge in `lpcchReturnLength`; die Liste kann leer sein (Volume ohne Mount-Punkt) [S: sysinfo überspringt solche Volumes, `src/windows/disk.rs:312-316`].
- Doku „Naming a Volume“: ein Volume braucht weder Laufwerksbuchstaben noch Label; zwei Volumes können dasselbe Label haben; Buchstaben ändern sich; „a volume can have more than one volume GUID path“; „The operating system assigns a volume GUID path to a volume when the volume is first installed and when the volume is formatted.“ Alle Volume-/Mount-Funktionen mit GUID-Pfad verlangen den abschließenden Backslash; `CreateFile` dagegen öffnet `\\?\Volume{GUID}` (ohne Backslash) als **Volume** und `\\?\Volume{GUID}\` als **Wurzelverzeichnis des Dateisystems** (Details im Abschnitt Zugriffsrechte).
- `FindFirstVolumeW`: Rückgabe `INVALID_HANDLE_VALUE` bei Fehler; „You should not assume any correlation between the order of the volumes … and drive letters“; SMB No.
- Stolperfalle [A]: der Volume-GUID-Pfad ist **nicht** der Geräteschnittstellen-Pfad (`\\?\STORAGE#Volume#…#{53f5630d-…}`), den `CM_Register_Notification` liefert; die Zuordnung läuft über Neuaufzählung (`FindFirstVolumeW`/`GetVolumePathNamesForVolumeNameW`).

## Groß-/Kleinschreibung: Volume-Flag und Verzeichnis-Flag
- Volume: `FILE_CASE_SENSITIVE_SEARCH` (0x1) in `lpFileSystemFlags`. Vergleichstabelle (Microsoft, `filesystem-functionality-comparison`): NTFS „Yes (option)“, exFAT No, UDF Yes, FAT32 No; case-preserving überall Yes; Hard Links: NTFS Yes, UDF Yes, **exFAT No, FAT32 No**; Alternate Data Streams/Named Streams/Extended Attributes/Sparse/Soft Links/Mount Points: nur NTFS (UDF teilweise), **nicht** exFAT/FAT32; FAT32: maximale Dateigröße 4 GiB, Namen 255 Zeichen.
- NTFS **je Verzeichnis**: „Support for per-directory case sensitivity began in Windows 10, build 17107“; neue Unterverzeichnisse erben das Flag (WSL-1-Modus ausgenommen); ein Verzeichnis muss zum Umschalten leer sein; Ändern braucht Administratorrechte. Warnung der Doku: Windows-Anwendungen, die Groß-/Kleinschreibung nicht beachten, „can no longer access the files“ in solchen Verzeichnissen; Dateien, die sich nur in der Schreibung unterscheiden, sind sonst für Windows-Programme nicht erreichbar. windows-sys 0.59: `FileCaseSensitiveInfo = 23` (`Storage::FileSystem`), `FILE_CASE_SENSITIVE_INFO { Flags: u32 }` (`Win32::System::WindowsProgramming`), `FILE_CS_FLAG_CASE_SENSITIVE_DIR = 1` (`Win32::System::SystemServices`) [A: Layout aus windows-sys; die Win32-Doku-Seiten dazu habe ich nicht gefunden – nur die WSL-Seite].
- Microsoft-Namensregel: „Do not assume case sensitivity. For example, consider the names OSCAR, Oscar, and oscar to be the same“; NTFS „supports POSIX semantics for case sensitivity but this is not the default behavior“.

## Zugriffsrechte beim Öffnen des Volumes
- `CreateFile`-Doku: „If this parameter [dwDesiredAccess] is zero, the application can query certain metadata such as file, directory, or device attributes without accessing that file or device, even if GENERIC_READ access would have been denied.“ Abschnitt „Physical Disks and Volumes“: „Direct access to the disk or to a volume is restricted“; für das Öffnen mit Lese-/Schreibzugriff gilt „The caller must have administrative privileges“, `dwCreationDisposition` muss `OPEN_EXISTING` sein, beim Öffnen eines Volumes muss `dwShareMode` `FILE_SHARE_WRITE` enthalten; aber „The dwDesiredAccess parameter can be zero, allowing the application to query device attributes without accessing a device“ (nützlich, um z. - Fehlercodes: Ziel vorhanden ⇒ `ERROR_ALREADY_EXISTS` (183, „Cannot create a file when that file already exists.“) oder `ERROR_FILE_EXISTS` (80, „The file exists.“); welcher von beiden bei `MoveFileExW` ohne Flag kommt, steht nicht in der Doku [A] – Rust std 1.99 bildet beide auf `ErrorKind::AlreadyExists` ab (`sys/io/error/windows.rs:21-22`). ## Zeitstempel auf FAT/exFAT und Sommerzeit
- Microsoft „File Times“: „The NTFS file system stores time values in UTC format, so they are not affected by changes in time zone or daylight saving time. The FAT file system stores time values based on the local time of the computer.“ Abschnitt „File Times and Daylight Saving Time“: „The FAT file system records times on disk in local time. GetFileTime retrieves cached UTC times from the FAT file system. When it becomes daylight saving time, the time retrieved by GetFileTime is off an hour, because the cache is not updated. When you restart the computer, the cached time that GetFileTime retrieves is correct. FindFirstFile retrieves the local time from the FAT file system and converts it to UTC by using the current settings for the time zone and daylight saving time. Therefore, if it is daylight saving time, FindFirstFile takes daylight saving time into account, even if the file time you are converting is in standard time.“ `FileTimeToLocalFileTime` benutzt ebenfalls die **aktuellen** Zeitzonen-/Sommerzeit-Einstellungen. CDFS-Zeiten sind an die lokale Zeitzone angepasst.
- Folge für Rust 1.99 [A]: `fs::read_dir(…).metadata()` bezieht die Zeiten aus `FindFirstFileExW`/`FindNextFileW` (`sys/fs/windows.rs:188-190,1132-1152`), `fs::metadata`/`File::metadata` aus `GetFileInformationByHandle` (`:523-553`) bzw. `FileBasicInfo` (`:558ff.`). Nach den Doku-Aussagen können beide Wege auf FAT um Zeitumstellungen um eine Stunde auseinanderliegen. Mtime-Vergleiche auf FAT daher mit Toleranz (Auflösung 2 s; ±1 h um Zeitumstellungen) und konsistent über **einen** Weg.
- exFAT (Microsoft-Spezifikation 7.4.8–7.4.10): Zeitfelder beschreiben „local date and time, down to a two-second resolution“ (`DoubleSeconds`); `10msIncrement` (0–199 = 0–1990 ms) ergänzt Create und LastModified, LastAccessed hat nur 2 s; `UtcOffset` (7 Bit `OffsetFromUtc` in 15-Minuten-Schritten + Bit `OffsetValid`) „includes the effects of time zones and other date-time adjustments, such as daylight saving and regional summer time changes“; der Wert `00h` steht nur, wenn die lokale Zeit gleich UTC ist (`OffsetValid` = 1), die lokale Zeit unbekannt ist (`OffsetValid` = 1; dann „shall consider UTC to be local date and time“) oder UTC unbekannt ist (`OffsetValid` = 0); ein nicht durch 15 Minuten teilbarer Versatz wird als `00h` gespeichert und ebenfalls als UTC gelesen. exFAT ist damit zeitzonenfähig, FAT nicht.
- Linux-Seite (vfat `tz=UTC`, `time_offset`): Abschnitt „Metadaten“ weiter unten.

## Dateinamen: unzulässige Zeichen, ':' = Alternate Data Stream, reservierte Namen
- Microsoft „Naming Files, Paths, and Namespaces“ (Stand 2024-08-28): erlaubt ist jedes Zeichen der aktuellen Codepage inkl. Unicode **außer** `<` `>` `:` `"` `/` `\` `|` `?` `*`, NUL, den Zeichen 1–31 („except for alternate data streams where these characters are allowed“) und „Any other character that the target file system does not allow“. Ein Dateiname mit `:` legt auf NTFS daher **stillschweigend einen Stream** statt eines Fehlers an (z. B. Datei `a`, Stream `b`) [A: folgt aus der Syntax, nicht ausgeführt]. - Rust 1.99: `ERROR_INVALID_NAME` (123) / `ERROR_BAD_PATHNAME` / `ERROR_FILENAME_EXCED_RANGE` ⇒ `ErrorKind::InvalidFilename` (`sys/io/error/windows.rs:30,65`).

## Ankunft von Volumes (Linux): poll(2) auf /proc/self/mountinfo
- man `proc_pid_mounts(5)`: „Since Linux 2.6.15, this file is pollable: after opening the file for reading, a change in this file (i.e., a filesystem mount or unmount) causes select(2) to mark the file descriptor as having an exceptional condition, and poll(2) and epoll_wait(2) mark the file as having a priority event (POLLPRI). (Before Linux 2.6.30, a change in this file was indicated by the file descriptor being marked as readable for select(2), and being marked as having an error condition for poll(2) and epoll_wait(2).)“ Dieselbe Poll-Funktion hängt der Kernel an `/proc/<pid>/mountinfo`: `proc_mountinfo_operations.poll = mounts_poll` (`fs/proc_namespace.c:317-332`).
- Kernel `mounts_poll` (`fs/proc_namespace.c:21-35`): `res = EPOLLIN | EPOLLRDNORM; poll_wait(file, &ns->poll, wait); if (m->poll_event != ns->event) { m->poll_event = event; res |= EPOLLERR | EPOLLPRI; }`; `mounts_open_common` setzt `m->poll_event = ns->event` **beim Öffnen** (`:236-296`). ⇒ Reihenfolge: **öffnen → komplett lesen (Ausgangszustand) → `poll(POLLPRI)`**; bei `POLLPRI|POLLERR` `lseek(fd, 0, SEEK_SET)`, neu lesen, gegen den alten Zustand vergleichen (neu gelesener Stand kann schon neuer sein ⇒ gelegentlich ein leeres Diff). Ein Ereignis zwischen `open` und erstem `poll` geht nicht verloren (der Zähler wird beim Öffnen gemerkt).
- Der Zähler gilt je **Mount-Namensraum** des öffnenden Prozesses; jede Änderung am Mount-Baum zählt (Mount, Umount, Remount, Bind, Propagation – auch Container-/Overlay-Mounts) [A] ⇒ nach dem Ereignis diffen (Mount-ID, `major:minor`, Mount-Punkt, Typ, Quelle), nicht „etwas ist neu“ annehmen.
- Skizze (**nicht kompiliert**; libc 0.2.186, `std::fs::File` + `AsRawFd`):
```rust
let f = File::open("/proc/self/mountinfo")?;                   // zuerst öffnen
let mut state = parse(read_all(&f)?);                          // Ausgangszustand (lseek(0) vor jedem erneuten Lesen)
let mut p = libc::pollfd { fd: f.as_raw_fd(), events: libc::POLLPRI, revents: 0 };   // POLLERR kommt immer mit
loop {
    let n = unsafe { libc::poll(&mut p, 1, timeout_ms) };
    if n > 0 && p.revents & (libc::POLLPRI | libc::POLLERR) != 0 { /* lseek(0), neu lesen, diff gegen state */ }
}
```
- Nicht geprüft [?]: libmount `mnt_monitor`, udev-Netlink, UDisks2 `InterfacesAdded`, `fanotify`-Mount-Ereignisse; auf Android ist unbelegt, ob `/proc/self/mountinfo` in App-Prozessen lesbar ist und dort bei SD-Karten-Wechsel `POLLPRI` auslöst – dort `StorageManager.registerStorageVolumeCallback` (API 30) verwenden.

## renameat2(2) mit RENAME_NOREPLACE
```c
#define _GNU_SOURCE
#include <fcntl.h>   /* AT_* */
#include <stdio.h>
int renameat2(int olddirfd, const char *oldpath, int newdirfd, const char *newpath, unsigned int flags);
```
- Seit Linux 3.15, glibc 2.28 (man HISTORY). `RENAME_NOREPLACE`: „Don't overwrite newpath of the rename. Return an error if newpath already exists.“ Nicht mit `RENAME_EXCHANGE`. „RENAME_NOREPLACE requires support from the underlying filesystem. Support for various filesystems was added as follows: ext4 (Linux 3.15); btrfs, tmpfs, and cifs (Linux 3.17); xfs (Linux 4.0); Support for many other filesystems was added in Linux 4.9, including ext2, minix, reiserfs, jfs, vfat, and bpf.“
- Fehler (man): `EEXIST` „flags contains RENAME_NOREPLACE and newpath already exists“; **`EINVAL` „The filesystem does not support one of the flags in flags“** (auch: ungültiges Flag, `NOREPLACE`+`EXCHANGE`); `EXDEV` „oldpath and newpath are not on the same mounted filesystem. (Linux permits a filesystem to be mounted at multiple points, but rename() does not work across different mount points, even if the same filesystem is mounted on both.)“ ⇒ Temp-Datei im **Zielverzeichnis** anlegen; `EPERM`/`EACCES` u. a. „the filesystem containing oldpath does not support renaming of the type requested“. BUGS: „On NFS filesystems, you can not assume that if the operation failed, the file was not renamed. If the server does the rename operation and then crashes, the retransmitted RPC which will be processed when the server is up again causes a failure. The application is expected to deal with this.“
- Atomarität der Existenzprüfung (Kernel `fs/namei.c`): `do_renameat2` prüft die Flags (`:6259-6264`, unbekannte Flags und `NOREPLACE|WHITEOUT` mit `EXCHANGE` ⇒ `EINVAL`), nimmt `lock_rename(rd->old_parent, rd->new_parent)` (`:3878`) und liefert **unter dieser Sperre** `-EEXIST`, wenn `d_is_positive(new_dentry) && (rd->flags & RENAME_NOREPLACE)` (`:4104`). Die Dateisysteme verlassen sich darauf: vfat „VFS already handled RENAME_NOREPLACE, handle it as a normal rename“ (`fs/fat/namei_vfat.c:1175`); exFAT „The VFS already checks for existence, so for local filesystems the RENAME_NOREPLACE implementation is equivalent to plain rename. Don't support any other flags“ (`fs/exfat/namei.c:1279-1283`); Android-FUSE „VFS handles request with RENAME_NOREPLACE by ensuring that new file does not exist before redirecting the call to FuseDaemon“ (`FuseDaemon.cpp:1355-1356`).

- `ENOSYS`: Syscall fehlt (Kernel < 3.15) oder ist per Filter gesperrt; Android ≤ 10: **SIGSYS** statt `ENOSYS` (Abschnitt „statx(2)“, Android).
- Rust/libc 0.2.186: `libc::renameat2(olddirfd: c_int, oldpath: *const c_char, newdirfd: c_int, newpath: *const c_char, flags: c_uint) -> c_int` gibt es **nur für glibc** (`src/unix/linux_like/linux/gnu/mod.rs:1067-1073`); `RENAME_NOREPLACE` ist auf Linux `c_uint = 1` (`linux/mod.rs:1575`), auf Android `c_int = 1` (`android/mod.rs:941`). Rust `std::fs::rename` ersetzt immer (`libc::rename`, `sys/fs/unix.rs:1861-1863`).

## systemd `rename_noreplace()` – die Drei-Stufen-Leiter
Quelle `src/basic/fs-util.c:68-111` (Datei zuletzt 2026-07-31, Commit `6b0e3ea`; neueste Release v262, 2026-09-22):
1. `renameat2(olddirfd, oldpath, newdirfd, newpath, RENAME_NOREPLACE)`; Erfolg ⇒ fertig. Weiter nur, wenn `ERRNO_IS_NOT_SUPPORTED(errno) || errno == EINVAL` („renameat2() exists since Linux 3.15, btrfs and FAT added support for it later. If it is not implemented, fall back to a different method.“); jeder andere Fehler (insbesondere `EEXIST`) wird zurückgegeben.
2. `linkat(olddirfd, oldpath, newdirfd, newpath, 0)` + `unlinkat(olddirfd, oldpath, 0)`; scheitert das `unlinkat`, wird der neue Name wieder entfernt (`unlinkat(newdirfd, newpath, 0)`) und der Fehler zurückgegeben. Kommentar: „This doesn't work on directories and on some file systems that do not support hard links (such as FAT, most prominently), but for files it's pretty close to what we want — though not atomic (i.e. for a short period both the new and the old filename will exist).“
3. Weiter nur, wenn das `linkat` mit „not supported“, `EINVAL` oder `EPERM` scheitert („FAT returns EPERM on link()…“): „OK, neither RENAME_NOREPLACE nor linkat()+unlinkat() worked. Let's then fall back to the racy TOCTOU vulnerable accessat(F_OK) check followed by classic, replacing renameat(), we have nothing better.“ ⇒ `faccessat(newdirfd, newpath, F_OK, AT_SYMLINK_NOFOLLOW) >= 0` ⇒ `-EEXIST`; `errno != ENOENT` ⇒ `-errno`; sonst `renameat`.
- `ERRNO_IS_NOT_SUPPORTED` (`src/basic/errno-util.h:162-174`: `static inline bool ERRNO_IS_NEG_NOT_SUPPORTED(intmax_t r)` mit Kommentar „Seven different errors“, acht Werte; `_DEFINE_ABS_WRAPPER(NOT_SUPPORTED)` erzeugt daraus `ERRNO_IS_NOT_SUPPORTED`): `EOPNOTSUPP`, `ENOTTY`, `ENOSYS`, `EAFNOSUPPORT`, `EPFNOSUPPORT`, `EPROTONOSUPPORT`, `ESOCKTNOSUPPORT`, `ENOPROTOOPT`.
- Folgerungen [A]: (a) `EEXIST` aus Stufe 1 ist endgültig, nie in Stufe 2/3 weiterlaufen. (b) Stufe 2 ist **nicht atomar** (beide Namen existieren kurz) und scheidet auf FAT/exFAT/Android-FUSE (kein Hard Link) aus. (c) Stufe 3 ist ein reiner Rennen-anfälliger Test-dann-Umbenennen; wer dort „kein Ersetzen“ zusagen muss, braucht zusätzlich Ausschluss zwischen kooperierenden Schreibern (z. B. Sperrdatei) oder meldet die Veröffentlichung als „nicht atomar zugesichert“. (d) Ein Seccomp-Filter, der `renameat2` mit `EPERM` ablehnt (manche Container-Profile), wird von systemd Stufe 1 nicht als „nicht unterstützt“ behandelt (`EPERM` fehlt in der Liste) [A].

## linkat() + unlink() und O_TMPFILE + linkat()
```c
int link(const char *oldpath, const char *newpath);
int linkat(int olddirfd, const char *oldpath, int newdirfd, const char *newpath, int flags);   // flags: AT_EMPTY_PATH (2.6.39; Privileg siehe unten), AT_SYMLINK_FOLLOW (2.6.18)
```
- man link(2): „If newpath exists, it will not be overwritten.“ Fehler: `EEXIST` „newpath already exists“; **`EPERM` „The filesystem containing oldpath and newpath does not support the creation of hard links“**; `EPERM` bei Verzeichnissen, `fs.protected_hardlinks` (seit 3.6) und unveränderlichen Dateien; `EXDEV` über Mount-Grenzen; `EMLINK` (ext4 ohne dir_index 65 000, btrfs 65 535 Links). Voreinstellung: „since Linux 2.0, Linux does not [dereference oldpath]: if oldpath is a symbolic link, then newpath is created as a (hard) link to the same symbolic link file.“ BUGS: „On NFS filesystems, the return code may be wrong in case the NFS server performs the link creation and dies before it can say so. Use stat(2) to find out if the link got created.“ open(2) (O_EXCL, NFS): „create a unique file on the same filesystem (e.g., incorporating hostname and PID), and use link(2) to make a link to the lockfile. If link(2) returns 0, the lock is successful. Otherwise, use stat(2) on the unique file to check if its link count has increased to 2, in which case the lock is also successful.“ ⇒ nach `EEXIST`/Fehler auf NFS `st_nlink` der Temp-Datei prüfen.
- Keine Hard Links: FAT/vfat (`EPERM`, systemd-Kommentar), exFAT und FAT32 (Microsoft-Vergleichstabelle „Hard links: No“), Android-FUSE-Emulation (`link` ist in `fuse_lowlevel_ops` auskommentiert, `FuseDaemon.cpp:2351` ⇒ Fehler zu erwarten [A]).
- `O_TMPFILE` (open(2), seit Linux 3.11): „Create an unnamed temporary regular file … Anything written to the resulting file will be lost when the last file descriptor is closed, unless the file is given a name.“ Veröffentlichen ohne Zwischenname: `linkat(fd, "", AT_FDCWD, "/pfad/ziel", AT_EMPTY_PATH)` oder `linkat(AT_FDCWD, "/proc/self/fd/<fd>", AT_FDCWD, "/pfad/ziel", AT_SYMLINK_FOLLOW)` (braucht eingehängtes `/proc`; nicht für Dateien, die mit `O_TMPFILE | O_EXCL` geöffnet wurden: `ENOENT`); schlägt mit `EEXIST` fehl, wenn das Ziel existiert (natürliches „kein Ersetzen“). Privileg für `AT_EMPTY_PATH`: man-pages 6.19 nennt „The caller must have the CAP_DAC_READ_SEARCH capability in order to use this flag“ (sonst `ENOENT`); der **Kernel verlangt sie seit v6.10 nur noch, wenn die Zugangsdaten des Dateideskriptors beim Öffnen nicht denen des Aufrufers entsprechen** (master `fs/namei.c:2750-2754` in `path_init`: `fd_file(f)->f_cred != current_cred() && !ns_capable(fd_file(f)->f_cred->user_ns, CAP_DAC_READ_SEARCH)` ⇒ `-ENOENT`, Kommentar `:5961-5966`; Tag v6.10 `:2425-2431`; Tag v6.9 dagegen `:4648` `if (flags & AT_EMPTY_PATH && !capable(CAP_DAC_READ_SEARCH)) … -ENOENT`) – die Man-Seite 6.19 ist an dieser Stelle veraltet. Ältere Kernel (u. a. viele Android-Kernel) ⇒ den `/proc/self/fd`-Weg verwenden [A]. „O_TMPFILE requires support by the underlying filesystem“ (`EOPNOTSUPP`): ursprünglich ext2, ext3, ext4, UDF, Minix, tmpfs; XFS 3.15, Btrfs 3.16, F2FS 3.16, ubifs 4.9 – **nicht** FAT/exFAT/NFS/FUSE aus der Liste [A]. Mit `O_EXCL` lässt sich die Datei nicht mehr verlinken.

## fsync, fdatasync, syncfs – Dauerhaftigkeit nach dem Veröffentlichen
```c
int fsync(int fd);  int fdatasync(int fd);  int syncfs(int fd);   // syncfs: _GNU_SOURCE
```
- man fsync(2): flusht Daten und Metadaten „so that all changed information can be retrieved even if the system crashes or is rebooted. This includes writing through or flushing a disk cache if present. The call blocks until the device reports that the transfer has completed.“ **„Calling fsync() does not necessarily ensure that the entry in the directory containing the file has also reached disk. For that an explicit fsync() on a file descriptor for the directory is also needed.“** `fdatasync()` „does not flush modified metadata unless that metadata is needed in order to allow a subsequent data retrieval to be correctly handled. For example, changes to st_atime or st_mtime … do not require flushing“ ⇒ nach `set_times` ist `sync_all` (fsync) nötig, `sync_data` genügt für die Zeitstempel nicht. Fehler: `EIO` („may relate to data written to some other file descriptor on the same file. Since Linux 4.13, errors from write-back will be reported to all file descriptors that might have written the data“), `EINVAL` („fd is bound to a special file (e.g., a pipe, FIFO, or socket) which does not support synchronization“), `EROFS`, `ENOSPC`/`EDQUOT` („fd is bound to a file on NFS or another filesystem which does not allocate space at the time of a write(2) system call, and some previous write failed due to insufficient storage space“).
- Muster (Reihenfolge) [S: PostgreSQL `durable_rename`, `src/backend/storage/file/fd.c:783-853`]: `fsync(Temp)` → `rename` → `fsync(neuer Name)` → `fsync(Elternverzeichnis)`. Für „kein Ersetzen“: `File::sync_all()` auf der Temp-Datei → `renameat2(NOREPLACE)` (bzw. Leiter) → `sync_all()` auf einem **Verzeichnis-`File`** des Elternverzeichnisses (`File::open(dir)` = `O_RDONLY|O_CLOEXEC`; auf Unix möglich [A]).
- Verzeichnis-fsync-Fehler, die „nicht unterstützt“ bedeuten: PostgreSQL ignoriert für Verzeichnisse `EBADF`/`EINVAL` („Some OSes don't allow us to fsync directories at all“, `fd.c:3884-3890`). FUSE: `fuse_dir_fsync` gibt `0` zurück, ohne etwas zu senden, wenn der Server `fsyncdir` nicht kennt (`fc->no_fsyncdir`, ein `-ENOSYS` des Servers wird zu `0`, `fs/fuse/dir.c:1937-1958`) ⇒ Erfolg ohne Garantie. Die Android-Emulation implementiert `fsyncdir` (`FuseDaemon.cpp` ops-Tabelle) [A].
- `syncfs(2)`: „synchronizes just the filesystem containing file referred to by the open file descriptor fd“; „Linux waits for I/O completions, and thus sync() or syncfs() provide the same guarantees as fsync() called on every file in the system or filesystem respectively.“ „In mainline kernel versions prior to Linux 5.8, syncfs() will fail only when passed a bad file descriptor (EBADF). Since Linux 5.8, syncfs() will also report an error if one or more inodes failed to be written back since the last syncfs() call.“ Seit Linux 2.6.39, glibc 2.14; bionic `syncfs` ab API 28 (`libc.map.txt` `LIBC_P`); libc 0.2.186 `libc::syncfs(fd: c_int) -> c_int` (`linux/mod.rs:4226`, `android/mod.rs:3735`). Stapelbetrieb: ein `syncfs` am Ende vieler Veröffentlichungen statt je ein Verzeichnis-`fsync` [A].
- Rust 1.99: `File::sync_all` ruft `sys::fs::File::fsync` = `libc::fsync` in `cvt_r` (Wiederholung bei `EINTR`; Apple `F_FULLFSYNC`), `File::sync_data` ruft `datasync` = `libc::fdatasync` auf Linux/Android (`sys/fs/unix.rs:1264-1301`); std-Doku: `sync_all` „Attempts to sync all OS-internal file content and metadata to disk“, `sync_data` „might not synchronize file metadata“.

## Öffnen fremder Dateien: O_NOFOLLOW | O_NONBLOCK | O_NOCTTY + fstat(S_ISREG)
- open(2) `O_NOFOLLOW`: „If the trailing component (i.e., basename) of path is a symbolic link, then the open fails, with the error ELOOP. Symbolic links in earlier components of the pathname will still be followed. (Note that the ELOOP error that can occur in this case is indistinguishable from the case where an open fails because there are too many symbolic links found while resolving components in the path prefix of the pathname.)“ `O_NONBLOCK`: „When possible, the file is opened in nonblocking mode. Neither the open() nor any subsequent I/O operations on the file descriptor which is returned will cause the calling process to wait.“ … „this flag has no effect for regular files and block devices“. `O_NOCTTY`: „If path refers to a terminal device—see tty(4)—it will not become the process's controlling terminal even if the process does not have one.“
- fifo(7): „Normally, opening the FIFO blocks until the other end is opened also. A process can open a FIFO in nonblocking mode. In this case, opening for read-only succeeds even if no one has opened on the write side yet and opening for write-only fails with ENXIO.“ ⇒ ohne `O_NONBLOCK` blockiert `File::open` auf einer FIFO unbegrenzt. `open(2)` `ENXIO`: „The file is a UNIX domain socket“ (Socket-Datei lässt sich nicht öffnen); „The file is a device special file and no corresponding device exists.“
- Danach `fstat` (Rust: `file.metadata()?.file_type().is_file()`; `std::os::unix::fs::FileTypeExt::{is_block_device, is_char_device, is_fifo, is_socket}` seit 1.5.0). man inode(7): `S_ISREG(m)`, `S_ISDIR`, `S_ISCHR`, `S_ISBLK`, `S_ISFIFO`, `S_ISLNK`, `S_ISSOCK`. Nicht-reguläre Dateien melden und auslassen (nie lesen/synchronisieren); Verzeichnis-`fsync` und Sync auf Spezialdateien liefert `EINVAL`.
- Rust: `OpenOptionsExt::custom_flags(&mut self, flags: i32) -> &mut Self` (1.10.0): „Pass custom flags to the flags argument of open. The bits that define the access mode are masked out with O_ACCMODE … Custom flags can only set flags, not remove flags set by Rust's options. This function overwrites any previously-set custom flags.“ std ergänzt `O_CLOEXEC` selbst (`sys/fs/unix.rs:1233-1236`); `create_new(true)` = `O_CREAT | O_EXCL` (`:1205`). Mit `OpenOptionsExt::mode(&mut self, mode: u32)` (1.1.0) lässt sich der Anfangsmodus (umask-abhängig) setzen. Skizze (**nicht kompiliert**):
```rust
use std::{fs::OpenOptions, os::unix::fs::OpenOptionsExt};
let f = OpenOptions::new().read(true)
    .custom_flags(libc::O_NONBLOCK | libc::O_NOFOLLOW | libc::O_NOCTTY).open(path)?;   // ELOOP bei Symlink als letztem Element
if !f.metadata()?.file_type().is_file() { /* FIFO, Socket, Gerät, Verzeichnis: auslassen und melden */ }
```
- Gerätedateien zu öffnen kann Nebenwirkungen haben (Band, tty) [A] ⇒ vorher `symlink_metadata` auf `is_file()` prüfen und nach dem `open` per `fstat` (Gerät/Inode) auf Gleichheit prüfen (TOCTOU).
- Zwischenverzeichnisse: `O_NOFOLLOW` schützt nur das letzte Element. `openat2(2)` (Linux 5.6; kein glibc-Wrapper, `long syscall(SYS_openat2, int dirfd, const char *path, struct open_how *how, size_t size)`) mit `RESOLVE_NO_SYMLINKS` – „Disallow resolution of symbolic links during path resolution. This option implies RESOLVE_NO_MAGICLINKS“; „the effect of the RESOLVE_NO_SYMLINKS flag, which affects the treatment of symbolic links in all of the components of path, differs from the effect of the O_NOFOLLOW file creation flag (in how.flags), which affects the handling of symbolic links only in the final component of path“ – ist unter Android **nicht aufrufbar** (nicht in `SYSCALLS.TXT`, SIGSYS). Android: Schrittweises `openat(dirfd, name, O_NOFOLLOW | O_DIRECTORY)` je Komponente ist die portable Alternative [A].

## utimensat/futimens und Rust `set_times` (Unix)
```c
int utimensat(int dirfd, const char *path, const struct timespec times[_Nullable 2], int flags);   // flags: AT_EMPTY_PATH (5.8), AT_SYMLINK_NOFOLLOW
int futimens(int fd, const struct timespec times[_Nullable 2]);
```
- man: `times[0]` = atime, `times[1]` = mtime (Sekunden + Nanosekunden seit der Epoche); `UTIME_NOW`/`UTIME_OMIT` im Feld `tv_nsec` (dann wird `tv_sec` ignoriert); **„Updated file timestamps are set to the greatest value supported by the filesystem that is not greater than the specified time.“** (abgerundet auf die Granularität); „The status change time (ctime) will be set to the current time, even if the other time stamps don't actually change.“ Rechte: beide Zeiten auf „jetzt“ ⇒ Schreibrecht, Besitzer oder `CAP_FOWNER`; jede andere Änderung ⇒ Besitzer oder `CAP_FOWNER` (`EPERM`); `append-only`/`immutable` ⇒ `EPERM`. Seit Linux 2.6.22, glibc 2.6. `AT_EMPTY_PATH` seit 5.8.
- Rust 1.99: `File::set_times(&self, times: FileTimes) -> Result<()>` und `File::set_modified(&self, time: SystemTime) -> Result<()>` seit **1.75.0**; `FileTimes::new()` setzt nichts, `.set_accessed(t)`/`.set_modified(t)` (1.75.0). std-Doku: „currently corresponds to the futimens function on Unix (falling back to futimes on macOS before 10.13) and the SetFileTime function on Windows“. Unix-Umsetzung `sys/fs/unix.rs:1558-1624`: nicht gesetzte Zeit ⇒ `tv_nsec = UTIME_OMIT` (`file_time_to_timespec`, `:1630-1647`); nicht darstellbare Zeit ⇒ `InvalidInput` („timestamp is too large/small to set as a file time“); **Android**: `weak!`-Aufruf von `futimens`, sonst `Unsupported` („setting file times requires Android API level >= 19“, `:1581-1596`); 32-Bit-glibc nutzt `__futimens64`, falls vorhanden. 32-Bit-Ziele (`time_t` = i32): Zeiten nach 2038 nicht setzbar [A].
- Präzision [A]: Unix-`timespec` hat Nanosekunden; was gespeichert wird, bestimmt das Dateisystem (FAT 2 s, exFAT 10 ms, NTFS 100 ns, ext4/btrfs/xfs ns). Nach dem Setzen ist die gelesene mtime ≤ der gesetzten (Abrundung) ⇒ Vergleiche mit Toleranz ≥ Granularität des **Ziels**.
- vfat (Kernel-Doku `Documentation/filesystems/vfat.rst`, identisch in mount(8)): **`tz=UTC`** „Interpret timestamps as UTC rather than local time. This option disables the conversion of timestamps between local time (as used by Windows on FAT) and UTC (which Linux uses internally). ## Linux: logind-Inhibitor (D-Bus `Inhibit`) und `systemd-inhibit`
```
// Systembus, Dienst org.freedesktop.login1, Objekt /org/freedesktop/login1, Schnittstelle org.freedesktop.login1.Manager
Inhibit(in s what, in s who, in s why, in s mode, out h pipe_fd)
```
- man `org.freedesktop.login1(5)`: „Inhibit() creates an inhibition lock. It takes four parameters: what, who, why, and mode. what is one or more of "shutdown", "sleep", "idle", "handle-power-key", "handle-suspend-key", "handle-hibernate-key", "handle-lid-switch", separated by colons … mode is either "block" or "delay" which encodes whether the inhibit shall be consider mandatory or whether it should just delay the operation to a certain maximum time, while the "block-weak" and variants will create an inhibitor that is automatically ignored in some circumstances. The method returns a file descriptor. The lock is released the moment this file descriptor and all its duplicates are closed.“
- systemd `docs/INHIBITOR_LOCKS.md`: `sleep` „inhibits system suspend and hibernation requested by (unprivileged) users“; `shutdown` „inhibits high-level system power-off and reboot requested by (unprivileged) users“; **`idle` „inhibits that the system goes into idle mode, possibly resulting in automatic system suspend or shutdown depending on configuration“**; Modi: `block` „inhibits operations entirely until the lock is released. If such a lock is taken the operation will fail (but still may be overridden if the user possesses the necessary privileges)“; `delay` „inhibits operations only temporarily, either until the lock is released or up to a certain amount of time“ (`InhibitDelayMaxSec=`, Standard 5 s, „This mode is only available for sleep and shutdown locks“); `block-weak` „identical to block, but has no effect on operations requested by root or by the user owning the inhibitor lock“. **„As soon as the file descriptor is closed (and all its duplicates) the lock is automatically released. If the client dies while the lock is taken the kernel automatically closes the file descriptor so that the lock is automatically released.“** `delay` taugt also nicht zum Wachhalten.
- logind.conf(5): `IdleAction=` wird erst ausgeführt, „after all sessions report that they are idle, no idle inhibitor lock is active, and subsequently, the time configured with IdleActionSec= … has expired“. **`LidSwitchIgnoreInhibited=` Standard „yes“: „when systemd-logind is handling events by itself (no low level inhibitor locks are taken by another application), the lid switch does not respect suspend blockers by default, but the power and sleep keys do.“** (`PowerKeyIgnoreInhibited=`, `SuspendKeyIgnoreInhibited=`, `HibernateKeyIgnoreInhibited=`, `RebootKeyIgnoreInhibited=` Standard „no“.) ⇒ Ein `sleep`-/`idle`-Lock hält das Gerät gegen Leerlauf- und Tasten-Suspend wach, **nicht** gegen das Zuklappen des Deckels (wie unter Windows); die Low-Level-Locks `handle-*` nicht nehmen (sie schalten die Tastenbehandlung des Desktops ab). `InhibitorsMax` Standard 8192.
- Empfehlung [A]: `what = "idle:sleep"`, `mode = "block"` (kein `shutdown`: ein Sync soll das Herunterfahren nicht blockieren), `who` = Programmname, `why` = kurzer Grund.
- **Polkit** (`src/login/org.freedesktop.login1.policy`): `org.freedesktop.login1.inhibit-block-sleep`: `allow_any` = **`auth_admin_keep`**, `allow_inactive` = `yes`, `allow_active` = `yes` (implizit zusätzlich `inhibit-delay-sleep` und `inhibit-block-idle`); `inhibit-block-idle`: alle drei **`yes`**; `inhibit-delay-sleep`: `yes`. polkit.8: `allow_any` „Implicit authorizations that apply to any client“, `allow_inactive` „clients in inactive sessions on local consoles“, `allow_active` „clients in active sessions on local consoles“. ⇒ Aus einer SSH-Sitzung, einem Dienst ohne lokale Sitzung oder einer Remote-Session braucht `block`+`sleep` Administrator-Authentifizierung (ohne Agent schlägt der Aufruf fehl), **`idle` ist immer erlaubt** [A: Zuordnung der Aufrufer zu `allow_any` nicht ausgeführt]. ## Windows-Autostart im Task-Manager abgeschaltet: `StartupApproved\Run`
- Microsoft „Run and RunOnce Registry Keys“ (Stand 2026-02-21): `HKCU`/`HKLM` `\Software\Microsoft\Windows\CurrentVersion\Run`; „The data value for a key is a command line no longer than 260 characters.“ „The system does not provide guarantees about how promptly the programs in the Run key are run.“ **`StartupApproved` kommt in der Microsoft-Doku nicht vor** ⇒ undokumentiert, Belege nur sekundär [S].

Schreiben (`:659-690`): aktivieren = `DeleteValue` im `StartupApproved`-Schlüssel; deaktivieren = `REG_BINARY {03 00 00 00 00 00 00 00 00 00 00 00}`; Autostart ganz aus ⇒ beide Werte löschen.
- [S] Windows-IR-Blog (2022-07): Schlüssel `[HKLM|HKCU]\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run` und `…\StartupFolder`; „the binary data for each values is 12 bytes in length“; „If the first 4 bytes (DWORD) is 0x02 or 0x06, then the corresponding value in the Run key is enabled“; „If the first DWORD is 0x03, then the value is disabled, and the remaining 8 bytes (QWORD) is the FILETIME object representing the data and time that the value was disabled.“ `Run32`: PolyScour-PR #27: „Windows keeps the approval byte for `HKLM\SOFTWARE\WOW6432Node\...\Run` values in `StartupApproved\Run32`, not `StartupApproved\Run`.“ Hexacorn: „This key is populated by Task Manager/Startup tab when we enable/disable entries“. PowerShell-Forum: „a value of 02 00 00 00 00 00 00 00 00 00 00 00 is enabled and anything else is disabled“ (nur 02/03 belegt).

# Offene Punkte
1. **Windows-Identität**: `GetVolumeInformationW`/`…ByHandleW` über SMB (Doku-Tabelle „No“, aber UNC-Share-Stamm als gültige Wurzel genannt) und mit einem Null-Zugriff-Handle sind nicht belegt; Unterstützung von `FILE_ID_INFO` auf FAT/exFAT/UDF steht nirgends (Doku nennt nur SMB 3.0, TFO, SO, ReFS „Yes“); Beziehung der 32-Bit-`dwVolumeSerialNumber` zur 64-Bit-`FILE_ID_INFO.VolumeSerialNumber` ist nicht dokumentiert; Win32-Doku zu `FILE_CASE_SENSITIVE_INFO`/`FileCaseSensitiveInfo` nicht gefunden (nur WSL-Seite und windows-sys-Layout).
2. **Windows-Klassifizierung/Ankunft**: Öffnen eines Volumes mit Zugriff 0 für `IOCTL_STORAGE_QUERY_PROPERTY` ist nur durch die `CreateFile`-Aussage und sysinfo [S] gestützt (Microsoft nennt für den IOCTL keine Rechte); Verhalten bei dynamischen Datenträgern/Storage Spaces und die Zuordnung `BusTypeSd`/`BusTypeMmc` je Treiber nicht gemessen; Reihenfolge „Volume-Schnittstelle erscheint“ → „Laufwerksbuchstabe/Dateisystem bereit“ ist nicht dokumentiert (hier als Wiederhol-Aufzählung empfohlen); ob ein `HWND_MESSAGE`-Fenster registrierte Geräte-Benachrichtigungen erhält, steht nicht in der Doku.
3. **Windows-Veröffentlichen**: Mindestversionen der einzelnen `FILE_RENAME_FLAG_*` (nur `FileRenameInfoEx` ab Windows 10 1607 aus dem Header-Guard); Wirkung von `MOVEFILE_WRITE_THROUGH` bei reiner Umbenennung; ob `FlushFileBuffers` auf einem Verzeichnis-Handle etwas bewirkt und ob NTFS Umbenennungen über sein Journal absichert (nicht aus Microsoft-Doku belegt); welcher Fehlercode (80 oder 183) `MoveFileExW` ohne Flag liefert; Widerspruch der WDK-Regel „A file cannot be renamed if it has any open handles …“ zur Praxis mit `FILE_SHARE_DELETE`; Wirkung von `FILE_FLAG_OPEN_NO_RECALL` auf Cloud-Platzhalter und Mindestversion von `RtlSetProcessPlaceholderCompatibilityMode`; Rust-Doku zu `set_times` auf Verzeichnissen (Windows ohne `FILE_FLAG_BACKUP_SEMANTICS`).
4. **Wachhalten**: Thread-Lebensdauer des `SetThreadExecutionState`-Zustands nicht dokumentiert; `StartupApproved` ist undokumentiert (Belege nur [S]: Werte `02`/`06` aktiv, `03` + FILETIME deaktiviert; `07`/andere nicht belegt; `Run32`/`StartupFolder` nur erwähnt); polkit-Zuordnung von SSH-/Dienst-Aufrufern zu `allow_any` nicht ausgeführt; Verhalten von logind-Locks bei Aufruf ohne Sitzung nicht getestet.
5. **Linux**: Stabilitätsversprechen für das udev-DB-Format (`/run/udev/data`) nicht gefunden (nur libudev/`udevadm` als stabile Wege); libmount-Monitor, udev-Netlink, UDisks2 und fanotify-Mount-Ereignisse nicht geprüft; `removable` bei USB-Festplatten ist bridge-abhängig (INQUIRY-Bit), SD-am-eingebauten-Leser-Pfad nicht gemessen; Kernel-Aussagen sind `master` vom 2026-10-02 (Zeilennummern driften, ältere Kernel können abweichen; `FS_XFLAG_CASEFOLD` erst ab v7.2); `ntfs-3g` ⇒ `EINVAL` bei `RENAME_NOREPLACE` ist aus Quelltext und `fuse_rename2` abgeleitet, nicht ausgeführt; Container-Seccomp-Profile mit `EPERM` für `renameat2` nicht belegt; `link()`-Fehlercode auf Android-FUSE nicht gemessen.
6. **Android**: Das Seccomp-Ergebnis (API ≤ 29: `renameat2`/`statx` ⇒ SIGSYS) ist aus `SYSCALLS.TXT`-Tags und `seccomp_policy.cpp` abgeleitet, nicht am Gerät geprüft; ob `/proc/self/mountinfo` in App-Prozessen lesbar ist und bei SD-Karten-Wechsel `POLLPRI` auslöst, ist unbelegt; Wirkung von `fsyncdir` der FUSE-Emulation auf das Lower-Dateisystem nicht gelesen; die ignorierten `chmod`/`chown`-Anfragen stammen aus dem `main`-Quelltext (ältere Android-Versionen können abweichen).
7. **Unicode**: Unicode-Version der `icu_normalizer_data 2.2.0`-Daten nicht belegt; Binärgröße der Tabellen von `unicode-normalization` nicht gemessen; „keine neuen Pakete“ für `icu_normalizer` folgt aus dem Lock-Eintrag (kein Cargo-Lauf); Verhalten der OS-Normalisierer (Windows `NormalizeString`, Android ICU) nicht geprüft.
8. **Allgemein**: Alle Codeblöcke „Skizze“ sind nicht kompiliert; alle `datei:Zeile`-Angaben beziehen sich auf den Abrufstand (Kernel/systemd/AOSP `master`/`main`, Rust 1.99.0). Die Windows-Aussagen zu Standardbenutzer-Rechten (Volume öffnen, `CM_Register_Notification`) sind nicht auf einem Windows-System ausgeführt worden und im Windows-Ziel-Job der Remote-Suite zu prüfen.
